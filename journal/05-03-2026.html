May 3, 2026 Homelab Learning

Configuration as Code

Ansible has been on the roadmap since the conversation with the network engineering manager — the one where automation came up as a team priority and I mentally moved it from "eventually" to "now." Today was the day I actually sat down and built it out. A new LXC, a real inventory, the first working playbooks. But the more interesting outcome was what the process surfaced: five nodes I thought were consistently configured, and a NUT setup that turned out to have enough drift between nodes to warrant tearing it down and rebuilding it from a single source of truth.

The control node

Ansible is agentless — it connects over SSH and runs tasks remotely. All you need is one place to run it from. I provisioned a small Debian LXC on Ankhh at 10.10.10.106: one core, 512MB of RAM, 8GB of disk. It barely uses any of that. Its only job is to hold the playbooks and SSH out to the other nodes.

Rather than use root for remote connections, I created a dedicated ansible user on each Proxmox host with passwordless sudo, then generated an ed25519 key pair on the control node and distributed the public key across all five hosts. The first real Ansible command — ansible all -m ping — returned green across the board on the first try, which felt like an unusually clean start.

Inventory and group vars

The inventory is a YAML file that describes all five nodes, their IPs, and how they're grouped. Groups matter because they let you scope playbooks precisely — run something against proxmox_nodes to hit everything, or against nut_slaves to hit only the four nodes that aren't the NUT master. The grouping maps directly to the real topology rather than being an arbitrary organizational convenience.

Variables shared across all nodes live in group_vars/all.yml: the NUT server address, shutdown thresholds, the node_exporter version to pin, the common package list. The idea is that changing node_exporter_version in one file and running the playbook is enough to update every node. No more SSHing into five machines individually, no more wondering whether they all ended up the same.

The first playbooks

I wrote four to start. A baseline playbook that ensures the same set of packages is present on every node — lm-sensors, nut-client, curl, htop, the fundamentals that should exist everywhere but had somehow drifted. A node_exporter playbook that checks the installed version against a pinned target, downloads and installs only if they don't match, and enforces an identical systemd unit across all five hosts. An audit playbook that collects the state of every service I care about — version numbers, active/inactive, installed or not — and prints a summary per node without touching anything. And a rolling update playbook that runs apt upgrade one node at a time with serial: 1 so the cluster is never being patched simultaneously.

The audit playbook was the most immediately useful. Running it against the existing infrastructure before touching anything is how I found out the nodes weren't as consistent as I'd assumed.

What the audit found

The discrepancies weren't dramatic. Nobody was running a wildly different NUT version or missing a package entirely. It was the smaller things — POLLFREQ values that didn't match between nodes, notification flags that were present on some hosts and absent on others, a FINALDELAY that was set differently on PBS than everywhere else. The kind of thing that happens when you configure five machines by hand over the course of several weeks, copying and editing config snippets each time.

Configuration drift is almost never dramatic. It accumulates in small decisions made under time pressure — a value that seemed fine at the time, a flag that got added to one node but not the others. The audit doesn't find catastrophes. It finds the quiet inconsistencies that only matter when something goes wrong.

Once I started looking at the NUT configs carefully, I also noticed something more fundamental. The MONITOR line on the slave nodes was using the old NUT terminology — master and slave on the type field — rather than the current primary and secondary that NUT adopted in version 2.8. Debian 12 ships 2.8.x. Everything was still functioning because NUT maintains backward compatibility during the transition, but running a mix of old and new terminology across five nodes with no clear reason why felt like exactly the kind of thing Ansible exists to prevent.

Rebuilding NUT from a single source

Rather than patch individual files, I mapped out the correct config for every node from scratch and encoded it into two playbooks. One for Ankhh, which runs the full NUT server — upsd, the usbhid-ups driver, and its own upsmon as primary. One for everything else, which runs only nut-client and connects to Ankhh as a secondary. The distinction matters more than it might look.

Ankhh gets four config files. The other four nodes get two. The one that most people configure wrong — or inconsistently — is the MONITOR line in upsmon.conf. It contains the power value: 1 for the primary, 0 for all secondaries. That number isn't cosmetic. A power value of 1 gives a node the authority to issue a forced shutdown broadcast to every connected client when it decides the UPS condition is critical. The wrong value on the wrong node, and the shutdown logic doesn't behave the way you expect it to when it actually matters. 

MONITOR cyberpower@10.10.10.55:3493 0 upsmon_slave [password] secondary

The credentials are stored in an Ansible Vault-encrypted file — the first time I've used Vault in practice rather than just reading about it. The playbook references {{ vault_upsmon_slave_password }} and the actual value never appears in plaintext anywhere in the repository. Small thing, right practice.

Running order

The master playbook runs first against Ankhh, brings nut-server up, and verifies that upsd is listening on port 3493 and that upsc cyberpower@localhost returns real data before the play ends. Only then does the slave playbook run against the other four. The final task on each slave queries upsc cyberpower@10.10.10.55 and prints what it sees — a concrete confirmation that the node can reach the master and is monitoring the right UPS with the right credentials. 

ansible ankhh -m command -a "upsc cyberpower@localhost ups.status"
ankhh | CHANGED | rc=0 >>
OL

All five nodes came up clean. The shutdown thresholds are consistent — 20% battery or 300 seconds of runtime remaining, matching what was always intended but not always enforced. The notification flags are identical across every node. The terminology is standardized on primary and secondary throughout.

What Ansible actually teaches you

Something becomes clear pretty quickly when you start writing playbooks: the exercise of encoding a configuration into a playbook forces you to understand it at a different level than configuring it by hand does. When you write the task that sets the MONITOR line, you have to know exactly what every field means. When you write the handler that restarts nut-monitor only when the config file actually changed, you have to understand the dependency between the config and the service. The playbook is documentation that also runs.

Running a playbook in --check --diff mode against a node you've configured by hand is one of the more honest things you can do as a homelab operator. It shows you exactly what you said the config should be versus what it actually is. The diff is the audit.

What's next

The Ansible LXC is running. The inventory covers all five nodes. The first real playbooks — baseline packages, node_exporter, NUT master and slave configs, rolling updates — are tested and committed. The next additions are Glances standardization across all nodes, and eventually refactoring the longer playbooks into proper roles once the structure is clear enough to warrant it.

The broader point is that the homelab now has a control plane for its own configuration. Changes get made in the playbooks, applied through Ansible, and the nodes converge to the declared state. The alternative — SSHing into each machine individually, editing files, trying to remember what you changed and where — was how the NUT drift happened in the first place.
