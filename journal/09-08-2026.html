The Sensor That Lied About What It Was

First real hardware project in the lab, after months of everything being virtual machines, containers, and config files: an ESP32 and a temperature/humidity breakout board, meant to report rack conditions into the same Prometheus stack already tracking everything else. It ended up being a good crash course in a different kind of debugging — one where the bug can be a wrong cable, not a wrong line of code.

Tooling problems before any code ran at all

Never having touched an ESP32 before, step one was just getting the Arduino IDE talking to the board at all. Two separate failures stacked on top of each other: the board's CP2102 USB-to-serial chip needed its own driver installed before Windows would even show a COM port, and — separately — the USB cable that shipped in the bundle turned out to be charge-only, no data lines at all. Neither failure looked like the other. Both looked identical from the outside: nothing shows up, no error message, just silence. Swap the cable, install the driver, and a board that had shown zero signs of life for twenty minutes uploaded cleanly on the first real attempt.

A sensor that answered, but wasn't what it claimed

Wiring was straightforward once the board itself worked — four wires, I2C, done. Except the sketch kept reporting "BME280 not found," despite everything being connected correctly by every check available: continuity, correct pins, 3.3V confirmed instead of 5V. An I2C bus scanner confirmed a device really was responding at the expected address. So something was responding. The library just refused to recognize it.

That gap — hardware present, library rejecting it anyway — is exactly the kind of situation where the fix is reading the actual source instead of trusting an abstraction on top of it. The Adafruit BME280 library checks a chip ID register during initialization and silently fails if it doesn't match. Bypassing the library entirely and reading that register directly over raw I2C settled it in one shot: chip ID 0x58. A genuine BME280 reports 0x60. 0x58 is Bosch's BMP280 — same footprint, same default I2C address, no humidity sensor at all. The board was never lying about being on the bus. It was mislabeled at the listing level, and the address alone couldn't have told the difference — only the chip's own identification register could.

The address a device answers at and the device's actual identity are two different questions. An address confirms something is there. It says nothing about what that something actually is.

Fixing the code around what the hardware actually is

Once the real chip was known, the fix was small: swap to the BMP280 library, drop the humidity metric from the Prometheus-format output entirely rather than reporting a fake or constant value for a sensor that isn't physically present. One near-miss along the way — writing bmp.begin(0x58) before catching that 0x58 is the chip ID, not the I2C address, which is still 0x76. Two different numbers, easy to conflate right after just having spent ten minutes staring at one of them on a screen.

Fitting it into infrastructure that already existed

The rest was familiar ground: the same VLAN and Wi-Fi work from the AP bring-up a week earlier made a decision easy here too — this first sensor lives on the flat main LAN rather than an isolated VLAN, on purpose, while still learning the board's basic behavior. Segmentation is the right long-term shape, once the hardware itself isn't a variable anymore. Getting the sensor into Prometheus was a two-line addition to an already-running scrape config — same shape as every node_exporter target already there, the ESP32 just serving its own tiny /metrics endpoint in the same plain-text format Prometheus already reads everywhere else.

None of today's actual problems were exotic. A bad cable. A missing driver. A component that wasn't quite what its own listing said. What made each one solvable in reasonable time was the same habit that already runs through everything else in this lab: when something that should obviously work doesn't, go check the actual source directly — the chip's own register, the device manager's own port list — rather than re-reading the same code or the same wiring diagram a fourth time hoping to spot something new in it.
