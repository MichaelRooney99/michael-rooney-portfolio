Two Modals, One Real Difference Between Them

Two components in the same application, both rendered as full-screen overlays on top of everything else, both keeping track of real internal state as a person interacts with them. On the surface, close to the same kind of thing. Look at what each one actually does the moment it appears, though, and they land on opposite sides of a real, meaningful line — one that has nothing to do with being a modal at all.

The actual question worth asking

The real distinction isn't about layout or visual style. It's whether a component is a window into data its parent already has, or whether it's a self-contained feature that goes and gets its own data the moment it needs it. The first kind — call it presentational — takes what it's handed, displays it, and would render identically given the same input twice. The second kind — a container — actively does something beyond displaying: it reaches out, fetches, manages its own data lifecycle, independent of whatever its parent happens to already have sitting around.

A real counter-example worth having, not just a definition

One of the two overlays in question fetches its own data the instant it mounts — real network activity, tied to its own lifecycle, not something its parent already had lying around. The other, despite looking structurally almost identical — the same kind of full-screen treatment, the same amount of real internal state to track — receives everything it needs as plain props from its parent. Same visual pattern. Opposite category, for a very concrete reason: one of them needs information its parent doesn't already possess (details specific to one thing someone just clicked), and the other only ever needs information the parent already has sitting in memory for other reasons.

Why this needs a real example to actually land

It would have been easy to accept a definition like "presentational versus container" as a clean abstract rule and move on. What actually made it stick was finding two components that share almost every surface trait — same UI pattern, same general complexity, built around the same time in the same codebase — and only diverging on the one thing that actually matters. That's usually the difference between memorizing a rule and actually being able to apply it later: not the definition itself, but having a real case where two things looked alike and weren't.

Why the split is worth keeping deliberately

The practical value isn't philosophical. A component that only ever renders what it's given is trivial to test, easy to reason about, safe to reuse anywhere the right data happens to be available. A component that manages its own data fetching carries real responsibility — loading states, error states, its own lifecycle — and deserves to be treated with more care specifically because of that, not lumped in with the simpler kind just because it happens to share a visual style. Knowing which one you're looking at, on sight, is worth being able to do quickly — and the only reliable way to check is asking exactly one question: does this thing know how to get its own data, or does it only know how to show what it's been handed.
