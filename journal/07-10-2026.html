Giving the Capstone a Real Home

The capstone deployment plan on paper — a Docker LXC on Shasta at 10.10.10.110 — was never wrong, exactly. It was just the default placement, not a deliberate one. Today that plan got replaced with something more intentional: a sixth M920Q, reviving the Dega name, built from the start as an isolated home for the status page rather than one more service folded into the existing Docker host.

Not a general-purpose node

The distinction that shaped everything else today: Dega isn't a place the capstone could run. It's the place built specifically because the capstone needed one. Once framed that way, putting it on VLAN 20 stopped being an interesting architectural experiment and became the obvious answer — a public-facing status page reachable from the internet via a Cloudflare tunnel has no business sharing a subnet with Vaultwarden or the NUT server. The isolation isn't a feature bolted on afterward. It's the reason the node exists on its own subnet at all.

Firewall rules — scoped to what the proxy actually needs

The tricky part of isolating a node that's supposed to host something is remembering that isolation cuts both directions. VLAN 20's existing rule blocks that subnet from reaching 10.10.10.0/24 outright — which would silently break the capstone's entire reason for existing, since the Express proxy makes outbound calls to three internal services on every poll cycle:

  • 10.10.10.55:8006 — Proxmox API (Ankhh)
  • 10.10.10.105:9090 — Prometheus
  • 10.10.10.108:8090 — Zabbix JSON-RPC

Rather than opening VLAN 20 back up broadly, each of those got its own narrow allow rule, scoped to the capstone VM's specific IP rather than the whole subnet, sitting above the existing block rule so OPNsense evaluates them first. Ansible gets the same treatment — one rule, port 22 only, control node to Dega. Kuma still doesn't get a pinhole; Prometheus and Zabbix already cover availability monitoring for this node the same way they do for the rest of the fleet, so a third path through the firewall would only be adding an opening, not adding coverage.

The failure mode I was specifically trying to avoid here: Promise.allSettled in the capstone's services facade swallows failed adapters silently by design — partial visibility over a blank page. That's the right behavior for the app, but it means a firewall misconfiguration and a real bug look identical from the UI. If the Proxmox category just vanished after deployment, I wanted the playbook to have already ruled the network layer out before I went looking anywhere else.

To make that concrete, the provisioning playbook ends with three wait_for checks — Dega reaching Ankhh, Prometheus, and Zabbix on their respective ports — before considering the node ready. If those pass, any future "category disappeared" debugging starts from the assumption that it's a code or permissions issue, the same pattern from the Session 4 capstone debugging, not a network one.

Ansible — retargeting, not rebuilding

The playbooks from the original Shasta-hosted plan didn't need new logic, just a new destination. The inventory group renamed from a placeholder to capstone_host, pointed at Dega's VM IP instead of a Shasta LXC. capstone_provision.yml — Docker and cloudflared install — needed the three verify tasks added but nothing else changed. capstone_deploy.yml needed literally nothing; it clones the repo, writes the proxy's .env from Vault, and brings up the Compose stack regardless of which node capstone_host resolves to. That's the value of having built these as inventory-driven playbooks from the start rather than hardcoding a target — the actual placement decision turned out to be swappable without touching deployment logic at all.

VM over LXC, and why that decision held

The Docker workload itself isn't running yet, but the VM-vs-LXC question got settled before any of the above. Every existing Docker host in the lab uses a privileged LXC, which works fine when the host isn't exposed externally — but a privileged LXC shares the host kernel with Proxmox, and Dega's entire purpose is reducing blast radius for something that's reachable from the internet. Matching the existing pattern here would have undercut the reason the node exists in the first place. Going with a VM instead was the one place today where consistency with the rest of the fleet was the wrong instinct.

Where things stand

Dega is live on VLAN 20 at 10.10.20.54, in Ansible inventory as a normal proxmox_nodes member, reporting into Prometheus and Zabbix like the rest of the cluster. The three outbound firewall pinholes for the capstone's data sources are in place and will get verified automatically the moment the provisioning playbook runs against the VM. The provisioning and deploy playbooks are retargeted and waiting.

What's next

  • Create the Docker VM on Dega
  • Run capstone_provision.yml against it — Docker, cloudflared, and the three connectivity checks
  • Run capstone_deploy.yml — clone, write the proxy env from Vault, bring up the Compose stack
  • Configure the public hostname route in the Cloudflare Zero Trust dashboard, pointing at the proxy port
  • Confirm status.michaelrooney.dev resolves and all four data sources render through the new firewall rules

Most of today was rework rather than new ground — same playbooks, retargeted; same firewall rule pattern, applied with narrower scope. But getting the placement decision right before the app is actually running there is worth more than getting it running quickly somewhere that turns out to be wrong.
