The Difference Between Asking and Being Told

Added real-time-feeling updates to the status page this week, and the mechanism behind it — Server-Sent Events — turned out to be a genuinely simple idea wearing an intimidating name. Worth untangling, because the concept is small and the practical gotcha that showed up in testing was the kind no tutorial mentions.

Asking, versus being told

Ordinary HTTP is a conversation that ends every time: the browser asks a question, the server answers, and the connection closes. If the browser wants to know whether anything's changed, its only option is to ask again — which is exactly what polling is. Ask every 60 seconds, get an answer, hang up, wait, ask again. It works, but "up to 60 seconds behind" is baked into the design.

Server-Sent Events (SSE) flips that around. The browser opens one connection and just leaves it open. The server doesn't have to wait to be asked — it can write a message down that same connection the instant it actually has something worth saying. Same underlying HTTP, just used differently: instead of a question-and-answer that repeats forever, it's one open line the server can speak into whenever it wants.

A few things about SSE specifically, since they explain real decisions in how this got built:

  • One-directional. Server → browser only. If a browser needs to talk back over the same channel, that's a job for WebSockets instead — SSE is the simpler tool for the simpler job of "server occasionally says something."
  • Plain text over plain HTTP — not a special protocol. No new library needed on the server side; a normal HTTP response that just never closes and periodically writes a line of text.
  • Auto-reconnecting, built into the browser. The browser's own EventSource object notices a dropped connection and retries on its own. Writing that reconnect logic by hand is exactly the kind of thing a heavier real-time protocol would ask for and SSE doesn't.

The signal doesn't have to be the data

The tempting version of this feature pushes the actual updated status straight through the open connection — the server does all the work, the browser just displays whatever arrives. That's the "impressive" answer, and it's also a bigger architectural commitment than it looks: it means relocating whatever combines multiple data sources into one coherent picture from the browser to the server, a piece of logic that, in this project, lived entirely client-side.

The version actually built here is smaller on purpose. The open connection carries one bare signal — something changed, go check — and the browser still does the real fetch itself, the same way it always did. The existing once-a-minute polling doesn't go away; it stays exactly as a fallback. The nudge's only job is making the browser do that fetch sooner than it otherwise would have.

The bug that only production could show

First real test of this was almost embarrassingly simple — open a raw connection to the new endpoint and watch it. It connected fine, then sat silent, which is exactly correct behavior for a stream with nothing new to report. Left running a little longer, it died on its own with an obscure-looking HTTP/2 error, no code change, no request made — it just stopped.

The actual cause had nothing to do with the code: Cloudflare's own edge network — sitting in front of this site for unrelated reasons, mainly SSL and tunneling — kills a connection that's gone quiet for too long, on its own schedule, regardless of what the origin server intends. A connection meant to stay open indefinitely met infrastructure that has an opinion about "indefinitely." This is exactly the kind of thing that never shows up in local development, since local dev never goes anywhere near the production edge network at all — it only exists once real traffic is actually flowing through it.

The fix is almost anticlimactic once you know the cause: the server now writes a small, meaningless line of text down the connection every 15 seconds, just often enough to keep looking "active" to the infrastructure sitting between it and the browser. The browser's own SSE handling already knows to ignore lines like that by design — they're explicitly defined as comments in the SSE spec, not data — so nothing about the actual feature changes. It's pure plumbing, invisible to anything the user sees, and it's the difference between "works for a minute" and "works."

Where it landed

Confirmed in both directions against a real service, not just a screenshot: stopped, watched a genuine change get detected and broadcast, watched a browser tab update within seconds; restarted, watched the same thing happen in reverse. Full build notes — the architecture decisions behind the hybrid approach specifically, the reasoning for giving the change-detection loop its own interval rather than reusing an existing one — are in the capstone journal entry for this session.
