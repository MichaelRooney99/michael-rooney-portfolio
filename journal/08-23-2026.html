When vi.mock Isn't the Right Tool

A couple sessions back, the whole point of vi.mock was replacing an imported module's real functions with fake ones — point it at an import path, get controllable stand-ins back. That works perfectly when the function under test actually imports its dependencies from somewhere. It stops working entirely the moment that's not true.

The function that doesn't import anything to mock

A function fetching real 90-day history from Prometheus doesn't import a Prometheus adapter module the way the earlier example imported four separate service adapters — it just calls the browser's own fetch directly, inline, three or four different times, hitting three or four different real URLs. There's no module boundary to swap out. vi.mock('./prometheus', ...) has nothing to attach to here, because the function being tested doesn't get its network access from a file called prometheus.ts — it gets it straight from the global fetch the whole browser environment provides.

Mocking the global instead of a module

The fix is a step further up the chain: replace fetch itself, globally, for the duration of the test, using vi.stubGlobal('fetch', ...) instead of vi.mock. That solves the "how do I intercept this at all" problem — but creates a new one immediately. vi.mock naturally gives each mocked function its own separate identity, so fetchNodeStatus and fetchZabbixStatus can be told to behave completely differently from each other without any extra work. A single mocked fetch has no such luxury — every single call in the whole function, no matter which real URL it was headed to, funnels through the exact same one mock function. 

function mockFetchByUrl(handlers) {
  return vi.fn((url) => {
    if (url.includes('query_range') && url.includes('node_exporter')) {
      return handlers.nodeRange?.() ?? okJson(...)
    }
    if (url.includes('query_range') && url.includes('nut_ups_status')) {
      return handlers.upsRange?.() ?? okJson(...)
    }
    // ...
  })
}

The real fix is inspecting the URL each call actually receives and routing based on that — checking for query_range versus a plain instant query, and for which real metric name shows up in the query string, since that's the only information available at the point a mocked fetch gets called. It's a genuinely uglier pattern than vi.mock's clean per-function identity — real conditional logic sitting inside test setup code, string-matching against URLs by hand — but it's the correct shape for what's actually being tested. There's no cleaner version available here, because the thing under test genuinely doesn't offer a cleaner seam to hook into.

The actual lesson, not just the workaround

The interesting part isn't really the URL-routing trick itself — it's what decided which technique was even on the table in the first place. vi.mock works at the level of "this file imports that file." A function using fetch directly has no such import to intercept. The real question worth asking before reaching for either tool isn't "how do I mock this dependency" — it's "does this function even have an importable dependency to mock, or does it reach past that boundary entirely." The answer changes which tool is even a candidate before any actual mocking code gets written.
