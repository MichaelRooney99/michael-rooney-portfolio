A Promise You Can Check Automatically

Added real automated tests to the status page this week — the first in the whole project. Setting them up raised a handful of genuinely reasonable questions that don't have obvious answers if you've never worked with a test suite before: what is a .test.ts file actually doing, why does it sit right next to the code it tests, what happens when it passes or fails, and why did one function end up in a brand new folder nobody planned for. Worth untangling all four.

What "testing" a file actually means

No magic, no simulation — a test file imports the real function from the real file and calls it, the same way any other code would, with input you made up on purpose and an answer you already know is correct: 

import { buildUpsUptimeDays } from './history'

const result = buildUpsUptimeDays([
  { metric: { status: 'LB' }, values: [[timestamp, '1']] },
])

expect(result[89].status).toBe('outage')

That's the entire idea. Run the actual code with a known input, check the actual output against what it should be. The value isn't in running it once — it's that the exact same check runs again, automatically, every single time that file changes in the future. If someone accidentally flips a priority order or breaks a date calculation six months from now, this fails immediately instead of quietly shipping as a wrong status on a live page.

Why the name, and why right next to it

.test.ts is close to a universal convention — the test runner needs some pattern to know which files are tests and which are regular code, and using the near-standard suffix means anyone who's ever touched a JavaScript project already knows what they're looking at without reading any config. Putting history.test.ts in the same folder as history.ts, rather than a separate tests/ directory somewhere else, keeps the relationship obvious from the file tree alone — and makes it much harder to forget a test exists, since it's sitting right there every time the real file gets opened.

What actually happens on pass or fail

Less than you'd expect, honestly — and that's worth being upfront about. A test isn't a gate. Passing just prints a checkmark; nothing runs differently afterward. Failing prints a red line with exactly what was expected versus what actually came back — genuinely useful, since it tells you precisely which promise broke — but it doesn't block anything on its own. Nothing today stops a broken commit from still being deployed even with a failing test sitting right there, unless a person actually looks at the terminal output and decides to act on it. Wiring that enforcement in — a deploy that refuses to proceed if the test suite fails — is real, separate work, not something a test file grants for free just by existing.

Does everything deserve a test?

Not automatically, and the honest answer is about cost, not principle. The functions that got tested this round share one thing: they're pure — same input, same output, every time, nothing reaching out to a network or a database in between. Code that wraps an API call is real and testable too, but doing it meaningfully means faking the entire network layer, and what you end up confirming is "did I call the right URL," not "is the underlying logic correct." That's a valid thing to test eventually — it's just a worse hours-to-value trade than the pure functions, so it waited.

Why one function got its own new folder

A small uptime-percentage calculation lived inline for months, and the natural first move was just to export it for testing right where it already sat. A linter caught a real problem with that: a file mixing a plain function export alongside a UI component breaks a framework feature called Fast Refresh, which needs a file to export components and nothing else to safely hot-reload without a full page reload. Fixing the actual lint error meant moving the function out — and once it was out, the honest question became: out to where? It wasn't a service adapter (nothing about it talks to an API), and it wasn't a component (no UI at all, just math). A new folder — the conventional name for exactly this kind of thing is lib — turned out to be less a workaround for the lint error and more just where the function always actually belonged.
