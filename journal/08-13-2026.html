The Browser Asks Permission First

A browser has a rule baked into it that most people never notice until they hit it: a page loaded from one origin can't freely make requests to a server on a different origin, unless that server explicitly says it's allowed to. "Origin" here is specific — protocol, domain, and port all have to match. Same domain over a different port still counts as a different origin. This rule exists purely to protect the person using the browser, not the server — it stops some other website you have open from quietly making authenticated requests to your bank on your behalf, using cookies your browser already has. The server on the other end has to opt in, explicitly, to being talked to from somewhere else.

That opt-in is CORS — a small set of response headers a server sends back saying which origins it trusts, which HTTP methods it'll accept from them, and which custom headers it'll allow attached to those requests.

The request that never shows up in the actual conversation

The part that isn't obvious until you actually watch it happen: for anything beyond the simplest kind of request — a plain GET, no unusual headers — the browser doesn't just send the real request and see what comes back. It sends a separate one first, automatically, called a preflight, using the OPTIONS method. The question it's asking, before committing to anything, is essentially "if I actually send this, will you allow it?" Only once the server answers yes does the browser send the real request at all.

A server that isn't expecting this can end up genuinely confused — a route built to handle POST requests suddenly receiving OPTIONS requests it has no idea what to do with. The fix is a small, separate handler specifically for that case: recognize OPTIONS, respond with an empty 204 No Content, and stop right there — never let it fall through to whatever the real route logic would do, because there's no real request to handle yet, just a permission check. It's easy to miss this exists at all if everything you've tested so far only used plain GET requests, since those skip the preflight step entirely.

The same file, a different kind of permission question

Right next to this CORS handling sat something that turned out to be a related idea, even though it's not about networking at all — a pattern for handling failures inside an actual route, once a request is genuinely being processed. A database write fails, or something else unexpected breaks mid-request. The instinct might be to just hand the real error back to whoever made the request — it's honest, it's informative, it feels helpful. But the actual code deliberately splits this into two separate messages: a full, real error — stack trace and all — written only to the server's own logs, and a flat, generic message sent back to the outside caller instead.

The reasoning is a genuinely different kind of permission question than CORS asks, but it rhymes: not "can you talk to me," but "how much do you get to know about what just went wrong inside me." A raw error message can leak real internal detail — file paths, database structure, hints about how something's built — to literally anyone who happens to trigger a failure, intentionally or not. None of that detail helps a legitimate caller recover from the error. It's just free information handed to whoever's poking at the system, good intentions or bad. Logging the real thing where only the person running the server can see it, and giving the outside world nothing but "something went wrong," keeps the useful detail where it's actually useful and denies it to everyone else by default.

Two completely different mechanisms, sitting a few dozen lines apart in the same file — one about which origins get to talk to a server at all, one about how much a request that's already been allowed in gets to learn when something breaks. Different layers, same underlying instinct: default to withholding, and only grant exactly as much access or information as is actually needed.
