Duplication Isn't the Enemy — Silent Drift Is

One small function in the status page's proxy — read a Zabbix host's interface, decide if it's up or down — exists in three separate copies across the codebase. A second function, deciding "what's the overall status across everything," is about to become a fourth duplicate of a different kind. The instinctive reaction to hearing that is "just share the code" — and working through why that instinct is wrong here, specifically, turned into a more useful lesson than the actual feature that prompted it.

DRY is a slogan, not a rule

"Don't repeat yourself" is one of the first principles anyone learns writing code, usually before they've written enough code to know when it doesn't apply. It's good advice for the case it was written for — the same logic, copy-pasted within one codebase, drifting because nobody remembered to update both spots. It says nothing about the actual question that matters here: what does removing the duplication cost, and is that cost smaller than the problem duplication is causing?

The "obvious" fix wasn't actually cheap

A shared package sounds like the correct engineering answer — one function, one source of truth, no drift possible. Working through what it would actually require here changed the picture entirely: both halves of this project deploy as separate Docker containers, each building from its own subfolder as the build context. A shared package means code living outside both of those folders — which Docker can't reach into on its own. Making that work means restructuring both Dockerfiles, the compose file that wires them together, and probably the Ansible playbooks that deploy the whole thing. That's a real infrastructure project, not an import statement, and it was being considered to save maybe twenty lines of duplicated logic total. The math didn't remotely work.

The actual problem was never the duplication itself

The one real bug this exact situation ever caused wasn't "two copies exist." It was two copies existing with no way to notice when they stopped agreeing with each other — a mismatched value silently shipped to production and only got caught by someone eyeballing a dashboard that looked wrong. That reframing is the actual useful part: duplication is a manageable, even reasonable cost. Duplication nobody can detect drifting is the real liability, and those are two different problems with two different price tags to fix.

The fix that mattered wasn't eliminating the duplication — it was eliminating the silence around it. A small shared file of expected input/output pairs, checked independently by each copy's own test suite, costs almost nothing and turns "these two might have quietly drifted apart" into "a test would immediately go red if they had." No shared code, no build changes, no infrastructure — just an agreement, written down once, that both sides get held to automatically from then on.

A trigger beats a worry

The part of this that felt genuinely new wasn't the duplication decision itself — it was deciding, on purpose, what would actually change the decision later. The easy version is "we'll keep an eye on it as the project grows," which sounds responsible and means nothing concrete — there's no moment where "keeping an eye on it" resolves into an actual decision, just a vague, growing unease that eventually gets acted on reactively, usually in the middle of debugging something that's already broken.

The alternative: name two specific, checkable conditions ahead of time. A genuinely new kind of thing needing to be duplicated a third time — not another copy of what's already duplicated, an actual new concept joining the list. Or a real bug slipping through despite the cheap fix already being in place, proving the cheap fix wasn't sufficient. Either one is a plain yes-or-no question anyone can answer later without re-litigating the whole argument from scratch. The decision gets made once, calmly, ahead of time — not repeatedly, under pressure, after something's already gone wrong.

Why this is worth remembering past this one project

None of this is really about Zabbix status codes. It's a small, concrete example of a bigger and genuinely transferable habit: most architecture decisions aren't "right" or "wrong" in the abstract, they're trade-offs between two real costs, and the correct call depends on which cost is bigger right now, at this project's actual size — not which one sounds more disciplined in principle. Writing down the specific condition that would flip the trade-off is what turns a decision into something that can actually be revisited on purpose later, instead of something that just quietly rots until it becomes a problem.
