Let the Tests Tell You What the Code Promises

Every unfamiliar codebase has to be read somehow the first time, and the obvious instinct — open the entry point, read top to bottom — turns out to be one of the slower ways to actually get oriented. There's a real, well-established alternative worth knowing, and a real method for doing it properly, not just a vague "read the tests" suggestion.

Why tests are worth reading before the code they test

A test suite is a form of documentation that can't quietly go stale the way a comment or a README can. If a test claims something about the code's behavior and the code stops living up to that claim, the test fails — there's no silent drift possible the way there is with prose. That alone makes tests a more trustworthy starting point than almost anything else in a codebase.

Corey Cleary's write-up on this exact approach makes a related point worth sitting with: most of what someone actually needs when learning a codebase is a plain answer to "what does this function expect, and what does it return or do" — and that's precisely the question a test already answers, in a form meant to be read by a human, not reverse-engineered from implementation.

The actual method

Read every test name in a file first, start to finish, without opening a single assertion. Form a one-sentence guess about what the function under test actually does, based on names alone. Only then go back and read the real assertions — starting with whichever names didn't fully make sense, since that's exactly where the guess has a real gap. Pay attention to the setup and fixtures along the way, not just the expectations — that's usually the fastest way to learn the real shape of a system's data. Only after all of that is it worth reading the actual implementation — and reading it with a hypothesis already in hand turns out to be a genuinely faster experience than reading it cold.

A broader piece on reading unfamiliar codebases frames part of why this works: tests reveal which concepts the original developers thought were important enough to protect, and they surface the edge cases someone already anticipated, saving real time compared to discovering those same edge cases the hard way later.

A related technique, for code with no tests at all

Worth knowing the adjacent case too, even though it wasn't needed this time: what do you do when there's no test suite to read at all? There's a real, named answer to that as well — Michael Feathers, in Working Effectively with Legacy Code, calls it a characterization test: rather than writing a test that says what the code should do, you write one that simply records what it actually does right now, correct or not, and use that as a safety net going forward. A good, approachable recent interview with Feathers himself covers this idea directly, including how it holds up even with AI-assisted tooling now in the mix.

What actually caught the mistakes

The real value of the technique showed up twice, in almost identical fashion, in two completely different files. Both times, a first guess reached for a soft, plausible-sounding verb — "excludes," "averages" — to describe behavior that was actually something sharper and more specific underneath. Both times, one real number from an actual test or fixture disproved the guess cleanly and immediately. That's the part worth remembering past this one project: when an explanation of what code does reaches for a vague, generic verb, that's often exactly the moment worth stopping and checking one real value before trusting the explanation any further.

A different technique for a different problem

Worth being honest that this isn't the only real approach to getting oriented fast, and it isn't always the right one. Mitchell Hashimoto's own written process for approaching complex projects leans on something different first — becoming a real user of the system, then tracing one feature end to end before trying to understand anything broadly. His advice not to read the source until you've actually built and run the project is a genuinely different starting point than reading tests first, and a reasonable one for a codebase with no tests to read at all. Different tools for different situations — worth having more than one approach available rather than treating any single technique as the whole answer.
