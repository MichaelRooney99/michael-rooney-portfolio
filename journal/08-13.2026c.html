Reading a Codebase by Its Layers, Not Its Files

A frontend codebase organized into folders like services/, hooks/, and components/ can look, from the outside, like an arbitrary filing system — just different drawers for different kinds of files. It isn't. Each folder represents a genuinely different responsibility, and understanding what's allowed to call what turns out to explain most of how the application actually behaves.

Services: no React, no opinions about display

The services layer's entire job is fetching real data and reshaping it into a consistent, predictable shape — nothing about how or where that data eventually gets shown. These files don't know a single thing about React. They're plain functions: given a real API call, return normalized data. That narrowness is deliberate — it means the exact same fetching-and-shaping logic could be reused in a completely different UI framework without changing a line, because nothing here assumes anything about rendering at all.

Hooks: the bridge between plain data and a living React tree

Hooks are where services actually meet React. A hook calls into the services layer, but wraps that call in real React state — is this loading, did it error, has new data arrived — and exposes all of that back out in a form components can actually consume. This is also where library-level behavior gets configured — how often to refetch, how long data stays considered fresh, how many times to retry a failure — real decisions, not defaults left untouched.

Components: rendering, and — sometimes — their own direct line to a hook

Components take data and turn it into what actually appears on screen. The instinct is to assume all data flows one way — a top-level component fetches everything and hands it down as props to everyone underneath it. That's often true, but not a hard rule here: some components reach directly into their own hook, fetching their own data independently, rather than waiting on something above them to hand it down. A modal that only needs its own data the moment it opens is a natural fit for that — no reason to make an unrelated parent component responsible for data only one specific child actually needs.

The file that makes almost all of it possible, and easy to skip past

It's tempting to assume the plain HTML page just loads the main application component directly. It doesn't — there's a real, separate file sitting between them, and it's doing more than just bootstrapping. That file is where a shared data-fetching client actually gets created and wrapped around the entire application, once. Every single hook anywhere in the app that relies on that shared client — and most of the interesting ones do — is silently depending on this one small file having wrapped things correctly. Overlooking that link doesn't just mean missing a small technical detail — it means missing the one piece that explains why data-fetching hooks scattered across a dozen different components all get to share caching and deduplication behavior without ever having to coordinate with each other directly. None of them know about each other. They're all just quietly plugged into the same thing, set up once, in a file easy to skip right past.

Why the layering matters more than it looks like it should

None of this is really about folder names. It's about being able to answer a real question quickly: if something's broken, which layer does the actual problem live in? Wrong data on screen — check the service doing the fetching first, before assuming the component rendering it is at fault. A component behaving strangely when it should be caching data — check whether it's actually inside the shared provider everything else depends on. The folder structure isn't decoration. It's a map for exactly this kind of question, and it only works if you actually know which layer is responsible for what before you start looking.
