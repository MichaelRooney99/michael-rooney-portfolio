The Build That Succeeded for the Wrong Reason

A clean compile isn't the same claim as a correct one. TypeScript checks a workspace package against whatever's actually sitting on disk, not against the intent behind a change — and the shared package from the first half of this session made that gap concrete the moment I wired it to a real Express API.

Wiring a real dependency between two packages

Adding the actual link — npm install @filament-calc/shared -w @filament-calc/api — writes something that looks completely ordinary into api's package.json: a plain semver range, "@filament-calc/shared": "^1.0.0", no different in shape from express's own entry. Nothing in that field says "this one's local." npm workspaces resolves it at install time — it scans packages/*, finds a package by that name satisfying that range, and symlinks instead of hitting the registry. Bump shared to 2.0.0 without updating this range, and the next clean install would genuinely try the registry instead. pnpm and Yarn sidestep this with an explicit workspace:* protocol; npm just doesn't have that syntax. Not a real risk on a two-person project, but a documented, real footgun on larger teams.

The bug that should have happened, and didn't

To actually see the build-order dependency, I renamed calculateCost to computeCost in the shared package's source — without rebuilding it — then checked whether the API package's build noticed. VS Code flagged it instantly, offering to auto-update the import. tsc did not. Ran clean, no error, import untouched.

Both outcomes are correct, for different reasons. The editor's language service watches a workspace package's live source for open projects — genuinely useful, but an editor convenience, not what happens at build or runtime. The actual compiler resolves imports against whatever shared's own package.json points types at — dist/index.d.ts — and that file still said calculateCost, frozen at the last time anyone ran tsc inside shared. The real lesson: a workspace package's actual interface to the rest of the repo is whatever's compiled into dist/, not whatever the current source file says. This exact gap — forgetting to rebuild a dependency before rebuilding what depends on it — is the specific problem real monorepo tooling like Turborepo or Nx solves, by building a dependency graph and forcing rebuild order automatically instead of leaving it to memory.

Encoding the fix by hand

Two packages doesn't justify pulling in a build orchestrator yet, so the fix here is a root-level script that hardcodes the correct order: "build": "npm run build:shared && npm run build:api". The && chain is the whole mechanism — shared always rebuilds before api does, so api can never compile against a stale dist/ again. It's the manual version of exactly what a real dependency-graph tool automates, which made it worth building by hand once before reaching for a tool that hides the mechanism.

Two things that only look like Express problems

The actual route handler uses zod's safeParse rather than parse — returning a {'{ success, data | error }'} object instead of throwing, which reads naturally when branching on routine "the client sent bad data" cases inside an Express handler, rather than wrapping every request in try/catch. The bigger point is where that schema lives: because CalculationInputSchema was defined once in shared rather than duplicated per-package, the exact same validation rules that reject a malformed request here will later live-validate a form in the React client — while the server-side check stays the actual security boundary regardless, since anyone can hit this endpoint directly and skip the form entirely.

Windows PowerShell isn't curl

Pasting a real curl command with -X POST and -H flags into PowerShell fails outright — PowerShell aliases curl to Invoke-WebRequest, which parses flags completely differently and throws a parameter-binding error on sight. The PowerShell-native equivalent for hitting a JSON API is Invoke-RestMethod, built from a hashtable piped through ConvertTo-Json — and it's the better default going forward for API testing on Windows regardless, since it auto-parses a JSON response straight into a usable PowerShell object instead of handing back a raw response blob.

Money math and floating point

The very first successful response came back as 2.4320000000000004 instead of 2.43 — not a bug in the arithmetic, but ordinary IEEE 754 double-precision float behavior: decimal fractions like 0.14 frequently have no exact binary representation, the same category of problem as 1/3 having no exact decimal one. For a learning project the fix is a one-line rounding pass at the return boundary rather than a bigger refactor into integer-cent arithmetic — the point here was monorepo mechanics, not financial precision engineering, and it's worth knowing which problem is actually in scope before reaching for the heavier fix.

Where this leaves it

The backend loop is fully proven end to end now: a request hits Express, validates through shared's zod schema, computes through shared's calculateCost, and comes back as clean two-decimal JSON — all three packages genuinely depending on each other rather than just sitting in adjacent folders. The React client side of the monorepo, and whatever surprises workspace-linking a Vite frontend turns up, is next.
