May 7, 2026 Homelab Projects Learning

Automation Infrastructure

Ansible is now a permanent part of the homelab rather than an item on a roadmap. A dedicated LXC on Shasta at 10.10.10.106 acts as the control node — 2 cores, 2GB of RAM, 16GB of disk. Its only job is to hold the playbooks and SSH out to the other five nodes. This entry is less a single session writeup and more a record of where the project stands: what's built, what was harder than expected, and what comes next.

Why this exists

The honest reason is that the lab had accumulated drift. Not dramatic drift — nobody was running a wildly different software version or missing a critical package entirely. It was the quieter kind: POLLFREQ values in NUT configs that didn't match between nodes, notification flags present on some hosts and missing on others, a FINALDELAY on PBS that differed from everything else. The kind of thing that happens when you configure five machines by hand over the course of several weeks, copying and editing config snippets each time, under varying amounts of deadline pressure.

The solution to drift isn't being more careful. It's removing the conditions that allow drift to accumulate — which means encoding the desired state somewhere that can be checked and enforced automatically.

Getting started was the hard part

The Ansible concepts — inventory, playbooks, idempotency, handlers — are not complicated. The friction was environmental. Getting ansible.cfg to load correctly, getting the vault password file in the right place, understanding why the inventory parser was silently rejecting a syntactically valid YAML file because the file didn't actually exist yet. None of these are deep problems. All of them cost time before the cause was clear.

The gap between "I understand how Ansible works" and "Ansible is actually working" is entirely environmental. The tool itself is straightforward. Getting the control node, SSH keys, sudoers entries, config file, vault password, and inventory all correct simultaneously takes longer than reading about any of them.

The thing that broke the most invisibly was the inventory file not existing at the path ansible.cfg expected. Ansible's error message — "unable to parse as an inventory source" — is the same whether the file is malformed or simply absent. Running cat inventory/hosts.yml before assuming the YAML was the problem would have saved twenty minutes.

The playbooks

Six playbooks are active. An audit playbook that collects the current state of every service across all five nodes and prints a structured report — read-only, safe to run at any time, the first thing to run after any change. A baseline playbook that ensures the same set of packages is installed on every node and that lm-sensors has been configured. A node_exporter playbook that checks the installed version against a pinned target and only downloads and reinstalls if they differ. A rolling update playbook that runs apt upgrade one node at a time with serial: 1 so the cluster is never being patched simultaneously.

The two NUT playbooks are the most consequential. One manages the full server configuration on Ankhh — all four config files, both services, and a live verification at the end that upsc returns real data before the play finishes. The other manages the secondary configuration on the four slave nodes: Node 0, Shasta, Murloc, and PBS. Each slave's play ends by querying the UPS through Ankhh and confirming it returns OL. If it doesn't, the play fails rather than silently leaving a node in an unmonitored state.

What Ansible revealed

Writing a playbook for an existing configuration forces you to understand it at a level that configuring it by hand doesn't require. When you write the task that deploys upsmon.conf, you have to know what every field on the MONITOR line means. The power value. The credential names. The primary versus secondary distinction that NUT renamed in version 2.8 — which Debian 12 ships — but which still appears as master and slave in most of the documentation online.

Running the audit playbook against the existing nodes before touching anything is what surfaced the inconsistencies. That's the point of the audit — not to find catastrophes, but to find the quiet differences that only matter when something goes wrong and you're trying to reason about what the system should look like.

Vault

The NUT playbooks need the upsmon passwords. Those can't live in plaintext in a file that gets committed to a repository. Ansible Vault handles this — AES-256 encryption, decrypted transparently at playbook runtime using a password stored in ~/.vault_pass on the control node. The encrypted file is safe to commit. The password file is in .gitignore and lives only on the control node and in a password manager.

The first time you forget to create the vault password file before running a playbook, Ansible errors with a message about the vault password file not being found. The second time it happens you check for the file first. That's roughly how all of this goes.

What's still in progress

The standardization playbook — a single play that runs baseline packages and NUT config together across the whole fleet — is partially written but paused. Writing it exposed a decision that needs to be made first: whether node_exporter comes from apt or from a pinned binary downloaded directly from GitHub. The apt package on Debian 12 is version 1.5.x. The pinned version in the node_exporter playbook is 1.8.1. Running both approaches on different nodes is exactly the kind of drift Ansible is supposed to prevent. That decision gets made before the combined playbook gets finished.

After that: a Glances standardization playbook, refactoring the longer playbooks into proper roles once the structure is stable enough to warrant it, and a nightly cron on the control node that runs the audit automatically and logs the output. The audit-on-a-schedule idea is particularly useful — it means drift gets caught without anyone having to remember to look.

The larger point

The conversation with the network engineering manager back in April was direct about automation being a team priority — moving from reactive firefighting to proactive response to network events. Ansible is the tool that lives in that space. Building playbooks in a homelab environment to manage configuration across five nodes is smaller in scale than managing hundreds of store locations, but the thinking is identical. Desired state. Idempotent operations. Version-controlled configuration. Changes that are testable before they're applied.

This is the part of the homelab that's most directly connected to where I'm trying to go professionally. It's also the part that's most obviously unfinished — which means there's more to write about here.
