Upgrading a Node the Right Way

One of my cluster nodes had been causing intermittent monitoring alerts for a while — services on it would go briefly unreachable, a reboot would clear it, and it would be fine for a few days before repeating. The root cause was never definitively confirmed but the slow NVMe drive was the leading suspect. Write latency under load can cause VM stability issues that look like network or application problems on the surface.

I had a replacement unit available — same form factor, faster storage, doubled RAM. The question was how to swap the hardware without losing the services running on that node.

The migration approach

The node in question runs the backup server for the entire cluster — the worst possible service to have go down during a hardware swap. The right move was to migrate that VM to another node first, perform the hardware replacement, then migrate it back.

Proxmox makes live VM migration straightforward through the web interface. Select the VM, choose a target node, confirm. The VM moves while running with only a brief network interruption. The backup server came up cleanly on the temporary host and I ran a manual backup job to confirm everything was working before touching any hardware.

Never do maintenance on the node that hosts your backups without first confirming your backups are current and accessible from somewhere else.

The hardware swap

Removing the old node from the cluster, installing Proxmox on the new hardware, and rejoining it to the cluster is a clean process when done in the right order. The key detail is that the new machine needs to be configured with the same hostname and IP before joining — the cluster recognizes nodes by identity, not just by address.

One gotcha: the new hardware has a different network adapter MAC address. My router assigns static IPs by MAC, so the new machine came up on a DHCP address rather than its expected static IP. DNS resolution failed, package updates failed, everything looked broken until the MAC was registered with the correct static assignment. Five minute fix once identified, confusing until it was.

What changed

The replacement unit has a significantly faster NVMe — the difference in sequential write speed is substantial. RAM doubled from 16GB to 32GB, bringing it in line with the primary cluster node. The old SATA drive carried over since it was fine and had no performance complaints.

The old NVMe went into a USB enclosure as a cold spare. I briefly considered adding it as a second backup datastore but the performance over USB made that impractical for nightly automated jobs. It's shelved and available if something catastrophic happens to the current storage.

The outcome

The monitoring alerts stopped immediately after the swap. All four cluster nodes are green. The backup server ran its first nightly job on the new hardware without issues. Current datastore usage sits well under one percent of available capacity — the upgrade added headroom alongside the stability fix.

The process itself was a useful exercise in infrastructure thinking. Having a three node cluster meant there was always somewhere to migrate a VM during maintenance. Having current backups meant there was a fallback if migration failed. Having a documented IP scheme meant the new node's network issue was diagnosable in minutes rather than hours. The infrastructure investments compound.
