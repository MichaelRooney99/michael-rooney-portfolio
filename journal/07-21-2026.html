July 21, 2026 Projects Learning

Chasing a Blue Line That Wasn't There

Today's session started small — a contrast fix on the capstone hours-log links — and kept surfacing one more real problem each time I went looking for the next one. By the end it touched nearly every page on the site, and the last hour was spent debugging something that turned out not to be a bug at all.

Small fix first

The capstone hours-log table's session links were unstyled <a> tags, falling back to browser-default blue on a dark background. Gave them var(--text) by default with a border-bottom, shifting to var(--accent) on hover — matching the treatment .back-link and .contact-links a already use elsewhere on the site.

While there, added a banner below the capstone hero linking out to status.michaelrooney.dev now that it's actually live. First pass was a full .journal-banner block; second pass folded it into the hero itself as a .project-link pill next to the existing copy, since a whole separate bordered section was pushing everything below the fold for no real gain over one inline button.

Cards that only looked clickable

The actual work started with a simple ask: make each project cell the click target instead of a separate "View Project" link. Converting <article class="project"> plus a sibling <a class="project-link"> into a single wrapping <a class="project"> — same pattern .entry-list a.entry already uses — turned up something worse than a styling gap.

.project-link { display: none; } at the 768px breakpoint had been hiding the only link on the whole card on mobile. Project cards weren't just under-styled on phones — they were completely untappable, silently, with nothing in the layout suggesting anything was missing.

Making the whole card the link fixed that as a side effect. Rewrote the mobile rule to keep the pill visible and stack it full-width below the content instead of hiding it, added aria-labels per card since the visible text is now split across a title, meta line, and pill rather than one link's contents, and deliberately left the .magnetic hover effect off the new card-sized links — it's tuned for small buttons, and stretching it over a whole card would read as jittery rather than subtle.

A second bug, found by accident

Scanning for other mobile gaps while in the CSS turned up .skills-table's mobile view — headers hide below 768px and category labels are meant to render via content: attr(data-label) next to each value. Not one <td> anywhere in the About section, or the capstone hours table sharing the same class, actually had a data-label attribute set. On mobile both tables were rendering as unlabeled rows with dead space where the category name should be.

Added the labels to the About section table directly; flagged the same fix for the capstone hours table since that file lives outside this project's local copy.

One collapse, thirty-three files

Nav mobile collapse was next — a hamburger toggle with three bars that morph into an ✕, a slide-in panel from the right using the existing --bg-raised and --border tokens, closes on link click or Escape. Built and verified on index.html and portfolio-showcase.html first, then the actual ask arrived: do the whole site.

Thirty-one more pages share the same nav markup — the logo link, then straight into <ul>. A short Python script matched that pattern and inserted the toggle button plus an id="primary-nav" on the list across every file in one pass. Thirty of thirty-one matched cleanly. The one holdout, 07-09-2026.html, used single-quoted HTML attributes instead of double — class='nav' instead of class="nav" — so the regex silently skipped it rather than failing loudly. Caught it by diffing the file count against the toggle count instead of assuming the batch run was complete, and patched it by hand.

Diffed a sample of the batch output against the originals afterward to confirm the change set was exactly what it should be — the <nav> block, nothing else, no incidental reformatting bleeding into entry prose or metadata.

The blue line that wasn't

The last stretch of the session was a debugging story rather than a build. A screenshot showed random phrases — the tail end of a paragraph, a project number, a card title — underlined in blue with no shared element or class between them. Every theory that would explain a real CSS bug (a missing text-decoration: none, a malformed nested <a>) predicts the entire linked region rendering the same way, not scattered fragments. That pointed at something injecting styling outside the page's own CSS — a browser extension doing grammar or style checking.

A follow-up screenshot from a private browsing window ruled that out — the underlines were still there, extensions disabled. Real bug, confirmed. Except the generated markup for the affected card, checked directly, was structurally identical to the card rendering cleanly right next to it. Nothing in the code explained the difference.

Turned out to be neither theory: the phone was still serving a cached copy of the site from before the deploy finished propagating. Confirmed once the cache cleared and the page reloaded clean. A frustrating one to chase, but a useful reminder that "confirmed in a private window" rules out extensions specifically — it doesn't rule out caching, which behaves the same way whether or not the tab has your saved logins in it.

Where things stand

Every project card on the site is now a full click target with the mobile tap-target bug fixed as a byproduct, the About section's skills table has correct mobile labels, and all 33 pages share one working hamburger nav. The capstone hours table still needs the same data-label treatment applied by hand, since it isn't part of this project's local files.
