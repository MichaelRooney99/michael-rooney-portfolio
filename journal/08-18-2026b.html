Fourteen Tests I Didn't Write, and Why That's the Point

Doing a test-files-first code review means reading a test's name, guessing what it checks, then confirming against the real code — the same technique from the previous entry on this method. That technique quietly assumes every test has a name to read in the first place. Most of nudge.test.ts — 14 of its 17 tests — don't. They're generated, one per entry, by looping over a shared JSON file. No hand-written it(...) block to hypothesize about at all. Working out why that's true turned into a better lesson than any individual test in the file.

The thing being tested twice, on purpose

The proxy and the browser client both need to answer the same small question — given a handful of service statuses, what's the single overall status to show — and they can't share code to do it. The browser can't import from an Express server's bundle. So the same tiny piece of logic exists twice, by necessity, in two different files, in two different packages that never talk to each other at build time.

Two copies of the same idea, with no mechanism to notice if they ever stop agreeing, is exactly the situation that already caused a real bug in this project — documented back in early August, where one copy checked for a Prometheus metric labeled nut_exporter and the other checked for nut. Both looked correct in isolation. Neither test suite caught it, because neither suite knew the other copy existed.

What actually closes that gap

Not more hand-written tests — more hand-written tests would just be two more places for someone to update one copy and forget the other, the exact failure mode that caused the bug in the first place. The real fix is a single JSON file of input/output pairs, sitting outside both packages so neither one owns it, that both test suites read independently and check their own local logic against. One definition of "the correct answer" for a given input, referenced by two completely separate copies of the code that's supposed to produce it. If either copy ever drifts, its own suite fails immediately — not eventually, not "whenever someone happens to compare the two by hand."

Revisiting it months after building it

The genuinely interesting part of coming back to this during a review, rather than while building it, was realizing how little the individual generated test cases matter compared to the reason the whole structure exists. Reading through fourteen auto-generated test names one at a time would have been a strange use of time — the value isn't in any single case, it's in the fact that the same fixture file backs both copies at once. That's a different kind of thing to understand than "here's what this specific test checks," and it took actually sitting with the "why fixtures, why not just write more tests by hand" question directly to see it clearly.
