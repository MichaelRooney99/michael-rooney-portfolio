The Playbook That Passed by Failing First

An accidental UPS forced-shutdown a day earlier left a real question sitting open: the documented shutdown threshold and the one actually configured on the UPS didn't match. Chasing that down properly meant checking three separate docs against each other and against reality — and it turned into a much better lesson about documentation drift than the mismatch itself.

A file that disagreed with itself

The first doc checked cleanly resolved the headline question: the real firmware threshold is 10% battery, not the 20% every runbook described. Easy fix — correct the docs, leave the UPS alone. What wasn't expected was finding the exact same five-node slave list stated as four nodes in one section of a file, and correctly as five in a completely different section of that same file. Nobody had edited the second section when a sixth node was added to the monitoring fleet months earlier. The file didn't just disagree with reality — it disagreed with itself.

Two copies, quietly diverging

A separate reference doc had something stranger: two full copies of the same slave config, embedded side by side under two different headings, each claiming to be the current version. One had a setting that would crash the monitoring service if actually deployed; the other didn't. Neither copy matched what was really running on the fleet, either — the live config on a real node was missing several lines both documented copies agreed on. Three different versions of one config, and not one of them was the ground truth.

Reconciling three disagreeing copies of a config by carefully reading each one is exactly the wrong instinct. The actual fix was ignoring all three and going straight to the thing that's supposed to be authoritative in the first place: the real Ansible playbook already sitting in the repo, and a live check of what a real node was actually running.

The playbook that failed on the first real run

Pulling the real nut_master.yml and nut_slaves.yml files and running them fresh against the whole fleet was meant to be the boring, correct fix — bring every node's live config back in line with the one file that should define it, no more hand-reconciling markdown. The first run against the master node failed instead, with Error: Driver not connected, immediately after a real config change had just been applied.

That's a genuinely alarming message on a project built around verifying a UPS shutdown chain — worth treating carefully, not waving off as a fluke. Checking the actual driver process directly (systemctl status on the real service, not trusting the failure message alone) told a much less scary story: the driver had, in fact, started successfully — four seconds after the playbook's own check had already given up and failed. The port the check was waiting on opened before the USB driver behind it had actually finished attaching to the physical UPS. The playbook was watching the wrong signal.

Confirming it, then fixing it properly

Re-running the exact same playbook a few seconds later, with nothing else touched, passed clean — zero config changes, verification check green on the first try. That's the confirmation that mattered: not "it works now," but "the failure was real, transient, and specifically the four-second gap, not a fluke that happened to go away." The actual fix was small — a retry loop on the verification task instead of a single immediate check — so a normal startup delay stops producing a false alarm on every future run, for whoever touches this playbook next.

Confirming the fleet, not just the fix

Re-running nut_slaves.yml against all five slave nodes afterward closed out the original question properly: a node on its own isolated VLAN, which had only ever appeared in one of the three disagreeing docs, connected across that VLAN boundary and confirmed the UPS status cleanly. Real confirmation, not an assumption carried forward from whichever doc happened to be right by accident.

The actual lesson isn't about NUT specifically. Three documents drifting out of sync with reality, and with each other, is what happens by default to hand-maintained config documentation over enough months — not a mistake anyone made on purpose, just the ordinary cost of a doc and a live system existing separately. The real fix was never going to be reading the docs more carefully. It was treating the actual playbook and the actual running config as the only two things worth trusting, and letting everything else get corrected to match them.
