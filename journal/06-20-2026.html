Connection Reset by Peer

The managed switch doesn't arrive until Wednesday, so today's Zabbix work was scoped deliberately narrow: get Zabbix Agent 2 installed and talking to the server on all five Proxmox nodes, and leave the SNMP/switch side for Thursday once the hardware is actually in hand. That part of the plan held. What didn't go as quickly as expected was getting from "agent installed" to "agent actually responding" — three separate problems stacked on top of each other, each one only visible once the previous one was cleared.

Starting from zero

First step was confirming there was actually nothing to build on. The Zabbix runbook notes said Agent 2 was part of initial setup, but a quick check across all five nodes — ansible all -m shell -a "systemctl status zabbix-agent2" — came back with Unit zabbix-agent2.service could not be found on every single one. Good to know before assuming otherwise. Clean slate, fresh install, and a clear case for doing it through Ansible rather than by hand five times.

The playbook itself came together quickly, following the same shape as the existing node_exporter.yml and nut_master.yml — add the repo, install the package, deploy a config, confirm the port is listening. Passive checks only, since everything's on one flat subnet with no firewall between the nodes and the Zabbix LXC — no reason to add the complexity of active checks pushing through NAT or firewalls that don't exist here.

A variable that wasn't where I thought

First real snag had nothing to do with Zabbix. The playbook referenced a new zabbix_host variable that needed to live in group_vars/all/common.yml alongside the existing NUT and node_exporter variables. Added it, ran the playbook, got 'zabbix_host' is undefined — even though the variable was sitting right there in the file.

The diagnostic path here is worth writing down because it's reusable: ansible -m debug -a "var=zabbix_host" -e @group_vars/all/common.yml resolved the variable just fine, which made the problem look like it was somewhere in the playbook itself. But that command force-loads the file directly via -e — it doesn't test whether normal auto-discovery would find it. ansible-inventory --list -y is the more honest test, because it resolves variables exactly the way ansible-playbook would, with no shortcuts.

A variable resolving under -e @file proves the file is valid YAML. It proves nothing about whether auto-discovery would have found it on its own.

The actual cause: group_vars/ has to live adjacent to wherever ansible.cfg points the inventory setting — in this case, inventory/hosts.yml — not at the repo root. A top-level group_vars/ next to playbooks/ looks like the right place by every convention I'd seen, but Ansible doesn't auto-discover it there. Moving it to inventory/group_vars/all/ fixed it. Documented in the Ansible runbook now so this doesn't cost twenty minutes again on the next variable I add.

Connection reset by peer

With the variable problem solved, the playbook ran clean across all five nodes — repo added, package installed, config deployed, service started, port 10050 confirmed listening. Felt done. Then I checked the Zabbix frontend after adding the five host entries, and every single one showed: 

Not available
Get value from agent failed: cannot read response: cannot read from
socket: [104] Connection reset by peer.

A reset is a more specific signal than it might look like at first. It's not a timeout — the connection isn't going nowhere. It's not a refused connection — nothing's actively blocking the port. The TCP handshake completes, the agent accepts the connection, and then something in the protocol exchange itself causes the agent to actively tear it down. That pattern points at a server-and-agent-don't-speak-the-same- protocol-version problem, not a network problem — which matters, because it meant the firewall and connectivity checks I'd already run were a dead end, not a place to keep digging.

zabbix_server -V on the Zabbix LXC: 7.4.10. dpkg -l | grep zabbix-agent2 on Ankhh: 7.0.27. There it was. I'd pinned the agent install to the 7.0 repo without ever checking what the server itself was actually running — the Zabbix.md runbook just said "7.x," and I filled in the rest with an assumption instead of a command.

A repo path that moved

Fixing the version should have been a one-line change — swap 7.0 for 7.4 in the repo URL. It wasn't, because Zabbix restructured the repo layout somewhere between those two versions. The 7.0 URL pattern is repo.zabbix.com/zabbix/7.0/debian/pool/... — no extra path segment. Swapping in 7.4 and keeping that same shape returns a clean 404. The actual 7.4 path adds a /release/ segment: repo.zabbix.com/zabbix/7.4/release/debian/pool/....

Worth saying plainly: that's not a guessable typo-fix. It's a real structural change in how Zabbix organizes their repo between major versions, and the only way to know it changed is to actually check rather than pattern-match from the last version that worked. A quick search against Zabbix's own repo directory listing confirmed the correct path before touching the playbook again — better to verify once than fail across five nodes a second time on a guess.

One more wrinkle on the version swap: the playbook's repo-already-configured check only tested whether /etc/apt/sources.list.d/zabbix.list existed, not what version it pointed at. Since the 7.0 repo file was already sitting there from the first run, that check silently skipped re-adding the repo entirely — the 7.4 URL never even got attempted until I added a step to forcibly remove the old repo file first. Fixed for today, flagged as a known idempotency gap for later — every future run of this playbook now re-downloads and reinstalls the repo package even when nothing's changed, which is wasteful but not wrong. A problem for a day when I actually run this playbook routinely instead of just today.

The upgrade that broke the thing it fixed

With the correct repo and state: latest forcing an actual upgrade rather than a no-op, the playbook reported everything changed as expected. Then the port 10050 check timed out on all five nodes — a regression from the run that had worked cleanly before the version fix.

systemctl status on Ankhh showed the service crash-looping — activating (auto-restart), restart counter climbing, exit code 1 on every attempt. The journal had the real story: 

Validating configuration file "/etc/zabbix/zabbix_agent2.conf"
Validation successful
Cannot open log file /var/log/zabbix-agent2/zabbix_agent2.log

Config was fine. Binary was fine. It just couldn't open its own log file — because the directory didn't exist. ls -la /var/log/zabbix-agent2/ confirmed it outright: no such file or directory. The zabbix system user and group were present and normal, so this wasn't a permissions problem on something that existed. The 7.0 package must have created that directory at initial install, and the 7.4 upgrade path simply never recreated it.

A task reporting ok on "enable and start the service" only confirms systemd accepted the request — not that the process stayed running. Check the journal, not just the task result, when something feels too clean.

The fix is one task: create the directory with the right ownership before the config gets deployed, every run, every time. Small addition, but it makes the playbook resilient to this specific packaging gap on any future reinstall — not just a patch for today.

What actually got verified, and what didn't

Once the directory existed, the service started clean and port 10050 came back green across all five nodes on the next run. I'd also added a step to the playbook that automatically ran zabbix_get against each node, delegated to the Zabbix LXC, so the whole chain — agent install through confirmed working response — could verify itself without manual steps. That step failed too, but for a boring reason: the Zabbix LXC isn't in Ansible's inventory and has no SSH access for the ansible user, so delegate_to couldn't reach it at all.

Rather than provision SSH access to a host that has no other reason to need it, I pulled the step out entirely. Manual verification — running zabbix_get directly on the Zabbix LXC — is the reliable path here, and it's what actually confirmed the fix. Not every check needs to be automated inside the playbook just because it can be. The port-listening check inside Ansible is good enough as an automated signal; the protocol-level confirmation can stay manual.

Where things stand

All five Proxmox nodes are running Zabbix Agent 2 7.4.x, version-matched to the server, passive-check-only, listening and confirmed responding. The Ansible playbook handles the whole install end to end and is resilient now to both problems hit today — the version pin and the missing log directory — for any future rebuild. What's left is entirely manual and entirely in the Zabbix frontend: creating the five host objects with the right hostnames, host group, and the standard Linux template, then watching the availability column actually turn green.

The switch lands Wednesday. SNMP configuration and the corresponding Zabbix template work for it is Thursday's problem, on purpose — today's scope was the part that didn't need to wait on hardware, and it's done.
