Six Tasks That Reported Changed When Nothing Had

Idempotent doesn't mean a task does nothing the second time. It means running it once, or running it a hundred times, leaves the system in the same end state either way. That distinction sounds pedantic until a real playbook proves it — which is exactly what happened while bootstrapping a fresh LXC for an Omada SDN controller today. Six tasks kept reporting changed on every single rerun, even though nothing about the container actually needed to change after the first pass.

What was actually happening

The bootstrap step creates an ansible user inside a brand-new container, drops in an SSH key, and grants passwordless sudo — all through pct exec, since the container has no SSH access yet on a fresh template. The first version of that bootstrap looked reasonable: 

- name: Create .ssh directory for ansible user
  ansible.builtin.command:
    cmd: "pct exec {{ vmid }} -- mkdir -p /home/ansible/.ssh"
  changed_when: true

Run it once, the directory gets created — correct. Run the exact same playbook again an hour later, after nothing on the container has changed, and it still reports changed. Not because mkdir -p did anything destructive — it's a genuinely harmless command to re-run — but because the task itself never checked whether the directory already existed before deciding to report a change. It just ran, every time, and said "changed" every time, regardless of whether anything was actually different afterward.

Why command and shell default to lying about this

Ansible's declarative modules — apt, systemd, file — check real state before acting. Ask apt to ensure a package is present, and it looks first: already installed, report ok; missing, install it and report changed. That's the whole idempotency guarantee built into the module.

command and shell don't get that for free. They have no concept of "already true" — they just run whatever string you hand them and report success or failure. Ansible's own default, absent any other guidance, is to assume any successful command/ shell execution counts as a change. That default exists because there's no general way to know whether an arbitrary shell command changed anything — so it's a reasonable default, but it's still a default that's wrong unless the task tells Ansible otherwise.

The fix is always the same shape: check, then gate

The pattern that actually works is checking real state first in its own task, then gating the mutating task behind that check: 

- name: Check if .ssh directory already exists
  ansible.builtin.command:
    cmd: "pct exec {{ vmid }} -- test -d /home/ansible/.ssh"
  register: ssh_dir_check
  changed_when: false
  failed_when: false

- name: Create .ssh directory for ansible user
  ansible.builtin.command:
    cmd: "pct exec {{ vmid }} -- mkdir -p /home/ansible/.ssh"
  when: ssh_dir_check.rc != 0

Now the create task only runs — and only reports changed — when the directory is actually missing. Second run, the check finds it already exists, the create task is skipped entirely, and the recap says exactly what's true: nothing changed. Same shape applies to comparing file content, not just existence — catching the SSH key and sudoers file needed the check task to cat the existing content and compare it against what should be there, not just confirm the file was present.

This wasn't the first time this exact bug shape turned up in this project. A real idempotency-verification pass in August found a Prometheus ACL task with the identical problem — a bare command with no when guard, reporting changed: true unconditionally on every run. Same root cause, different playbook. Once you've seen the shape once, it's worth checking for everywhere a raw command or shell task shows up without a guard.

Why a clean rerun is the actual point

The payoff isn't cosmetic. A genuinely idempotent playbook can be re-run any time without thinking about current state first — no mental tracking of "did I already run this on Shasta." The playbook becomes a statement of what the system should look like, and running it just confirms or corrects toward that, safely, regardless of how many times it's already run. That's also precisely what verify_idempotency.sh exists to catch automatically — run a playbook twice, fail loudly if the second run reports anything other than changed=0 — rather than relying on someone noticing a suspicious recap by eye.

The concept isn't specific to Ansible, either. It's the same property that separates HTTP's idempotent methods (PUT, DELETE) from the ones that aren't (POST) — a repeated PUT should leave a resource in the same state as a single one, while a repeated POST might create the same thing twice. Same underlying question either way: if this runs again by accident, does the end state stay correct, or does it quietly drift?
