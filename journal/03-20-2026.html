March 20, 2026 Homelab Learning

CI/CD in the Real World

My front-end development coursework this week asked me to map an eight-phase CI/CD pipeline to something real in my life. The example in the assignment was a podcast. I used my homelab instead.

It turned out to be a better exercise than I expected — not because it made the assignment easier, but because it forced me to articulate something I'd been doing intuitively without a framework for it.

The pipeline mapped to infrastructure

Every service I deploy follows roughly the same cycle, even when I don't think of it that way. Mapping it explicitly made the pattern visible:

Phase What it looks like in my lab
Plan Decide what to deploy, check resource availability across four Proxmox nodes, determine network placement
Code Write config files, firewall rules, NPM proxy host entries — commit to Git before touching anything
Build Provision the LXC or VM, apply configs, assign static IP on 10.10.10.0/24
Test Access via internal IP first, then test through NPM proxy, then verify Tailscale remote access
Release Commit finalized configs to GitHub, update documentation
Deploy Set autostart on boot, enable NPM proxy host with SSL, add to Uptime Kuma
Operate Monitor via Uptime Kuma, apply updates, watch Proxmox resource usage
Monitor Review firewall logs, track uptime trends, evaluate whether the service is doing what I built it to do

The gap between the documented process and the real one

Writing this out exposed something uncomfortable: the process I documented is cleaner than the process I actually follow. I don't always commit configs before making changes. I don't always update documentation after deploying something. The monitoring step listed Uptime Kuma as if it was already running — it wasn't, I deployed it the same day I wrote the assignment.

Documenting what you intend to do is easy. Doing it consistently under pressure is the actual skill.

Foreseeable frustrations I wrote about

The assignment also asked me to anticipate frustrations. A few I flagged:

  • Git habits. The hardest part isn't knowing version control exists — it's building the reflex to commit before you start playing, not after something breaks.
  • Dependency chains. OPNsense and NPM are foundational infrastructure. If either misbehaves, every downstream test and deploy phase blocks. You can't mock your own router.
  • Long iteration cycles. A software CI/CD loop can run in minutes. An infrastructure cycle — plan to monitor — might take a full weekend session. That makes it easy to leave things half-finished.
  • Ansible and Uptime Kuma are still new. I know enough to know what they're for. I don't know enough to use them without hitting walls. That's fine — it's why I have a lab.

What the assignment was actually teaching

CI/CD isn't just a software deployment concept. It's a thinking pattern — iterative, documented, testable, repeatable. The fact that it maps cleanly to infrastructure work, homelab management, even personal projects, suggests it's a more general framework than it first appears.

I'll probably think about my homelab sessions differently now. Less "playing around" and more "running a cycle."
