Building a Homelab Dashboard

I've had monitoring in place for a while via Uptime Kuma, but monitoring tells you when things break — it doesn't give you a clear picture of what's running and how to get to it. That's what a dashboard is for. Today I deployed Homepage and it turned out to be one of the more satisfying things I've set up.

Why Homepage

The homelab dashboard space has a few options — Homarr, Dasherr, Flame — but Homepage kept coming up as the most actively maintained and the most capable in terms of integrations. It also uses YAML config files rather than a database, which means the entire configuration lives in plain text that I can version control and back up trivially. That felt like the right architectural choice.

The install process

Homepage runs as an LXC on my main cluster node. The installation was straightforward — clone the repo, install dependencies, build. The build step is memory hungry though. 512MB RAM caused the process to max out and stall. Bumped it to 1GB temporarily, ran the build successfully, dropped it back down. Homepage at runtime uses well under 512MB.

Build requirements and runtime requirements are different things. Always check both before sizing a container.

YAML configuration

Homepage is configured through four YAML files — services, bookmarks, widgets, and settings. Services define the dashboard cards grouped by category. Bookmarks define quick-link rows. Widgets populate the top bar with system stats. Settings control layout, theme, and access control.

YAML's indentation-sensitive syntax is unforgiving at first. A single misaligned line breaks the whole config silently — Homepage just renders nothing for that section rather than throwing an error you can act on. The fix is methodical editing and checking the result after every meaningful change.

It's worth noting that Ansible — which is next on my learning roadmap — is almost entirely YAML. Time spent in Homepage's config files is quietly building fluency I'll use constantly later.

Proxmox live stats

Homepage can pull live data from Proxmox via API tokens — VM and container counts, CPU usage, memory usage per node. Setting this up required creating a dedicated API token on each node through the Proxmox web interface, then referencing those credentials in the services config.

The network node pulled stats immediately. The cluster nodes needed their own tokens created individually — they don't share credentials across the cluster automatically. Once that was sorted, all four nodes show live resource data on the dashboard.

Wildcard SSL and DNS

Homepage is proxied through NGINX Proxy Manager and accessible at a subdomain with HTTPS. The SSL certificate is a wildcard issued through Cloudflare, which means any new subdomain I add gets HTTPS automatically without touching certificates again. That's the right way to handle it — set it up once, never think about it again.

What the dashboard actually does

At a glance I can see CPU and memory across all nodes, which services are running where, and get one-click access to any interface in the lab. It sounds simple but having everything in one place changes how the lab feels to use — less context switching, less remembering which IP does what.

It's also a forcing function for documentation. Every service that goes on the dashboard gets a description and a category. That discipline compounds.

What's next

  • Ansible for configuration management across nodes
  • Prometheus and Grafana for metrics and temperature monitoring
  • Network+ certification — study begins in earnest
