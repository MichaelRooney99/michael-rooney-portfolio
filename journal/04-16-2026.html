April 16, 2026 Homelab

Chasing Ghosts, Finding Watts

Today was one of those sessions where you go in with a simple goal, pull on a thread, and three hours later you're somewhere you didn't expect — with something better than what you set out to build, and still no clean answer to the original question.

The starting point was the backup server. It had been randomly unreachable for extended periods — the dashboard would show it red, backups would fail, and then it would come back on its own or after I noticed and poked at it. Annoying. The kind of thing you can ignore for a day or two before it becomes the thing you have to sit down and actually fix.

The first answer was easy

The backup server runs as a VM on one of my cluster nodes. When I dug into the task logs, the pattern was immediate — the VM wasn't crashing, the node was rebooting. Every outage corresponded to a reboot event on the host. The backup VM wasn't set to auto-start, so when the node came back up, the VM just sat there stopped until someone manually started it.

That part was a one-liner to fix. Auto-start on boot, done. The backup server will come back up automatically now regardless of why the node reboots. Problem solved at the surface. Then I made the mistake of looking at why the node was rebooting.

Everything that wasn't the problem

I went through the standard checklist. Thermals — fine, mid-40s under load, well within spec for a small form factor machine. Memory — 28GB free, swap untouched, no OOM events in the logs. Kernel panics — none. Machine check errors — none. Hardware watchdog misfiring — not active. Rogue cron jobs — nothing unusual. Power — the node is on a brand new UPS I'd just picked up, so simple power sags were unlikely.

I did find one thing that needed cleaning up — a custom monitor service that had been created during an earlier debugging session. It was broken from the start due to a quoting error that systemd flagged on every boot, and instead of running live diagnostics, it was just endlessly echoing a hardcoded snapshot of data from weeks ago into log files. It was doing nothing useful and generating noise. Disabled and removed.

But that wasn't causing the reboots either.

The reboots that weren't reboots

When I finally pulled the full shutdown logs from before each reboot event, the picture got clearer and more frustrating at the same time. The shutdowns were clean. Fully ordered, graceful, every service stopping in sequence — the kind of shutdown you only see when something deliberately told the OS to shut down. No crash, no panic, no watchdog timeout. Just a clean exit.

Going further back through the reboot history, most of the clustering events — multiple reboots in a single day — lined up with dates I'd been actively working on the node. My own debugging sessions. The node wasn't randomly rebooting. I was rebooting it and apparently forgetting I'd done it, or not connecting the dots when reviewing history later.

Ruling out hardware, software, power, and firmware as causes is genuinely useful — even when the answer turns out to be "it was you the whole time."

There's one reboot that doesn't fit that pattern cleanly — a poweroff event late in the session today that happened while I was actively trying to SSH into the node. The logs show a clean poweroff target, not a reboot target, triggered by something that issued a shutdown command. The node came back on its own, which points to either the UPS or the hardware cycling it. I was in the middle of reconfiguring the UPS monitoring service at the time, which is a plausible culprit. The root cause on that one is still open.

UPS monitoring — the actual win today

Since I was already deep in the node's configuration and had just picked up a new UPS, it made sense to finally get proper power monitoring set up. The UPS has a USB port for data — plug it in, install Network UPS Tools, and you get live telemetry on battery charge, runtime, load, and input voltage.

I ended up building out a full NUT architecture across the cluster. One node acts as the master — it has the USB connection to the UPS and runs the NUT server, exposing power data on the network. Every other node runs a NUT client that connects to the master and can trigger a graceful shutdown if the UPS battery gets critically low. The whole cluster will shut itself down in an orderly way during a sustained power outage rather than just dying when the battery runs out.

On top of that I deployed PeaNUT — a clean web UI for NUT that lives in its own LXC on one of the cluster nodes. It connects to the NUT server and gives a proper dashboard view of UPS health, load history, and battery status. That's now proxied behind a domain with SSL like everything else in the lab, and there's a live widget on the homelab dashboard pulling the same data.

65 watts

Once everything was connected and reading, I had something I didn't have before — actual power draw data for the whole homelab. The UPS is reporting around 65 to 70 watts of total load across all four nodes, the switch, and whatever else is on that circuit.

That number is lower than I expected. Four mini PCs running Proxmox continuously, a managed switch, a UPS, and a handful of always-on services — under 70 watts. For context that's roughly what a single bright incandescent bulb used to draw. The efficiency of modern small form factor hardware running low-power processors is genuinely impressive once you see the actual number.

It also means the UPS has a lot of headroom. At current load, runtime on battery is well over 50 minutes. That's enough to ride out almost any realistic power event without a graceful shutdown ever being necessary.

Where things stand

The backup server auto-start is fixed. Power monitoring is live across the cluster. PeaNUT is deployed and integrated into the dashboard. The cluster is in better shape than it was this morning in every measurable way.

The mystery reboot is still a mystery. There's a communication gap somewhere between the monitoring stack and the backup service — something occasionally drops the connection in a way that looks like an outage without leaving clean evidence of why. I'll keep an eye on it. The NUT monitoring and the auto-start fix mean the blast radius of future events is significantly smaller regardless of cause.

Some days you solve the problem. Some days you build better infrastructure around it and call that a win. Today was the second kind. I'll take it.
