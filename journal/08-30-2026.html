The VLAN That Existed on Exactly One Port

A phone would associate to the new guest Wi-Fi network fine — authentication succeeded instantly, no password needed, exactly as designed — and then just sit there. No IP address, ever. Every individual piece of the chain that should have produced one checked out clean on inspection. The actual bug was one I'd built myself, days earlier, and never noticed: a VLAN that had been created but only ever connected to a single port on the entire switch.

The setup, briefly

A new EAP610 access point, freshly adopted into a self-hosted Omada controller, broadcasting two SSIDs — one for lab devices on VLAN 20, one open/passwordless guest network on VLAN 30. The lab SSID worked immediately. The guest SSID authenticated but never completed a DHCP handshake, which on most phones just shows up as a spinner that eventually gives up and says something unhelpful like "Failed to obtain IP address."

Ruling things out, one real check at a time

The instinct with an isolated VLAN that "almost works" is to suspect the newest thing you touched — in this case, Omada's SSID configuration. That got checked first: VLAN tagged correctly by ID, Guest Network toggle turned off (it assumes an Omada-brand gateway is present to handle guest traffic, which this network doesn't have), security set to Open. All correct.

Next was the router side — OPNsense already had a documented, known gap where a VLAN interface was missing from Dnsmasq's list of interfaces to actually serve DHCP on. A strong candidate, and worth checking first precisely because it was already a known issue rather than a new guess. Checked the Dnsmasq General tab: the interface was there, correctly included alongside the others. Ruled out.

Then the device itself — was the AP even running the config it was supposed to be running? Pulled up the device's own WLANs tab directly on the controller, which lists exactly what SSIDs are live on that specific radio, not just what exists in the controller's database. Both SSIDs, correct VLANs, enabled, synced. Also clean.

The packet capture that actually settled it

At that point, three plausible layers had all checked out individually correct, and the bug was still there. That's exactly the situation where guessing at a fourth layer stops being productive — the better move is querying the source directly rather than continuing to reason about config screens. OPNsense's own packet capture tool, filtered to the guest VLAN's interface and to DHCP ports specifically, would show definitively whether a request was even arriving at the router.

It ran for the full duration of a connection attempt. The resulting capture file was 24 bytes — an empty pcap header, zero packets. Not "no response." Nothing arrived at all.

That one empty capture eliminated the entire router side of the problem in a single check. If nothing reaches OPNsense, OPNsense can't be the bug — full stop, regardless of how many DHCP settings get re-examined there. The problem had to be upstream: the AP or the switch.

Finding the actual gap

With the AP's own config already confirmed correct, that left the switch — specifically, the 802.1Q VLAN membership table, not the per-port tag/untag settings that had already been checked once. Pulling up VLAN 30's own definition and comparing it side by side against VLAN 20's told the whole story immediately: VLAN 20 listed six member ports, including the trunk port running up to OPNsense. VLAN 30 listed exactly one — the port the access point itself was plugged into.

The access point was doing everything right. It tagged guest traffic as VLAN 30 and sent it out correctly. The switch received that tagged frame on a port that was, in fact, a member of VLAN 30 — so it accepted it. And then had nowhere to forward it, because no other port on the switch was a member of that VLAN. Not the uplink, not anything. The frame had a valid entry point and no exit, so the switch silently dropped it. That's why nothing ever reached OPNsense to be captured, logged, or even rejected — from the router's perspective, VLAN 30 traffic simply didn't exist.

The fix was one checkbox: adding the trunk port as a tagged member of VLAN 30, the same way it already was for VLAN 20. The instant that was applied, the guest network worked exactly as designed.

The actual lesson

Defining a VLAN and giving it a member port is not the same claim as giving that VLAN a path anywhere. A VLAN's traffic can only travel between the ports that are explicitly members of it — every hop, not just the ports where end devices happen to plug in. It's easy to remember that when building the first VLAN, where the trunk-to-router membership feels like an obviously required step you're actively deciding to add. It's much easier to forget on the second one, where the mental model has quietly shifted to "add the VLAN, assign the device's port, done" — skipping the fact that the trunk membership isn't automatic just because a previous VLAN already used that same trunk port.

Worth connecting back to something from the first time VLAN segmentation went into this lab — the trunk port carrying multiple tagged VLANs to the router was the whole point of the design from day one. What broke here wasn't a misunderstanding of that concept; it was a configuration screen where adding a new VLAN doesn't automatically add it to ports that already exist as trunks for other VLANs. The 802.1Q standard itself doesn't have an opinion about that — it's purely a per-switch, per-VLAN membership table, and every entry in it has to be explicit.
