The Half-Second Nobody's Supposed to See

Building a light/dark toggle for the status page, I said a few things almost in passing — no flash of the wrong theme on reload, the OS preference gets respected the first time you ever visit, your choice sticks after that. Someone asked me to actually explain those, rather than take them as given. Fair ask — there are three separate ideas doing work there, and one of them only became simple because of a genuinely recent change to how Tailwind handles theming at all.

The problem, named properly

A page that decides its own colors in JavaScript has a timing problem most people never notice until they build one. The browser paints the page the instant it has enough CSS to do so. If the "real" theme decision — read localStorage, check the OS preference, pick light or dark — happens inside a React component after the page has already mounted, there's a real gap between "first paint" and "correct paint." For a fraction of a second, the browser shows whatever the default CSS says, then visibly snaps to the right theme once the JavaScript catches up. On a page that should load in light mode for a given visitor, that means a flash of dark before it corrects itself. Small, but the kind of small that reads as broken the moment you actually see it happen.

Fixing it by not letting the browser paint yet

The fix isn't clever, it's just early. A plain <script> tag — not type="module", not async, not defer — sitting in <head> blocks the browser from rendering anything until it finishes running. Put the theme decision inside one of those, ahead of any stylesheet, and the correct theme is already set on the page before the first pixel ever gets painted. There's no wrong frame to flash, because the browser never renders a frame with the wrong answer in the first place. 

(function () {
  var stored = localStorage.getItem('capstone-theme');
  var theme =
    stored === 'dark' || stored === 'light'
      ? stored
      : window.matchMedia('(prefers-color-scheme: light)').matches
        ? 'light'
        : 'dark';
  document.documentElement.setAttribute('data-theme', theme);
})();

That same logic runs again inside a React hook once the app actually mounts — deliberately kept as the same priority order in both places rather than shared code, since the inline version has to run before any JavaScript module has loaded and can't import anything. Two copies, same decision, timed differently on purpose.

Asking the OS instead of guessing

window.matchMedia('(prefers-color-scheme: light)').matches is doing more work than it looks like. Every modern OS lets someone set a system-wide light or dark preference, and the browser exposes that choice to any page that asks — no permission prompt, no async loading, just a synchronous true-or-false read of something the visitor already decided once, at the OS level, probably without ever thinking about this specific page. Defaulting a new visitor to whichever theme happens to be more convenient to code first is a small but real disrespect of a preference they already stated somewhere else. Asking costs one line.

The priority order matters and is easy to get backwards: check for an explicit stored choice first, and only fall back to the OS preference if there isn't one. Someone who deliberately picked light mode on a dark-preferring system made a real choice — the OS default should never silently override something they already told the page directly.

Making the choice stick

Once someone actually clicks the toggle, localStorage.setItem('capstone-theme', theme) writes that choice somewhere that survives a reload, a closed tab, a restarted browser — unlike sessionStorage, which clears the moment the tab closes. Nothing exotic here; the interesting part isn't the storage mechanism, it's that both the inline script and the React hook read the exact same key with the exact same fallback order, so they can never disagree with each other about what the "current" theme actually is.

Where Tailwind actually enters this story

None of the above is Tailwind-specific — it would work identically with plain CSS. The part that is specific to this project's tooling is how the theme values themselves get defined, and it's a genuinely new capability. Tailwind v4 replaced its old JavaScript config file with a CSS-native @theme block, and critically, values inside @theme are allowed to be var() references pointing at other CSS custom properties — not just static colors. 

@theme {
  --color-capstone-bg: var(--theme-bg);
  --color-capstone-text: var(--theme-text);
}

:root {
  --theme-bg: #0e0d0b;
  --theme-text: #f0ede8;
}

[data-theme="light"] {
  --theme-bg: #faf7f2;
  --theme-text: #201e1a;
}

That indirection is the whole trick. Tailwind compiles real utility classes from that @theme block — bg-capstone-bg, text-capstone-text — and their generated CSS is literally background-color: var(--color-capstone-bg). Since that variable is itself defined as var(--theme-bg), and --theme-bg's actual value depends entirely on which CSS selector currently matches the page (:root versus [data-theme="light"]), flipping one HTML attribute cascades through every element using that utility class — instantly, with zero JavaScript re-render, because the browser is just re-resolving a CSS variable the way it always does.

Worth naming the alternative this replaces: Tailwind's older dark: variant approach means writing two classes on every themed element — bg-white dark:bg-black — for every property that changes. That scales fine for a handful of elements and gets genuinely unpleasant across a real component tree, since every single element needs its own explicit light-and-dark pair remembered and kept in sync by hand. The token-based approach only requires writing the utility once; which actual color it resolves to is entirely the CSS cascade's problem, not something tracked per-element in the markup.

Where this actually landed

Built this into the status page's theme toggle directly — one @theme block mapping named tokens to CSS variables, two selector blocks defining what those variables actually equal in each mode, one inline script prevent the flash, one hook to keep it in sync after mount. The interesting realization wasn't any single piece — it's that "avoid a flash," "respect the OS," and "remember the choice" are three genuinely separate problems that happen to look like one feature from the outside, and each one has a small, specific, well-established answer once you see them as distinct.
