What a Webhook Actually Asks of You

Every piece of monitoring in this homelab so far has worked the same way: something checks, on a schedule. Prometheus scrapes a target. A dashboard polls an endpoint. The whole capstone status page is built around that model — ask, wait, ask again. A webhook flips that around entirely, and building a real one for the first time this week made clear how much that flip actually changes, not just in theory but in what the code has to account for.

The difference isn't speed, it's who's in charge

The instinct is to think of a webhook as just a faster kind of polling — instead of asking every sixty seconds, you get told immediately. That's true, but it undersells what actually changed. With polling, the client decides when to check, how often, and what to do if a check fails — all the control lives on the side asking the question. A webhook hands that control to whoever's on the other end. Something external decides when your server hears from it, and your server's job is just to already be listening, correctly, whenever that happens. That's a real shift in where responsibility sits, not just a change in latency.

What "already listening" turns out to demand

Two things stopped being optional the moment a server existed specifically to receive calls from somewhere else, rather than to answer questions on its own terms.

The first was concurrency. Nothing about a webhook guarantees only one delivery arrives at a time — a person could push twice in quick succession, a retry could fire while the first attempt is still running. A receiver that just runs whatever it's told, whenever it's told, has no way to recognize "I'm already doing this" and will happily start a second deploy on top of a first one. The fix was a simple lock file — check first, refuse if busy, release when done — but the need for it only exists because something is now listening instead of asking.

The second was authentication, and specifically the kind that doesn't assume a human. Every access control this project had built before this point assumed a person logging in — an email, an OTP, a browser. A webhook caller is a machine with no browser and nothing to click. Trusting it can't work the same way trusting a person does; it needs a credential a machine can present in a header, checked at the edge before the request ever reaches anything real.

The response itself is a real design decision, not a formality

One instinct while building this that turned out to be wrong, briefly: have the receiver do the work and then respond once it's actually done, so the caller gets a real answer. That's backwards for a webhook specifically. The thing that triggered it is often waiting on a fixed timeout, and the actual work here — a full deploy, tests included — takes far longer than that timeout allows. The correct shape is to acknowledge the delivery immediately, then do the real work afterward, separately, reporting the outcome through a different channel entirely rather than the original response. Confirming this wasn't just an assumption — it's the documented recommendation for exactly this situation, which was a good, small confirmation that the instinct landed on the right design for reasons that generalize beyond this one project.

An old alert relay became the accidental proving ground

The "report the outcome separately" piece needed somewhere to actually report to, and the obvious answer was a small Flask relay already sitting in the homelab, built months ago for a completely unrelated, mostly-for-fun purpose — turning backup notifications into something with a little more personality. Wiring one new route into that existing file surfaced three real problems that had nothing to do with webhooks specifically: a data structure that had gone missing during editing, a duplicate function definition, and a stubborn character-encoding issue that kept corrupting the same two symbols through several attempts at fixing it, eventually solved by just not using those characters at all rather than continuing to fight whatever was mangling them.

None of those were webhook problems. They were just bugs, the kind that only show up by actually running code and watching what happens to it, and they happened to surface because a small, previously-quiet file suddenly had real weight riding on it for the first time.

What actually proved it worked

Not that the receiver started cleanly, and not that a manual test curl came back with the right status code. Those were necessary steps, but the real proof was deliberately triggering a real deploy with a real, planted failure in it, and watching the whole chain — trigger, authentication, the receiver, the deploy, a genuine failure, an automatic recovery, and a notification landing in the right place — actually happen, once, for real, before ever trusting the mechanism against something that mattered.
