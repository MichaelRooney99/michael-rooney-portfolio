Building a Homelab Kanban Board

The homelab dashboard was showing a blank area next to the monitoring section. Rather than fill it with something decorative I started thinking about what would actually be useful there. A calendar felt too tied to external accounts. What I actually needed was a way to track the moving parts — homelab projects, cert progress, internship conversations, coursework deadlines — without switching between tools constantly.

The answer was a self-hosted Kanban board. Specifically Planka — a clean, minimal, open source tool that does one thing well. No bloat, no subscriptions, no data leaving the network.

Why Kanban makes sense right now

I'm balancing more parallel workstreams than at any point in this transition. Network+ study, Google IT cert modules, portfolio updates, homelab builds, internship conversations across multiple departments, and regular coursework. Some of those are active, some are blocked waiting on external factors, some are done but undocumented.

A Kanban board with Backlog, In Progress, Blocked, and Done columns maps directly to that reality. Each card gets a category, a description, and sub-tasks. Moving a card from Blocked to In Progress when a dependency resolves is more satisfying than hunting through notes to remember where something was left.

The tool you'll actually use is better than the perfect tool you keep meaning to set up. Planka took one evening to deploy.

The installation

Planka runs as an LXC on my third cluster node — Murloc — which had been sitting nearly idle. The official installer script handles Docker, PostgreSQL, and an internal NGINX reverse proxy automatically. The whole process from blank LXC to running Planka was under 30 minutes.

The installer sets up its own NGINX inside the container to handle websocket routing for real-time updates. That created an interesting challenge when routing through my external reverse proxy — the two NGINX instances needed to cooperate rather than conflict. Getting the websocket connection to work cleanly through the proxy took some troubleshooting, which is its own lesson in how layered proxying works in practice.

What goes on the board

The initial board structure I'm working with:

  • Backlog — everything queued but not started. NAS build, Ansible, Prometheus/Grafana, remaining Google IT cert modules.
  • In Progress — active work. Network+ study, current homelab session, portfolio journal entries.
  • Blocked — waiting on something external. KwikTrip internship department responses, Network+ exam scheduling.
  • Done — completed and documented. PBS deployment, Planka install, SEO pass on portfolio.

Each card links to the relevant Obsidian note or journal entry where the detail lives. The board is the status view — the notes are the documentation. They serve different purposes and work better together than either does alone.

The bigger picture

Between Uptime Kuma for monitoring, Homepage for a live infrastructure overview, Obsidian for documentation, and now Planka for project tracking, the homelab has developed a genuine operational layer on top of the infrastructure layer. That's not something I planned deliberately — it emerged from asking what's actually useful rather than what's technically impressive.

That distinction feels important. The goal was never to run the most complex homelab. It was to build something that teaches real skills and solves real problems. A Kanban board I check daily does more for the transition into tech than another service running idle in a container.
