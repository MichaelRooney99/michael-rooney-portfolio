Planka, Persistence, and Layered Proxies

I spent two days troubleshooting a websocket issue with Planka that turned out to be one of the more instructive problems I've hit in the homelab. Not because the fix was complicated — it wasn't — but because the path to finding it required understanding exactly how traffic flows through a layered proxy setup.

What was happening

Planka's official installer sets up its own NGINX instance inside the container to handle websocket routing. My external reverse proxy — NGINX Proxy Manager — sits in front of that. Two NGINX instances in the path, each with their own configuration, each expecting to handle certain headers.

The symptom was a spinning loading screen after login. The browser console showed websocket connection failures on the socket.io path. Traffic was reaching the container but the websocket upgrade wasn't completing successfully through the proxy chain.

When something works directly by IP but fails through a proxy, the proxy is almost always modifying or dropping something the application depends on. The question is what.

What I tried

The standard websocket proxy headers — Upgrade, Connection upgrade, proxy_http_version 1.1 — are the first thing to check. I added those to NPM's advanced config. Still spinning. The internal NGINX already had those headers configured, so adding them again at the NPM layer was creating conflicts rather than solving anything.

I checked the BASE_URL setting in Planka's environment config — it was set to HTTP while the site was being served over HTTPS. Updated it. Still spinning. Deleted the proxy host and recreated it from scratch. Checked ports, checked the internal NGINX default server block that was intercepting traffic before the Planka server block. Each fix resolved one layer and revealed the next.

What fixed it

The resolution came from understanding the internal NGINX configuration fully and then configuring NPM to pass traffic through cleanly rather than trying to handle websockets itself. The internal NGINX already had correct socket.io routing — NPM just needed to get out of its way rather than duplicate the work.

Once that mental model clicked the fix was straightforward. Two days of frustration, ten minutes of actual configuration change. That ratio is familiar by now.

Vikunja as a comparison point

While working through the Planka issue I also deployed Vikunja — a more fully featured task manager with Kanban support. The contrast was immediate. Vikunja required no special proxy configuration whatsoever. Standard NPM setup, wildcard SSL, done. No internal proxy layer to navigate.

Both tools are now running. Planka is clean and minimal — pure Kanban with a card-based interface that feels fast. Vikunja has more structure — projects, subtasks, due dates, and a Homepage widget that shows tasks in progress, overdue items, and upcoming deadlines directly on the dashboard.

Which one I actually use consistently will tell me more about what I need than any feature comparison. That's the real evaluation criteria for self-hosted tools.

What the whole process taught me

Troubleshooting layered proxy issues requires being able to isolate each layer independently. Direct IP access confirms the application is running. Internal curl confirms the container's own proxy is working. Browser dev tools confirm what the client is actually receiving. Each layer has its own diagnostic surface and you have to work through them in order rather than guessing.

That systematic approach — eliminate variables one at a time, confirm each layer before moving to the next — is the same methodology that applies to any network troubleshooting. The specific technology changes. The approach doesn't.
