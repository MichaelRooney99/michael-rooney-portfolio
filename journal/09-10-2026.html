The Flag That Only Checks

tsc --noEmit runs TypeScript's type-checker without writing any output files. That's the entire flag. The reason it's worth a second look is what it implies about what tsc does without it — and why a project would want type-checking and "actually building the code" to be two separate steps in the first place.

Two jobs bundled into one command

Running plain tsc does two things at the same time: it walks the whole project checking that every type actually lines up, and it compiles every .ts file into a real .js file somewhere on disk, wherever tsconfig.json says to put it. Most of the time that's exactly what you want — check it, then produce the thing that actually runs.

That stops being true the moment something else in the project is responsible for actually running the TypeScript. A backend built around tsx (or ts-node, or a bundler doing its own transpilation) never touches tsc's compiled output at all — tsx reads the .ts files directly and handles turning them into something Node can execute, on the fly, every time the dev server or a script runs. In that setup, a plain tsc build still happily writes a full second copy of the project as compiled .js, next to the real source, that nothing ever reads.

What the flag actually buys

--noEmit keeps the half that's actually useful — walk the project, check every type, report every error — and drops the half that would just be clutter. It's the same underlying type-checking pass either way; the flag only decides whether that pass also tries to write files as a side effect.

It's also a genuinely different check than a passing test suite. tsc --noEmit answers "does every type actually line up" — nothing about whether the logic behind those types is correct. A test suite answers the opposite question: does the behavior actually work, regardless of whether the types are airtight. Neither one substitutes for the other; a clean type-check and a green test suite are two separate real signals, not one signal said twice.

Where this actually shows up

On the Rack Planner backend specifically, this is why tsc --noEmit runs after every real change, before the actual test suite: a fast, side-effect-free way to catch a hand-keying mistake or a type mismatch immediately, without waiting on the slower step of actually exercising the code's behavior. Two checks, run in that order, because they're answering two different questions.
