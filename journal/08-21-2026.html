The Benchmark That Lied, Twice

Dega — the standalone node hosting the capstone status page — needed more room. 256GB was tight with two VMs on the roadmap instead of one, and the RAM was down to a single stick. The actual hardware swap ended up being the easy part. Trusting the new drive, and then trusting my own read of whether I could trust it, took two separate corrections before either one held up.

A budget drive with a real reason to be suspicious of it

The replacement was a 1TB KingSpec NX-1TB-FB — inexpensive, and I'd already been burned once by DRAM-less NVMe drives struggling under real load. Worth checking before it went anywhere near production. KingSpec's own product announcement for the NX series is explicit about it: built around a cache-free controller, relying on Host Memory Buffer instead of onboard DRAM. A firmware readout of this exact model confirmed HMB active at 64MB — consistent with that, not contradicting it. One review site claimed a 256MB onboard cache; the manufacturer's own words and the actual firmware telemetry outweighed that.

DRAM-less drives specifically struggle with sustained, concurrent random I/O — the exact pattern multiple VMs sharing one physical drive under Proxmox produce. Worth a real test before trusting it, not just a vibe check from watching an install run.

The first test wasn't actually testing anything

First pass in a dummy M920Q: installing Proxmox itself felt noticeably slow. Before drawing any conclusion from that, the honest answer was that the drive had leftover configuration from a previous install — a plain reformat wouldn't have caught it. wipefs -a, sgdisk --zap-all, and blkdiscard -f cleared it properly — the last one matters specifically because it TRIMs the whole device, clearing data still sitting in flash cells that a reformat alone leaves behind.

Real testing needed a real tool, not a consumer benchmark — fio, the actual industry-standard for this. First real run specified --iodepth=32, meant to simulate several concurrent I/O streams the way multiple VMs would genuinely contend for one drive. The tool printed a warning that was easy to miss: 

note: both iodepth >= 1 and synchronous I/O engine are selected, queue depth will be capped at 1

fio's default I/O engine, psync, is synchronous — one request in flight at a time, full stop, no matter what depth is requested. The results confirmed it: IO depths: 1=100.0%. The entire first test measured something real, but not the thing it was built to measure — a single-request-at-a-time workload, not concurrent contention. Swapping to --ioengine=libaio (an async-capable engine) fixed it — the corrected run showed 32=100.0%, real depth-32 concurrency, and a meaningfully different latency profile than the broken run had shown.

"Huge swings" that didn't survive actual math

Even with the engine fixed, one read of the results was still wrong. The IOPS summary reported a min/max spread from 31k to 71k reads per second — eyeballed, that looks like a drive lurching between good and bad performance. It wasn't.

fio samples instantaneous IOPS repeatedly throughout a run — nearly 2,400 times over five minutes here — and reports stdev alongside the min/max range. Actually dividing stdev by avg — the coefficient of variation, the right metric for comparing consistency across numbers with different scales — came out to roughly 3.3–3.4%. That's a tight, consistent distribution. Min and max are each a single most-extreme sample out of nearly 2,400 data points, not a representative picture of typical behavior on their own. The visual impression from the range alone was flatly wrong until the actual math got done.

Forcing the real answer: a fixed 100GB, no shortcuts

One thing hadn't been settled yet: a freshly wiped, mostly empty drive can dynamically borrow a large pool of spare flash as a fast SLC write cache — meaning an early-run benchmark can look fast simply because it never wrote enough to exhaust that cache, not because the drive is actually fast once it's full.

The fix was dropping --runtime entirely and setting a fixed --size per job instead — four jobs at 25G each, guaranteeing a full 100GB written regardless of how long it took. It never dropped. Sustained ~296MiB/s and 75.7k IOPS across the entire 100GB, coefficient of variation around 1.7% — tighter than the earlier test, not looser. A small latency tail out at the 99.9th percentile (~13ms against a ~1.5ms median) turned out to be ordinary background garbage collection, not a cache running dry — negligible at the actual scale of I/O two lightweight VMs will ever throw at it.

The part that actually mattered: resizing storage under a live VM

Cloning is a 1:1 sector-level copy — the new 1TB drive booted still behaving like a 256GB one until the partition table, physical volume, and thin pool all got told about the extra space, one layer at a time. parted flagged it immediately on first inspection: the GPT header still described the old disk size. Fixing that only updates the table's awareness of the disk — the partition itself was still sitting at its original 255GB until parted resizepart 3 100% actually grew it. 

parted /dev/nvme0n1 resizepart 3 100%
pvresize /dev/nvme0n1p3

That freed up roughly 731GB inside the LVM volume group — confirmed via vgs, not assumed. Extending the thin pool that actually backs VM disks came with one real trap: a plain lvextend -l +100%FREE /dev/pve/data only grows the pool's data portion. A thin pool's metadata volume — tracking which chunks belong to which VM disk — doesn't scale automatically, and growing the data pool roughly 6x without growing metadata alongside it is exactly the kind of thing that looks fine today and turns into a genuinely ugly failure mode months later once it actually fills. One extra flag closed that gap in the same command: 

lvextend -l +100%FREE --poolmetadatasize +1G /dev/pve/data

Verified from three independent angles before calling it done — lvs from the shell, the Proxmox Disks panel showing the drive at its full size with a clean S.M.A.R.T. pass, and pvesm status confirming Proxmox's own storage layer agreed with what LVM reported. Three sources agreeing is a much stronger claim than one command's output looking right.

What actually caught the outage

The physical swap meant Dega, and the capstone VM running on it, were genuinely offline for a stretch. No incident got drafted — there was nothing left running to draft one — but the status page's own uptime history still recorded the gap once everything came back. Not a designed test, just an honest, unplanned confirmation that the monitoring stack degrades gracefully instead of silently losing the record entirely.
