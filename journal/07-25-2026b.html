Three Small Lies a Working Ansible Collection Told Me

Second entry today — the scraper writeup this morning was curiosity for its own sake; this one's the actual roadmap item it turned out to sit next to. Every Proxmox node has needed one manual step since Zabbix Agent 2 first went out: opening the frontend and registering the host by hand. Today that step got automated, and it took three real, specific bugs to get there — none of them the kind you'd guess from reading the collection's own documentation.

The plan that was already wrong

Scoped a few sessions back: use the community.zabbix collection instead of hand-rolling API calls, since it handles idempotency correctly rather than me reimplementing it badly. The plan called for passing server_url, login_user, and login_password straight to the module. First real run:

Unsupported parameters for (community.zabbix.zabbix_host) module: login_password, login_user, server_url

The collection had moved on. Current versions authenticate through a dedicated httpapi connection plugin — the play has to "connect" to the Zabbix server the same way a network-device play connects to a switch, not pass credentials as task arguments. That's a structural change, not a syntax fix: the play's actual target became a new zabbix_server inventory entry, deliberately kept out of every other group so no SSH-based playbook ever picks it up by accident, with the real node names looped over inside the play instead of driving which hosts it targets.

A global default that assumes a shell that isn't there

Second run, past the auth fix:

/bin/sh: 1: sudo: not found

ansible.cfg sets become: true globally, for every play, by default — correct for every SSH-based playbook in this fleet, and something I've never had to think about before because every previous playbook actually had a shell to escalate privilege in. An httpapi connection doesn't. There's no remote terminal underneath it for sudo to run inside — it's an HTTP call, not a login session. Explicit become: false on this one play fixed it, and a Zabbix API call was never going to need root regardless.

Two permission systems that look like one

Third run:

Template not found: Linux by Zabbix agent

The automation user had Read-Write on the Proxmox Nodes host group — visibly correct in the frontend, confirmed twice. What I hadn't touched was template group permissions, a separate scope from host group permissions in Zabbix's own permission model. The user couldn't see the template at all through the API, despite it being completely visible and linked correctly when I checked as myself. Granted Read on the template's actual group and the error vanished.

Confirmed the way everything gets confirmed here

Ran it dry against Ankhh first — already registered by hand months ago — specifically to prove the module would recognize existing state instead of trying to recreate it. ok, not changed. Then the same dry run against the full fleet: all six nodes, ok across the board, changed=0 in the recap. Only then the real run, same result. Wired into new_node_setup.yml via import_playbook right after the agent install, and the manual frontend step is genuinely retired now — any new node gets registered automatically the moment it joins the fleet.

Where this leaves me

None of the three errors were things I could have predicted from reading the module's parameter list ahead of time — each one only showed up by actually running it against a real server and reading what came back. Good reminder that "the collection handles this correctly" and "I know exactly how the collection handles this" are different claims, and only one of them needs to be true before you start.
