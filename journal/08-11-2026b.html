A Comment Can Be Perfectly Honest and Still Be Wrong

The task going in felt almost clerical: a full pass through the capstone codebase's comments, replacing every reference to a private planning document with an explanation that stands on its own. Nothing about the code was supposed to change. It was a writing task, not an engineering one.

Doing it properly meant actually reading every comment in every file, start to finish, instead of skimming for the pattern being removed. That's the part that mattered. One comment, in the config that routes traffic to the backend, described exactly what a particular live-update connection needed to work correctly — the specific settings, the exact reasoning for each one. It was a genuinely good comment. It was also describing something that had never been built. The setting it explained didn't exist anywhere in the file.

A broken feature with a perfect alibi

A quick, direct check against the live site confirmed it — the connection that was supposed to power near-instant status updates had been silently falling back to a static page since the day it shipped. Not degraded. Not intermittent. Never once worked.

Nobody noticed because two separate, individually good decisions combined into exactly the wrong outcome. The client-side code treats a failed live-update connection as routine — no console error, no visible complaint, just a quiet retry — because a dropped connection reconnecting on its own really is normal and shouldn't look like a problem. And the page has a slower fallback built in specifically so a missing live-update connection never breaks anything, just makes updates arrive a little later. Both of those are the right calls in isolation. Together, they meant a completely dead feature was indistinguishable, from the outside, from a healthy one quietly running on its backup plan.

The actual lesson, separated from the bug

The bug itself got fixed in twenty minutes once it was found. The more interesting part is what it means for comments generally. A comment is a claim about the code, not a guarantee. It can be written by someone who fully understood what needed to happen, worded with total precision, and still describe a world that the actual code never caught up to. Reading the comment told me what should happen. Only checking the real, running system told me what actually did.

That distinction turns out to generalize past this one bug. A comment in the code, a changelog entry, an architecture decision record, a runbook — these are all different tools solving different problems, and none of them are the system itself. A comment explains why a piece of code looks the way it does, for whoever reads that code next. A changelog is a record of what changed and when, for tracing how something got to its current state. A decision record is the reasoning behind a choice, so the same debate doesn't happen twice without anyone remembering why it was settled the first time. All of them are worth keeping current, and none of them are a substitute for actually going and checking the thing they describe.

Why this is worth writing down at all

This project has been as much about learning how to build software properly as it has been about the status page itself, and today felt like one of the clearer examples of that — a task that looked like tidying turned into a real finding, purely because doing it thoroughly meant actually reading the thing instead of trusting that it was probably fine. That habit doesn't feel like it belongs to any one project. It's the kind of thing worth carrying into whatever comes after this one.
