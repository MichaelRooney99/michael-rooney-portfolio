Smoke Test Doesn't Mean What the Exit Code Thinks It Means

"Add a smoke test" has been sitting on a scope doc for weeks, filed as one item in a list of four testing layers. Getting to it made the term worth actually unpacking, rather than treating it as a synonym for "test."

Where the name comes from

Hardware, originally. Power something on and watch for smoke. No smoke, move on to real testing. Smoke, stop immediately — something's fundamentally wrong, no point running detailed diagnostics on it yet. Software borrowed the term directly: fast, shallow, and specifically meant to catch catastrophic failure before trusting anything deeper.

The gap it actually closes

Deploy tooling almost universally measures success by exit codes — did the command that started the thing return 0. That's a real signal, but it's a proxy for "it worked," not proof of it. A container can start cleanly, report success, and crash-loop three seconds later. The command that launched it already returned before that happened. As far as the deploy tool is concerned, nothing went wrong.

This isn't hypothetical for this project specifically — it's the exact, already-documented bug in the capstone's own deploy playbook. docker compose up's exit behavior decided whether Ansible reported the deploy as successful, with nothing actually confirming the site was serving requests afterward. A smoke test is the direct fix: hit the app's own /health endpoint right after the deploy step, and fail the whole play loudly if it doesn't come back healthy. Turns "the container started" into "the container started and the app is actually answering requests."

Not a replacement for a real test suite

Worth being precise about the boundary, since it's easy to blur. A real test suite runs before a deploy, against the code, and can be as thorough and slow as it needs to be. A smoke test runs after, against the real live thing, and asks exactly one narrow question: did this specific deploy actually work. It's not trying to catch a subtle logic bug — that's what the test suite upstream is for. It's trying to catch "the site is completely broken and nobody noticed yet," which is a much lower, much more urgent bar.

Why it comes last in the actual build order

A smoke test only means something once there's a real /health endpoint to check and a real deploy pipeline to attach it to — which is exactly why it's sitting downstream of the earlier pieces of this same project rather than being the first thing built. Testing the deploy outcome before the deploy process itself is trustworthy would just be adding a check on top of something already known to have gaps.
