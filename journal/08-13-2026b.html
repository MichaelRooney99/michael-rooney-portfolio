NULL Isn't Nothing

A table that's already been running in production for months needs three new columns added, all at once, for a new feature. The straightforward approach: add all three the same way, let old rows come back empty for values that didn't exist yet when they were written. Reasonable instinct. Wrong for exactly one of the three, and the reason why turns out to be worth understanding properly, not just memorizing as a rule.

What NULL actually means to a database

NULL isn't an empty string, isn't zero, isn't "false" — it represents the complete absence of a value, and it behaves strangely as a direct consequence. Ordinary equality comparisons simply don't apply to it. A row where some column is NULL doesn't equal any specific value in a query filtering on that column — not even another NULL. A condition like WHERE some_column = 'x' silently excludes any row where that column is NULL, without erroring, without warning. It just isn't included in the results, the same as if it failed the comparison outright.

Two columns where this genuinely didn't matter

Two of the three new columns in this migration were purely descriptive — read and displayed, never used to filter or search for anything. Old rows simply never had a real value for either of them, because the feature that would have populated them didn't exist yet when those rows were written. Leaving them NULL for old data isn't a gap to patch — it's the honest, correct answer for rows where the concept genuinely doesn't apply.

One column where it would have been a real, silent bug

The third new column was different in exactly one way: real application logic filters on it directly, inside a WHERE clause, to answer a specific operational question — something like "is there already an active record of this particular kind for this specific thing?" before deciding whether to create a new one.

Picture what happens if that column had been left NULL on every pre-migration row instead of given a real default. Every one of those old records is, in fact, exactly the kind the filter is looking for — they just don't say so explicitly anymore, because the column simply didn't exist when they were written. The query wouldn't error. It wouldn't warn. It would just quietly behave as though those old records didn't exist at all, because NULL can never satisfy an equality check, full stop. Code relying on that filter would treat genuinely already-existing records as though there were nothing there yet — and could easily create a duplicate, with no error anywhere pointing at why.

The actual fix, and why it works without extra effort

The real solution wasn't some elaborate one-time data-repair script. It was one clause, right in the same statement that added the column: a genuine default value, applied specifically because every row that already existed was, by definition, exactly that value — the feature that could have produced anything different for that column didn't exist until this exact migration ran. The database itself retroactively fills every old row with the correct value the instant the column is added. No separate update step, no follow-up script, no chance to forget a step — because the default value isn't just a fallback for missing input going forward, it's the entire migration for the data that already existed.

The lesson that actually generalizes past this one table: before deciding a new column is safe to leave empty for old rows, the real question isn't "does this column have a value yet." It's "does anything downstream ever go looking for this value in a way that requires it to actually be there." A column that's only ever displayed can be empty with zero consequence. A column that's ever asked "does this equal something" needs a real, deliberate answer for every row that existed before it did — or it quietly, invisibly, stops being findable at all.
