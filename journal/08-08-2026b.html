CI and CD Are Not One Thing

"Add CI/CD to the project" was on the capstone roadmap for weeks before it actually got built, filed as one item. It isn't one item. Building it made that obvious fast, and it's worth writing down why, because the difference ended up deciding a real architecture question rather than just being a naming nitpick.

CI: does the code work, before anyone merges it

Continuous Integration means running checks automatically on every push — tests, linting, a real build — rather than trusting that whoever's committing remembered to run everything locally first. For the status page, that's npm test on both the client and the proxy, linting, and a real production-style build. For the Ansible side, it's ansible-lint against every playbook.

The thing that makes CI genuinely easy to add: none of it needs real infrastructure. Checking out a copy of the repo and running tests against it happens entirely inside whatever machine GitHub hands the workflow — no credentials, no network path into anything private, no secrets stored anywhere. Safe by construction, not just carefully configured to be safe.

CD: does the code actually get deployed, automatically

Continuous Deployment is the part people usually picture when they hear "CI/CD" — merge to main, and the real thing updates itself, no one has to SSH in and run a playbook by hand. That's a completely different problem than CI, and for this project specifically, a much bigger one.

GitHub's hosted runners execute in GitHub's own cloud. They have no path into a private LAN sitting behind a home router and a Cloudflare tunnel — and the tunnel is outbound-only by design, the same decision that keeps every port on this homelab closed to the internet. Nothing initiates an inbound connection from GitHub's cloud to the capstone VM. A standard "deploy on merge" workflow just can't run on a hosted runner here, full stop — not a configuration problem to solve, the same "no open ports" decision holding firm against a new tool that assumes otherwise.

What actually shipped

CI, fully — both repos, real checks, required before anything merges. CD stayed explicitly undecided, not skipped by accident. Three real options exist (a self-hosted runner on the Ansible control node, a tunneled webhook behind the same Cloudflare Access setup the admin page already uses, or just keeping deploys manual with CI as a pre-check) — and the two automated ones both mean giving something outside the LAN a real way to trigger code execution inside it. That's not a decision to make casually or by default; it's the kind of call that should follow a real threat-model pass, not precede one.

The bug CI found on its first real run

The very first workflow run failed immediately — working-directory: client pointed at a folder that didn't actually exist. Every scope doc written for this project, every "monorepo structure" diagram, described client/ and proxy/ as sibling folders. The real repo didn't match — proxy/ genuinely was nested, but the client app had been sitting at the repo root the entire time, silently wrong in every document describing it, never caught because nothing had ever actually executed against those exact paths before a real CI workflow tried. That's most of the actual value of automated checks, in one small example — not catching a bug in the application logic, catching a structural assumption that had been quietly false the whole time.
