April 10, 2026 Homelab Learning

Network Segmentation — VLANs in the Homelab

Today I implemented VLAN segmentation in the homelab. It's one of those topics that comes up constantly in networking conversations — on certification exams, in job descriptions, in enterprise architecture discussions. I've understood the concept for a while. Now I've actually built it.

What a VLAN actually is

A Virtual LAN is a way to divide a single physical network into multiple logically separate networks. Devices on different VLANs can share the same physical switch and cabling but can't talk to each other directly — traffic between VLANs has to go through a router, where firewall rules control what's allowed.

The practical value is isolation. A device on your IoT network can't reach your servers even if they're plugged into the same switch. A guest WiFi network can reach the internet but not your NAS. A lab environment can be completely separated from production. You get the physical simplicity of one network with the security boundaries of many.

The physical setup

The homelab already had an unused network port on the router VM and an 8-port managed switch that had been waiting for exactly this purpose. Managed switches are what make VLANs possible at the physical layer — they understand VLAN tags and can route traffic to the right logical network based on which port a device is plugged into.

The switch connects to the router on one port — the trunk port. A trunk port carries traffic for multiple VLANs simultaneously, with each frame tagged to identify which VLAN it belongs to. The router receives tagged frames, strips the tags, and routes the traffic through the appropriate virtual interface.

Tagged vs untagged — where it gets interesting

This distinction tripped me up initially. Tagged traffic carries a VLAN identifier in the frame header. Untagged traffic has no tag — it belongs to whatever VLAN the switch port is configured to assign by default, called the native VLAN or PVID.

Access ports — where end devices plug in — send and receive untagged traffic. The device doesn't need to know anything about VLANs. It just sends frames and the switch handles the tagging. Trunk ports between switches and routers carry tagged traffic so both sides know which VLAN each frame belongs to.

A device doesn't need to be VLAN-aware to be on a VLAN. The switch handles the segmentation transparently. That's what makes it powerful.

The OPNsense configuration

On the router side, each VLAN gets its own virtual interface with its own subnet, its own DHCP server, and its own firewall rules. VLAN 20 — the isolation network — sits on a separate subnet from the main network. The firewall has two rules: block traffic destined for the main network, allow everything else. Order matters — the block rule has to come first or the allow-all rule catches it before the block can fire.

Testing the isolation

A spare machine plugged into the VLAN 20 port on the switch received an IP address on the isolated subnet automatically via DHCP — no configuration on the machine itself. Internet access worked. Attempting to ping devices on the main network failed as expected. The firewall rule was working.

That test result — internet works, main LAN unreachable — is exactly what proper network segmentation looks like. A device on that port gets connectivity but no visibility into the rest of the infrastructure.

Why this matters beyond the homelab

VLANs are foundational to enterprise networking. Every organization of any size uses them — separating corporate devices from guest WiFi, isolating servers from workstations, segmenting IoT devices from sensitive data. The specific implementation varies but the concepts are identical to what I built today.

Being able to say I've configured VLAN segmentation on a managed switch with firewall-enforced inter-VLAN routing is meaningfully different from being able to describe it from a textbook. The conversation I have coming up with a network engineering team feels a little more grounded now than it did yesterday.

What's next for the network

The current setup has one isolated VLAN and the main network. The natural expansion is adding more VLANs for different purposes — a dedicated management VLAN for infrastructure devices, potentially a guest network, IoT devices as they get added. The trunk port is already configured to carry additional VLANs — adding a new one is additive, not a rebuild.

There's also a cleaner topology to work toward where the trunk port carries the main network as the native untagged VLAN, eliminating the need for a separate management uplink on the switch. That's a future configuration once I'm more comfortable with how OPNsense handles bridged interfaces. For now the working segmentation is the win.
