March 28, 2026 Homelab

Real Backups, Finally

I've had automated Proxmox snapshots running for a while — weekly, stored locally on each node. They've saved me at least once already when a firewall misconfiguration broke my router's web interface. But local snapshots stored on the same machine they're backing up aren't really backups. They're convenience copies. If the node dies, the snapshot dies with it.

Tonight I deployed Proxmox Backup Server and that problem is solved.

What Proxmox Backup Server actually is

PBS is a dedicated backup solution built by the same team that makes Proxmox VE. It runs as a separate VM, exposes a datastore that your Proxmox nodes can target, and handles deduplication, compression, and retention policies automatically. The key difference from a simple snapshot is that backups go to a separate machine — in my case, a VM on a different node than the things being backed up.

A backup on the same machine as the original is not a backup. It's a duplicate. The distinction matters when hardware fails.

The setup

PBS runs as a VM on my second cluster node with 2 cores, 4GB RAM, and a 32GB OS disk. The actual backup storage is a separate 1.8TB virtual disk attached to the same VM. Separating OS and data storage is good practice — if PBS itself ever needs to be rebuilt, the datastore disk survives independently.

The installer is straightforward — same Proxmox-style interface, static IP, root password, done. The web UI runs on port 8007 and looks nearly identical to the Proxmox VE interface. Once the datastore disk was initialized with GPT and formatted as ext4, PBS picked it up immediately.

Connecting the nodes

Each Proxmox node needs PBS added as a storage target. The process is the same on all four — Datacenter → Storage → Add → Proxmox Backup Server. You provide the PBS IP, credentials, datastore name, and a fingerprint that verifies you're talking to the right server. The fingerprint requirement is a nice security detail — it prevents a misconfigured node from accidentally sending backups somewhere else.

Deduplication in practice

The first full backup of all four nodes ran in under a minute and used 3.33GB on the datastore. That number sounds implausibly small until you understand how deduplication works — PBS breaks backup data into chunks and only stores unique chunks. If two VMs share a base Debian install, those shared chunks are stored once. Every subsequent backup only stores what actually changed since the last one.

For a homelab running similar Debian-based containers across multiple nodes, deduplication is extremely effective. The 3.33GB figure will grow as configurations diverge, but it will always be significantly smaller than storing full snapshots of everything.

Retention policy

The backup job is scheduled to run nightly at 2am with a retention policy of 3 most recent, 7 daily, and 4 weekly backups. PBS prunes automatically after each run — old backups outside the retention window are removed and the freed space is reclaimed. No manual cleanup required.

This is the kind of thing that sounds boring until you need to restore something from three weeks ago and the backup actually exists. The boring infrastructure is the important infrastructure.

What's next for backups

The 1TB SATA drive on the same node is still unused — a natural candidate for a second PBS datastore or offsite sync when a NAS gets added to the lab. The longer term goal is a dedicated NAS with TrueNAS providing a third copy of critical data. Two copies on separate nodes plus one on dedicated storage is a reasonable homelab backup posture.

For now, nightly automated backups across all four nodes stored on a dedicated VM with deduplication and automatic retention is a significant improvement over where things were this morning.
