August 18, 2026 Homelab Learning

The Isolated Node That Had No Backup

Dega — the sixth Proxmox node, standalone, sitting on its own isolated VLAN specifically so a lab-tier host can't reach anything on the main network it shouldn't — hosts the capstone status page. It's genuinely the most important single machine in the whole homelab right now, given what's riding on it. It also had zero backup coverage. Not degraded, not stale — none at all, and had never had any, since the day it was stood up on VLAN 20.

How isolation quietly became a blind spot

The isolation itself isn't the mistake — it's working exactly as designed. Dega can't reach the main LAN, and the main LAN can't reach Dega, except through a small number of deliberately scoped exceptions already carved out for the capstone app's own outbound calls. Proxmox Backup Server just never got one of those exceptions. It wasn't a decision anyone made on purpose — it was a gap that never surfaced, because nothing about daily operation ever asked the question "does this specific node have a real backup." The other five nodes all route through PBS's staged nightly job without anyone thinking about it. Dega quietly never joined that list.

An isolation boundary built for a good reason doesn't automatically come with a checklist of everything that now has to be re-threaded through it on purpose. Backup coverage was one of those threads, and it stayed missing for months simply because nothing forced the question.

What actually surfaced it: planning an unrelated hardware upgrade — swapping Dega's NVMe for more capacity — and asking what the safe recovery path looked like if something went wrong mid-swap. The honest answer was "there isn't one." That's not a great place to discover a gap from, but it's a far better one than discovering it after a bad clone.

A firewall rule the isolation deserved, not a subnet-wide hole

Fixing it meant one narrow OPNsense rule — Dega's specific IP, to PBS's specific IP, on PBS's one real port, nothing broader. The isolation boundary already has a handful of rules shaped exactly this way for the capstone app itself, so this was matching an existing pattern rather than inventing a new one. The alternative — opening the whole VLAN to the whole main subnet just to make one backup job work — would have quietly undone most of the reason the isolation exists in the first place.

The actual PBS registration hit one real snag worth naming: the first attempt used the root account's password and failed with a vague "error fetching datastores" message from Proxmox's own UI. Tailing PBS's own service log during a retry — rather than guessing from the dialog box — showed the real rejection reason immediately. The fix was switching to an existing API token instead of the root password. Querying the actual source instead of trusting a relayed error message answered in under a minute what guessing could have burned twenty on.

Verifying from the right side

A backup job reporting success in its own UI isn't proof anything backup-shaped actually exists — it's proof the job ran. The real confirmation came from checking PBS's own datastore view directly and seeing a genuine new backup group appear for the capstone VM. Trusting a job's own "success" message without checking the destination is the same shape of mistake as trusting a smoke test that only confirms a process ran, not that it did anything real — a pattern this project keeps running into in different disguises.

Where this leaves the hardware upgrade

The NVMe swap that prompted all of this hasn't happened yet — it was deliberately sequenced after backup coverage existed, not before. Getting the precondition right first, even though it delayed the thing that was actually planned, is the same discipline as everything else in this project: confirm the safety net exists before doing the thing that might need it, not after.
