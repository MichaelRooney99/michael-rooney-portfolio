Two Hours to Spare

The wildcard cert for *.michaelrooney.dev was set to expire at 2:17 AM. I noticed with about a day of runway left, tried to renew it through NPM the normal way, and got nothing but a generic "Internal Error." No detail, no hint. What followed was an hour of reasonably chasing the wrong thing before the actual log told me what was really going on — and it had nothing to do with certificates at all.

The obvious suspect

This cert renews via a DNS-01 challenge through Cloudflare, which means the first thing worth checking is always the API token — permissions, scope, whether it's stale. That's exactly where I started. Checked the token's permission type, confirmed it was Zone.DNS:Edit and not the easy-to-mistake Zone.Zone:Edit, confirmed it was scoped to the right zone, regenerated it as a precaution, dropped the new one into NPM. Still failed. Same generic error.

At that point the reasonable move was to stop guessing and go read the actual log instead of continuing to reason about NPM's UI from the outside.

What the log actually said

NPM runs Certbot inside its own LXC, and the real output lives at /data/logs/letsencrypt.log on that container — not anywhere NPM's UI surfaces directly. The traceback wasn't subtle once I was looking at it: 

socket.gaierror: [Errno -3] Temporary failure in name resolution
Failed to resolve 'acme-v02.api.letsencrypt.org'

Certbot never got far enough to even attempt the Cloudflare challenge. It couldn't resolve Let's Encrypt's own API endpoint. Every minute I'd spent on the token was chasing a step the process never reached.

A generic "Internal Error" from a wrapper UI tells you almost nothing about where in the process something actually broke. The instinct to reason from the most likely cause — the Cloudflare token, in this case — isn't wrong, but it's still a theory. The log is the test. I should have pulled it first and saved the hour.

Chasing DNS resolution to its actual source

cat /etc/resolv.conf on the NPM LXC explained everything: 

# --- BEGIN PVE ---
search taild13874.ts.net
nameserver 100.100.100.100
nameserver fd7a:115c:a1e0::53
# --- END PVE ---

The LXC's DNS was pointed entirely at Tailscale's MagicDNS resolver — 100.100.100.100 — instead of OPNsense and Unbound at 10.10.10.1. Nothing about certificates, tokens, or Cloudflare was ever the problem. The container simply couldn't resolve any external hostname, Let's Encrypt included.

The # --- BEGIN PVE --- marker is the tell — that block is injected automatically by Proxmox based on the LXC's DNS Domain setting in the Datacenter UI, not something that lives durably inside the container itself. Editing resolv.conf by hand fixes the symptom for exactly as long as the container stays up. The actual setting lives one layer up, at the Proxmox host level.

Fix now, fix for real

With expiry a couple hours out, the immediate move was the manual one — overwrite resolv.conf with nameserver 10.10.10.1 and retry the cert immediately. It worked cleanly: DNS resolved, the Cloudflare DNS-01 challenge completed, a new wildcard cert issued with time to spare.

That alone wasn't enough to actually close this out, though. A manual edit to a file that Proxmox regenerates on every container start is a fix with an expiration date of its own — next reboot, same failure, probably discovered at a worse time than this one. The real fix was in Proxmox: Datacenter → the NPM LXC → DNS Domain, nameserver corrected to 10.10.10.1 at the source Proxmox actually reads from.

The manual fix and the real fix aren't the same thing, and it's worth being honest with yourself about which one you've actually done. Editing a generated file buys time. Fixing the thing that generates it is what makes the problem stay fixed.

Rebuilding rather than renewing

Rather than keep fighting the existing cert's renewal state once DNS was working again, I issued a fresh certificate outright — same domains, ECDSA P-256, clean DNS-01 validation against the newly-scoped Cloudflare token. Kept the old cert alive and in place while migrating every proxy host over to the new one individually — Grafana, Vaultwarden, Zabbix, Homepage, Portainer, Prometheus, and the rest — confirming each one loaded correctly before moving to the next. Only deleted the old cert once nothing referenced it anymore.

That order matters more than it sounds like it should. If the new cert had turned out to have its own problem, the old one — expiring but still valid in the moment — would have kept everything online while I sorted it out. Migrating everything at once and deleting the old cert immediately would have traded a slow, controlled process for an all-or-nothing bet.

What actually happened here

No part of this was a certificate problem. It was a DNS problem wearing a certificate problem's clothes, and the token investigation — reasonable as a first theory — turned out to be a detour because I hadn't looked at the actual evidence yet. Somewhere along the way this LXC's Proxmox-level DNS setting got pointed at Tailscale's resolver instead of the LAN, probably during the Tailscale install itself, and it sat unnoticed because nothing failed until the one moment a fully-qualified external hostname actually needed resolving.

That's a familiar shape from the Network+ troubleshooting material — form a theory, test it, and when it's wrong, go get better evidence instead of forming a second theory from the same vantage point. The log was sitting right there the entire time. It just took a wrong turn through Cloudflare's dashboard to remember to go read it.
