The Failure That Wasn't About Rack Planner At All

A new CI workflow's first real run threw 17 violations. The instinct, coming off a session that had just added three new playbooks, was to assume the new stuff broke it. Fifteen of those violations turned out to be the exact same failure, repeated once per playbook in the repo — capstone's included — with nothing to do with anything added for Rack Planner at all.

Two real fixes, buried in fifteen identical ones

The workflow was ansible-lint, added alongside the CI/CD scope doc as the cheapest real piece of the deployment- safety doc's Layer 1 — static analysis, no live host, supposedly no credentials needed. Its first run produced a wall of output: internal-error on audit.yml, capstone_provision.yml, node_exporter.yml, zabbix_agent.yml, every playbook in the repository — alongside two genuine yaml[line-length] violations on inventory/group_vars/all/secrets.yml, both Cloudflare tunnel tokens running past the 160-character line limit by nature of being long base64 JWTs. Those two were the real, fixable part — a targeted # noqa: yaml[line-length] on each line, not a reflow, since folding a quoted YAML value across lines inserts a space at the break and would have silently corrupted the token.

The other fifteen were one root cause wearing fifteen costumes: The vault password file /home/runner/.vault_pass was not found. ansible.cfg sets vault_password_file = ~/.vault_pass globally, and inventory/group_vars/all/secrets.yml loads for every playbook automatically — it's under the all group. The runner had no vault password, so Ansible failed trying to decrypt a file it needed just to load inventory, before ansible-lint ever got to look at any playbook's actual content.

"Why would it fail if we're doing the same as capstone?"

That question was the actual turning point, not the fix itself. The assumption going in was that something about the new playbooks — the LXC bootstrap, the deploy rollback logic — differed from capstone's established pattern in some way that broke CI. Looking again at the full output instead of just the Rack Planner lines in it: capstone_provision.yml and capstone_deploy.yml show the identical failure. Every playbook does. The likely explanation was that this workflow had simply never successfully gotten past the vault- loading step before — new workflow, first run that actually exercised a playbook path touching vault-encrypted vars, and the gap had been sitting there the whole time. Nothing about Rack Planner triggered it; Rack Planner just happened to be what got run against it first.

A credential is not automatically the thing you're avoiding

Fixing it meant reversing the workflow's own stated design goal — its header comment said "no credentials needed" in so many words. Two real paths existed: add the vault password as a GitHub Actions secret and accept the workflow is no longer literally credential-free, or restructure the lint job to avoid vault decryption entirely and keep that property at the cost of losing real syntax-check coverage.

The deciding question was what kind of credential the original comment was actually protecting against. Almost certainly an SSH key or a Proxmox API token — something that gives a GitHub-hosted runner an actual path into the real network. A vault password isn't that. It only unlocks values already committed to the repo; there's no lateral step from "decrypted the vault" to "touched Dega" from a sandboxed runner with no route to the LAN at all. Different risk category, even though both technically qualify as "a credential." Went with the secret — same call already made for capstone's own CI months back, just applied consistently to a second repo instead of left as a one-off exception.

Comments that stopped being true

The old workflow file's comments described a capstone-only, credential-free pipeline that no longer existed the moment the fix landed — same kind of drift as yesterday's stale doc gaps, just at the CI-config layer instead of a runbook. Rewrote the header to state plainly that this workflow now covers every playbook in the repo, not just capstone's, and that it requires ANSIBLE_VAULT_PASSWORD for a documented, deliberate reason rather than leaving a claim standing that a two-line diff had already made false. Added chmod 600 right after writing the password to the runner's filesystem too — low real risk on an ephemeral runner, but cheap insurance, and matching the same instinct that added no_log: true to the cloudflared token task a day earlier.

The fix unmasked what it had been hiding

Landing the vault secret was supposed to be the end of it. The next CI run instead threw 10 fresh, genuine violations across six files that had never appeared before — nut_master.yml, nut_slaves.yml, omada_controller_provision.yml, update.yml, zabbix_agent.yml, zabbix_host_registration.yml. None of it was new breakage. Every one of those files had been sitting there, unlinted, since before this workflow existed — the vault failure hadn't just blocked CI, it had been quietly standing in front of real content-level checks for the entire fleet the whole time, on every single run. Fixing the root cause didn't finish the job; it was what finally let the job start.

A linter bug, isolated the hard way

node_exporter.yml threw jinja[invalid]: 'in <string>' requires string as left operand, not UndefinedMarker on a version-comparison check that had been running correctly in production for weeks. The instinct to just silence it with a noqa comment didn't sit right — better to know whether it was a real bug or a linter limitation before deciding how to handle it, same as always. Reproducing it locally meant building out eight throwaway test playbooks, one variable at a time: does a plain group_vars variable resolve on its own? Yes. Does the exact same variable work fine as the right operand of in? Also yes. Only when a group_vars- sourced variable sits as the left operand of in/not in does ansible-lint's static type-checker lose track of it and report it as undefined — confirmed by swapping the operand order on the identical expression and watching the error disappear. A real, narrow bug in the linter's own template validation, not the playbook.

The actual fix avoided the broken code path entirely rather than suppressing it: x not in y and y.find(x) == -1 mean the same thing, and .find() doesn't trip the bug. Same behavior, same runtime result, just phrased in a way ansible-lint's parser can actually follow.

The same bug, copied forward

capstone_provision.yml had the identical curl | sh Docker-install pattern already fixed in Rack Planner's own provisioning playbook two sessions back — unsurprising once it clicked that Rack Planner's playbooks were deliberately built by mirroring capstone's. omada_controller_provision.yml — the file Rack Planner's own LXC bootstrap had been mirrored from — carried eight identical no-changed-when gaps and the same Docker-install issue, for the same reason: a pattern gets copied forward, bugs included, until something forces a real look at the original. capstone_deploy.yml's tunnel-status check had the same raw systemctl is-active call already replaced with the systemd module elsewhere — swapping it here meant updating a downstream .stdout reference to .status.ActiveState too, verified against ansible-doc directly rather than assumed, since that's a real behavior change riding along with a lint fix, not just a rename.

A missing file wasn't a missing bug

One file stalled the pass outright: nut_slaves.yml as mounted locally turned out to be a three-line group_vars file, not the 107-line playbook CI was actually complaining about — a straight filename collision. Rather than guess at fixing a file that might not even be the right one, that file got set aside and flagged explicitly until the real playbook could be uploaded under its own name. Once it was, the actual issue was exactly what the error said: a genuinely missing trailing newline, one line past the real end of a 106-line file. No mystery once the right file was actually in hand — the only risk had been editing blind.

Two package-latest calls that were deliberate, not sloppy

Not every violation deserved a fix that changed behavior. zabbix_agent.yml installs zabbix-agent2 with state: latest on purpose — the task exists specifically to track the Zabbix server's version, not to pin to one, so pinning it to satisfy package-latest would have quietly broken what the task is actually for. Suppressed with a noqa and a comment explaining why, same treatment as a long repo URL two lines up that can't be safely reflowed without risking a broken package source. A suppression with a stated reason is a different thing than silence — the next person reading either line knows exactly why the linter's being overridden instead of wondering if it was missed.

Where the password actually lives now

One real question worth settling explicitly: whether the vault password itself belongs inside secrets.yml for safe keeping. It doesn't, and the reason is structural, not just cautious — the vault password is what decrypts that file, so storing it inside the file it decrypts is circular by construction, and storing it there unencrypted would put a master key in plaintext inside a git-tracked file, readable from history forever even after a later commit removes it. It only belongs in places genuinely outside the repo: ~/.vault_pass on the control node, the GitHub Actions secret, and now a copy in Vaultwarden as durable backup — so losing the control node's disk stops being an unrecoverable loss of every secret in the vault, and becomes an inconvenience instead.

The last mile

CI passed clean after all of that, with exactly one leftover note: actions/checkout@v4 and actions/setup-python@v5 both still target Node.js 20 internally, which GitHub is deprecating on its runners. Nothing broken yet — both actions were simply being force-run on Node 24 in the meantime — but worth bumping to @v5/@v6 the next time this workflow file was already open, rather than a special trip back in for a warning with no real urgency behind it. Low-stakes, compared to everything before it — which was itself the point of the whole session: most of what looked urgent at each step turned out to be either already broken somewhere upstream, or not actually urgent at all once looked at directly instead of assumed.
