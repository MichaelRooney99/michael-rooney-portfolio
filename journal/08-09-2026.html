A Fixture Is Just Test Data With a Job

"Fixture-based parity check" had been sitting in a scope doc since early August, written down as the fix for a real problem and never actually built. Finally building it made something click that I hadn't really understood before — a fixture isn't a special kind of test. It's just data, doing a specific job that regular tests don't.

The problem it exists to solve

The status page has one small function — deriveOverallStatus — that decides the overall health banner: outage beats degraded beats "everything's fine," anything else falls back to unknown. Simple logic. The catch is that it needs to exist in two places that can't share code directly — the browser, and the Express proxy behind it — because the proxy has no way to import from the client's bundle. So there are two separate, hand-written copies of the same three-line decision, living in different files, in different packages.

That's exactly the situation that already caused a real bug in this project once — a different pair of duplicated logic drifted apart silently (one copy checked for a Prometheus job named nut_exporter, the other checked for nut) and nobody noticed until it showed up wrong in production. Two copies of the same idea, no way to know if they ever stop agreeing.

What a fixture actually is

Not a mock. Not a stub. Not a testing framework feature at all, really — just a plain file of example inputs and their correct answers. In this case, a JSON file sitting at the repo root:

{ "statuses": ["operational", "outage"], "expected": "outage" }

One file, sitting outside both packages so it isn't "owned" by either one. Both the client's test suite and the proxy's read the exact same file and check that their own local copy of the logic still produces the fixture's expected answer. Not similar tests written twice by hand — the literal same input/output pairs, checked independently.

Why this beats "just write more tests"

Two test files that happen to cover the same logic, written separately, can drift the exact same way the logic itself drifted — someone updates one copy's test cases and forgets the other, and now both suites are green while quietly testing two different definitions of "correct." A shared fixture removes that possibility structurally. There's only one definition of what the right answer is for a given input, in one file, and if either copy of the actual logic stops matching it, that suite fails — immediately, not eventually, not "whenever someone happens to compare them side by side."

The part that surprised me

Writing the fixture file itself took ten minutes. Getting it to actually load in the client's test file took longer than expected — not because the concept was hard, but because reading a file off disk works differently depending on how a package is built. The proxy runs as plain CommonJS, where __dirname just exists. The client builds through Vite as ESM, which has no __dirname at all — the real equivalent is import.meta.url, and getting there meant actually understanding why the two packages needed different code to do the identical job of "find this file relative to me," not just copy-pasting until the red squiggle went away.
