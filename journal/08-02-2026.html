The Shortcut Everyone Already Knows How to Use

Added a command palette to the status page this week — Cmd/Ctrl+K or /, type to search, arrow keys to move, Enter to jump. The appeal isn't novelty — it's that most people who'd ever use one already know exactly how, because GitHub, Linear, Notion, Slack, and a dozen other tools all settled on the same shortcut years ago. Building your own doesn't need a library. It's three genuinely separate small problems that happen to look like one feature, and each one has a short, specific answer.

Problem one: catching the keypress without breaking everything else

The naive version — a global keydown listener checking for Cmd/Ctrl+K or / — works fine until someone's typing in an actual text field elsewhere on the page and types a literal slash. The listener needs a guard: check what the event actually fired on, and skip / specifically (not the modifier shortcut, which never collides with typing) if focus is inside an input, textarea, or contenteditable element. 

function handleKeyDown(event) {
  const target = event.target
  const isTypingTarget =
    target instanceof HTMLInputElement ||
    target instanceof HTMLTextAreaElement ||
    target?.isContentEditable

  const isCmdK = (event.metaKey || event.ctrlKey) && event.key.toLowerCase() === 'k'
  const isSlash = event.key === '/' && !isTypingTarget

  if (isCmdK || isSlash) {
    event.preventDefault()
    openPalette()
  }
}

Worth writing this guard even on a page with zero text inputs today. It costs nothing, and it's exactly the kind of thing that's invisible until the day a form gets added and / silently stops being usable inside it.

Problem two: a flat list that filters and navigates by keyboard

The palette itself is a search box plus a list, and the list needs three behaviors: filter as you type, move a highlighted row with the arrow keys, and activate whatever's highlighted on Enter. None of this needs a state machine — three pieces of useState cover it: the query string, the highlighted index, and the (memoized) filtered results. 

const [query, setQuery] = useState('')
const [activeIndex, setActiveIndex] = useState(0)

const filtered = useMemo(() => {
  const q = query.trim().toLowerCase()
  if (!q) return allItems
  return allItems.filter(item => item.label.toLowerCase().includes(q))
}, [allItems, query])

function handleKeyDown(event) {
  if (event.key === 'ArrowDown') {
    event.preventDefault()
    setActiveIndex(i => Math.min(i + 1, filtered.length - 1))
  }
  if (event.key === 'ArrowUp') {
    event.preventDefault()
    setActiveIndex(i => Math.max(i - 1, 0))
  }
  if (event.key === 'Enter') {
    event.preventDefault()
    runItem(filtered[activeIndex])
  }
  if (event.key === 'Escape') onClose()
}

If your palette searches more than one kind of thing — my version searches services, categories, and incidents in one project — resist the urge to build three separate lists with three separate selected-indexes. Flatten everything into one array of {'{'} type, label, action {'}'} items up front, tag each one with a small type badge in the UI if you want the visual grouping, and let the arrow keys move through one combined list. Three synchronized selection states is a genuinely worse problem than one flat array.

Problem three: focus has to land somewhere on open

A modal that opens without moving keyboard focus into it is a real accessibility miss — a keyboard or screen-reader user's focus stays wherever it was, silently, behind an overlay they may not even know appeared. Fix is one line, in a mount-only effect: 

const inputRef = useRef(null)

useEffect(() => {
  inputRef.current?.focus()
}, [])

Pair that with role="dialog", aria-modal="true", and a label on the container, plus role="listbox"/role="option" on the results — cheap to add, and it's the difference between a palette that works for everyone and one that only works for people using a mouse.

The bug you'll probably also hit

Here's the one that actually cost time. The obvious way to reset the highlighted row whenever the search query changes is a useEffect watching query, calling setActiveIndex(0) inside it. If your project has the newer eslint-plugin-react-hooks rules enabled, react-hooks/set-state-in-effect will flag that immediately. 

// Flagged: calling setState synchronously inside an effect
useEffect(() => {
  setActiveIndex(0)
}, [query])

The rule's reasoning: an effect that calls setState synchronously causes React to commit once, run the effect, then commit again — a cascading extra render for something that didn't need a render cycle in between at all. React's own docs describe the correct version as adjusting state during render: track the previous value of whatever you're watching in a piece of state, and when it differs from the current value, call setState directly in the render body — not inside useEffect — the moment they diverge. 

const [activeIndex, setActiveIndex] = useState(0)
const [prevQuery, setPrevQuery] = useState(query)

if (query !== prevQuery) {
  setPrevQuery(query)
  setActiveIndex(0)
}

It reads strangely the first time — calling setState outside any hook, right in the middle of a component function — but it's an officially sanctioned pattern specifically for this shape of problem: state syncing to a prop or another piece of state, not state reacting to something outside React entirely (the system clock, window size, localStorage — those are what useEffect or useSyncExternalStore are actually for). Worth keeping the distinction straight, because the fix looks similar on the surface and is genuinely a different tool for a different job.
