What vi.mock Actually Does, and Why Order Doesn't Matter the Way It Looks Like It Should

Testing one function that depends on five other functions doing real network requests meant needing a way to control exactly what those five functions returned, without actually calling out to anything real. Vitest's answer to that is vi — its own built-in mocking toolkit, the direct equivalent of what people coming from Jest would know as the global jest object. The part worth actually understanding, rather than just copying the pattern, is that one specific piece of it — vi.mock — doesn't run when it looks like it runs, and that's not a minor detail. It's the whole reason the pattern works at all.

What a mock actually is

A mock function, created with vi.fn(), is a fake stand-in for a real one — it remembers how it was called, and it returns whatever the test tells it to return instead of doing real work. That much is intuitive. vi.mock() does the same idea at the level of an entire module instead of a single function: point it at an import path, and every function that module normally exports gets replaced with a mock version for the whole test file. 

vi.mock('./proxmox', () => ({ fetchProxmoxNodeStatus: vi.fn() }))

Written like that, it reads as an ordinary function call — something that runs top to bottom, in the order it's written, same as everything else in JavaScript. That reading is wrong, and the wrongness is exactly the thing worth understanding.

Hoisting: why the "wrong" order actually works

A real test file has its imports at the very top, before any vi.mock() calls appear on the page. If vi.mock genuinely ran in written order, it would always be too late — the real module would already be imported and already in use by the time the mock call executed a few lines later. That's not how it behaves in practice, and the reason is that Vitest doesn't just run the file as-written. It rewrites it first. Every vi.mock() call gets hoisted — physically moved, during a compile step, to the very top of the file, above every import statement — before any of it actually runs. By the time a real import statement executes, the module it's pointing at has already been swapped out.

This is the single most important thing to internalize about vi.mock: it isn't a runtime instruction telling JavaScript what to do next. It's closer to a build-time instruction telling the test runner what to construct before anything runs at all. Writing it in a spot that reads naturally — right under the imports it affects — works specifically because the tool doesn't care where it's written, only that it's present somewhere in the file.

vi.mocked: making TypeScript agree with reality

Once a module's been mocked, the imported function still has its real type as far as TypeScript is concerned — an async function that returns a real promise, with none of the extra methods a mock actually has, like telling it what to resolve or reject with on the next call. vi.mocked() exists purely to bridge that gap — it doesn't change anything about how the mock behaves at runtime, it just tells the type checker "trust me, this is actually a mock," which is what makes autocomplete and type safety work on the mock-specific methods that come next. 

vi.mocked(fetchProxmoxNodeStatus).mockRejectedValue(new Error('proxmox API down'))

Why this was the right tool here specifically

The function under test merges results from four separate data sources, each doing a real fetch, plus a fifth for incidents with its own independent failure handling. Testing it for real would mean either standing up real infrastructure just to run a test suite, or accepting tests that are slow and occasionally flaky depending on network conditions that have nothing to do with whether the actual merging logic is correct. Mocking each dependency means the test can force any combination directly — every source succeeding, one specific source failing while the rest succeed, everything failing at once — and each case runs instantly and identically every time, because nothing real is happening at all. The thing actually being tested is the merging and fallback logic itself, not whether five unrelated services happened to be reachable at the moment the test suite ran.
