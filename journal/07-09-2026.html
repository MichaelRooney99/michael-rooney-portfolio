The Math of a Shutdown Daemon

Brought the sixth node online today. I reused the name dega for it, configured it as a dedicated Docker host, and dropped it cleanly onto the isolated VLAN 20 subnet at 10.10.20.54.

The isolation is deliberate — this node exists to host the capstone status page once it's public via a Cloudflare tunnel, and a public-facing box has no business sitting on the same subnet as Vaultwarden or the NUT server. That reasoning gets its own writeup tomorrow. Today was just getting the node itself into a healthy, fleet-managed state before anything gets deployed on it.

Because dega falls outside the main management range, pulling it into the core Ansible automation was the immediate next step. The baseline tasks completed smoothly—node_exporter compiled and began ticking off metrics directly into the cluster array, and the physical sensor sweeps looked perfectly normal.

Then I ran the NUT client configuration, and the system instantly blew up.

The failure mode was classic systemd noise: nut-monitor.service: Failed with result 'exit-code', immediately hitting a start-limit throttle and flatlining. Peeling back the logs via journalctl revealed the raw math problem buried in my inline deployment template: Fatal error: insufficient power configured! Sum of power values: 0, Minimum value (MINSUPPLIES): 1.

When writing the nut_slaves.yml configuration playbook, I hardcoded a baseline directive: MINSUPPLIES 1. But on a netclient node acting purely as a secondary monitor, the declared power monitoring value for the remote host link is set explicitly to 0. Since 0 is less than 1, the daemon treats the configuration as a logic error and halts execution instantly.

The funny thing about infrastructure management is the quiet liabilities. The other secondary nodes in the cluster—network, shasta, murloc, and pbs—had been reporting healthy for weeks simply because their active run states predated the change, or they hadn't cleanly recycled their processes against the updated template parameters. Had any node experienced an unplanned restart, the monitor would have crashed out exactly like the fresh install.

A playbook applying cleanly doesn't mean the configuration is functionally sound, it just means the syntax was valid. A restarted daemon is the only true test of a configuration file.

I fixed the root problem inside the Ansible logic by dropping the template requirements down to a proper MINSUPPLIES 0 alignment. To ensure the fix held, I pushed the playbook fleet-wide to force a template rewrite and daemon restart across all secondary nodes.

While validating fleet consistency, network hit an apt-cache locking hang. With a 1,700-hour uptime, it hadn't touched its package repositories in months and timed out on the cache refresh. After manually clearing the locks and refreshing the chains, the final audit run cleared completely. A full, unified wall of green across all subnets, with all six nodes tracking their power states perfectly.
