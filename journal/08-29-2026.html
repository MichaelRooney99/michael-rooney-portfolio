Ad-Blocking at the Router With Unbound's DNSBL Engine

Blocking ads at the router instead of in the browser means one policy covers every device on the network — phones, smart-home gadgets, guest devices on VLAN 30 — without installing an extension anywhere. OPNsense already runs Unbound as the network's DNS resolver, and its newer blocklist engine turns that resolver into a DNS-level ad and tracker filter with a single policy, no separate appliance required.

What actually changed in OPNsense's blocklist page

Older guides for this feature describe a checklist of preset feeds under a single "enable blocklists" toggle. The current UI (Services → Unbound DNS → Blocklists, OPNsense 25.7.8+) is a proper table of policy entries instead — each one its own row with a multi-select "Type of DNSBL" field, an optional custom URL field, and its own allowlist, blocklist, wildcard, and source-network scoping. That last part matters: a policy can be scoped to specific source nets, so a VLAN could in principle get a different block policy than the main LAN, or none at all. For a first pass, one policy with source net left blank covers everything — LAN and edge_Lab (VLAN 20) alike.

What's actually in the stack

A single policy can combine multiple DNSBL sources — Unbound dedupes overlap automatically, so stacking lists doesn't double-count matches:

  • EasyList — the base list most browser ad-blockers are built on; ad-serving domains specifically.
  • EasyPrivacy — EasyList's companion, targeting tracking/analytics domains rather than ad servers.
  • AdGuard List — a general-purpose ads/tracking list, similar tier to the StevenBlack hosts list.
  • Abuse.ch – ThreatFox IOC database — malware/botnet command-and-control indicators. Not ad-related, but a reasonable inclusion since the mechanism is identical: block a domain at resolution time.
  • Hagezi Multi NORMAL — a combined ads/tracking/security list, one tier up in aggressiveness from a single-purpose list like EasyList alone.

Five sources sounds redundant, but redundant coverage is cheap here — the cost is a slightly longer initial build when Unbound pulls and merges the feeds, not runtime overhead per query.

Verifying it actually works, not just configured

Same principle that applies everywhere else in this homelab: query the actual source, don't trust the UI saying "Apply" succeeded. OPNsense ships a built-in Tester tab next to Blocklists for exactly this — enter a known ad domain, and it returns the matched policy directly: 

{
  "status": "OK",
  "action": "Block",
  "address": "0.0.0.0",
  "policy": {
    "description": "Ad-Blocker",
    "bl": "custom1"
  }
}

That confirms the list logic is correct, but it's a local simulation inside Unbound — it doesn't prove a real client is actually using this resolver. The second check has to come from an actual device: nslookup ads.google.com pointed at OPNsense's LAN IP, from a machine on the network, confirming the same 0.0.0.0 result outside the tester's sandbox. Both checks passed here — tester and live client agreed.

The one hidden dependency: DHCP

None of this blocks anything for a client that isn't actually querying Unbound. If any DHCP scope hands out a different DNS server — a public resolver, or anything other than OPNsense's own IP — devices on that scope skip the filter entirely, silently, with no error to indicate why ads are still loading. Worth a periodic check on each VLAN's DHCP configuration, not just a one-time confirmation at setup — the same reasoning that applies to VLAN segmentation and firewall-enforced isolation generally: a policy is only as real as the traffic that actually flows through it.

Triage first, disable never

With Hagezi's NORMAL tier in the stack, something eventually breaks — a smart-home integration phoning home to a domain that gets caught, or an app that depends on an analytics endpoint to function rather than just to track. The fix in that case is adding the specific domain to the policy's own Allowlist Domains field, not disabling the blocklist wholesale. Same instinct as the Unbound blocklist documentation recommends — narrow the exception, keep the policy.
