March 16, 2026 Homelab

Fixing What I Broke

Earlier this year I was having persistent issues with my VPN mesh dropping connections. I kept adding Proxmox firewall rules trying to fix it, got frustrated when nothing worked, and eventually just cleared all the rules. Problem solved, right? Not quite.

I didn't touch the setup for a while after that. Today I opened my router's web GUI and found the menu loaded but the entire content area was blank — just a black void where the dashboard should be.

What was actually happening

My router VM loads its UI dynamically — the menu skeleton is static HTML but the dashboard content comes from API calls the browser makes back to the router. When I cleared the Proxmox firewall rules but left the Proxmox firewall enabled, it defaulted to blocking everything. The API calls never returned. Menu loads, content doesn't.

Lesson: clearing firewall rules with the firewall still enabled is not the same as disabling the firewall. It defaults to block, not allow.

The fix

I restored the network node VM from a weekly automated Proxmox snapshot. Took a few minutes, everything came back clean. First thing I did afterward was export the router config and commit it to a private GitHub repo — exactly the kind of thing I should have been doing before making changes, not after things break.

Sorting out the VPN properly

With a working router again I went back to the original problem. The actual fix was straightforward — one inbound firewall rule on the LAN interface of my router, scoped to the VPN container's IP:

  • Protocol: UDP
  • Direction: inbound
  • Destination: VPN container (specific host, not the whole subnet)
  • Port: 41641 (direct peer connections)

The default LAN-to-any rules already covered outbound traffic. I only needed the one inbound rule. After adding it, my desktop machine shows direct connections in the VPN status output. My phone stays on relay through the provider's servers — that's carrier NAT on the cellular side, not something fixable locally.

Exit node vs subnet routing

While troubleshooting I noticed the VPN was breaking my reverse proxy connections and websockets whenever it was active on my desktop. The VPN container was configured as an exit node and my desktop was using it — meaning all traffic, including traffic destined for local services, was routing through the VPN even when I was sitting on the same network.

Exit node routes all internet traffic through your home network. Useful on public WiFi, counterproductive when you're already home. Subnet routing advertises your local network to remote devices so they can reach it from anywhere. Those are two different features and I was conflating them.

Deploying monitoring

With the network sorted I deployed Uptime Kuma as a container on my main cluster node. It's proxied through my reverse proxy with SSL, Gmail SMTP notifications configured, and all nodes and services now have monitors — grouped and color-coded by role.

Everything green within an hour. That's the first time I've had real monitoring on this infrastructure rather than just assuming things are up.

What I'd do differently

  • Commit configs to version control before making changes, not after things break
  • Disable the hypervisor firewall on the network node entirely — the router VM handles actual firewall duties, the extra layer is redundant and caused this whole problem
  • Scope firewall rules to specific container IPs rather than broad network ranges
