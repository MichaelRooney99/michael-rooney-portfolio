The Package That Only Exists as a Symlink

A monorepo doesn't need a dedicated build tool to become real — npm workspaces alone is enough to make three separate packages resolve into each other, share types, and fail in genuinely instructive ways. I wanted hands-on monorepo experience outside of the capstone and RPP, so I picked something small and low-stakes to build it with: a filament cost calculator for leftfootLabs, split into a shared calculation package, an Express API, and (eventually) a React client.

Why a shared package instead of shared folders

The whole point of putting the cost math and its zod validation schema in a dedicated shared package, rather than just writing the calculation twice — once in the API, later again in the client — is closing off silent drift before it can start. Two copies of the same formula are two places a future edit can land in only one of them. That's the same underlying problem a duplicated-logic decision on the capstone came down to: duplication itself isn't the enemy, silent divergence between copies is. A shared package makes divergence structurally harder, not just something to remember to avoid.

A name that has to match exactly

npm init -y inside the shared package's folder defaulted its name to plain shared — which is also a real, existing package name on the public npm registry. That's not just an aesthetic problem. A package's name field is the literal string that ends up in an import statement later, and npm workspaces resolves that name locally instead of hitting the registry — but only when the name is unambiguous. The standard fix is scoping internal packages under your own namespace, @filament-calc/shared, which costs nothing since nothing here gets published, and makes it visually obvious in any import line that a package is internal rather than a registry dependency.

What actually happens on npm install

Running installs from inside a single workspace still lands everything in one root node_modules, not a folder-local one. For real registry dependencies like zod or express, that's just hoisting. For internal packages, npm does something more specific: it creates a symlink — root/node_modules/@filament-calc/shared pointing at packages/shared — which is the actual mechanism that lets import { calculateCost } from '@filament-calc/shared' resolve at all later. One lockfile at the root tracks the whole graph. The -w flag (npm install zod -w @filament-calc/api) doesn't change where anything physically lands — it only changes which package's package.json records the dependency.

CommonJS vs. ESM isn't cosmetic

Every fresh package.json defaults to "type": "commonjs" — Node's historical module system, where require() loads synchronously and file extensions are optional. The alternative, "type": "module", switches Node to real ECMAScript modules: import/export, mandatory .js extensions on relative imports, and no __dirname global. The part worth being precise about: writing import/export syntax in a .ts file is a TypeScript language feature and has nothing to do with this setting — TypeScript compiles that syntax down to whichever target the tsconfig.json module option specifies. The "type" field in package.json is telling Node how to interpret the compiled output, not the source. Get a package's "type" out of sync with what its build actually emits, and the failure shows up as a real, sometimes cryptic ERR_REQUIRE_ESM at runtime — a genuinely common monorepo footgun. All three packages here are set to "type": "module", targeting ESM output throughout.

A file that gets deleted on purpose

JavaScript has no runtime concept of types at all — there's no : number syntax the engine understands. TypeScript's types exist purely to catch mistakes while writing code; once tsc finishes checking that everything lines up, the types have done their job and get stripped from the compiled .js entirely. This is called type erasure, and it's why the shared package's build produces two separate files per module: dist/index.js (plain JS, no type annotations) and dist/index.d.ts — a declaration file that preserves the erased type information separately, entirely for the benefit of whatever imports this package later. Every const or function in a .d.ts file gets prefixed with declare — TypeScript's way of saying "this exists somewhere, trust me, generate no code for it." interface and type entries never get that prefix, since they were never runtime constructs to begin with. This split is what makes cross-package IntelliSense work at all: when the API package later imports from @filament-calc/shared, the editor reads dist/index.d.ts for full autocomplete and type-checking, without ever parsing or executing the actual compiled JS.

Shared package built, compiling clean, exporting a validated calculateCost function with real types attached. Next: wiring an Express API to actually depend on it — which is where the build order turned out to matter a lot more than it looked like it would.
