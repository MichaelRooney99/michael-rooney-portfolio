The Certificate Fix Browsers Couldn't Ship for Me

A certificate authority compromise gets fixed in two very different places. Browsers and operating systems fix it for you, usually before you've heard about it. Any software that ships its own list of trusted certificates waits until someone upgrades it by hand. The Cloudflare Tunnels that publish this site and the Rack Planner fall into the second group, which is why a security email from Cloudflare turned into an afternoon of upgrades.

What actually happened

On October 19, 2026, Cloudflare found that eight intermediate certificates issued by eMudhra, an Indian certificate authority that sells under the emSign brand, had been generated with weak keys. The private keys could be recovered from the public certificates alone. Anyone holding those keys could sign a certificate for any domain, and every client that trusted the chain would accept it as real. Cloudflare's write-up of the incident covers the timeline. Mozilla pushed a revocation update the same evening, and Chrome and Mozilla are both removing trust in the affected root.

None of that reached cloudflared, the small daemon that holds open the outbound connection between my servers and Cloudflare's edge. It verifies certificates against a trust list compiled into the binary, so a browser update changes nothing for it. Versions before 2026.10.2 still trusted the compromised intermediates.

Why a tunnel is worth patching at all

The tunnel is the only path between the public internet and the services behind it. I wrote about what that path replaces in Publishing Isn't the Same as Protecting: no open inbound ports, no port forwarding on OPNsense, every request arriving through a connection the server dialed out itself. That design only holds if the daemon can tell the real Cloudflare edge from an impostor. A forged certificate that cloudflared accepts breaks exactly that guarantee. Cloudflare found no active exploitation, so this was hygiene rather than an incident, but it is the kind of hygiene that keeps an incident from happening.

A restart is not an upgrade

The step that would have been easiest to get wrong was the container part. Restarting a Docker container brings it back up from the same image it was already running. If the compose file says cloudflare/cloudflared:latest, the local copy of "latest" is whatever was pulled last time, and a restart or even a docker compose up -d keeps using it. The fix only lands after pulling the new image and recreating the container from it: 

docker compose pull cloudflared
docker compose up -d cloudflared
docker exec <container> cloudflared --version

The last line is the part that actually proves the fix. The tunnel's connector list in the Cloudflare dashboard shows the same thing from the other side, with the version each connected instance reports. It's also the quickest way to find an instance you forgot was running.

The general rule: the tag in a compose file names an image, not a version. latest means "whatever this host pulled last," which can be months old. Checking the running binary's version is the only check that tells you what is actually deployed.

The fix you shouldn't reach for

Cloudflare's notice included one warning worth repeating. An upgraded cloudflared will refuse to connect to an HTTPS origin whose certificate chains to one of the bad intermediates. The tempting response to that error is turning on noTLSVerify so the tunnel connects again. That would remove the exact check the upgrade restored. The right fix is replacing the origin's certificate. Before upgrading, the thing to check is which tunnel routes point at an https:// origin at all and where those origin certificates come from.

Why I did it by hand this time

This was a natural Ansible task: pin the image tag in a variable, pull, recreate through a handler, and verify against the daemon's /ready endpoint. I upgraded every instance manually anyway, for the refresher. Walking through each host and each compose file one at a time was a useful reminder of where every tunnel actually lives, including the one on Dega, the isolated VLAN 20 node from Giving the Capstone a Real Home. A playbook would have been faster. The manual pass is the reason I could write one confidently next time.

I also skipped Cloudflare's zero-downtime procedure, which adds a second replica before restarting the first. That procedure exists for production traffic. For a portfolio site and a planning tool, a few seconds of downtime while a container recreates is an acceptable cost, and adding temporary replicas would have been ceremony rather than engineering.

What I'm taking from it

"Keep things updated" is too vague to act on. The useful version is knowing which software trusts the operating system's certificate store and which carries its own, because the second kind is invisible to the update that fixes everything else. Daemons, language runtimes, and container images that bundle their own CA list all belong on that list. The cloudflared update guide covers each install method if you run tunnels too.
