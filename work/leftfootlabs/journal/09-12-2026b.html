The Save Button That Doesn't Block You

Real-time validation went in earlier today, which meant the last real piece of the rack-elevation work was actually saving and sharing a build. Two calls made back when this whole arc first got scoped — before a single line of the elevation UI existed — turned out to shape the final feature directly, rather than staying abstract decisions on a page.

Why the save button doesn't block you

The live validation panel can be sitting there showing real issues, and the Save & Share button still works anyway — it's never disabled based on what the client-side check thinks. That was the actual content of an early call that real-time feedback would be client-side UX and the server would stay the final authority at save time, not a compromise made because gating the button would have been harder to build. Clicking save with visible issues still showing sends the request anyway, and whatever comes back — success, or a real rejection with the server's own reasons — is the actual answer, not a guess enforced a layer too early.

An API with no update endpoint decided the share view for you

A saved layout's share link opens a genuinely read-only view, not a second copy of the interactive builder pointed at existing data. That wasn't a separate design call so much as a consequence already sitting in the API: it has a way to create a layout and a way to read one back, and nothing in between. Making the share view editable would have implied saving changes over the original, which nothing on the backend actually supports — so read-only isn't a restriction added on top, it's just what honestly matches what the API can actually do.

Proving the round trip, not just the pieces

Each function involved — the save call, the fetch call, the error handling — had already passed its own tests. The thing worth actually checking was whether they agree with the real server end to end: a real save against the live backend, a real fetch of that exact layout back, and a real rejected save with two shelves deliberately placed on top of each other, all checked directly against what the code assumes those responses look like rather than trusted from reading the route handlers. All three matched.

A clean type-check and a green test suite say the pieces are each internally sound. Only running the real request against the real server says the pieces actually fit together the way the code assumes they do.

What actually shipped

Shelves, devices, real-time validation, and now save and share — the full rack-elevation arc, backend and frontend both, each piece verified against something real before moving to the next one rather than assumed correct from a passing build.
