The Discharge Test That Turned Into a Real Shutdown

A UPS runtime estimator built from a spec sheet is a guess wearing a number. The Rack Planner's power-budget feature is meant to tell someone whether their layout will actually stay up long enough to matter during an outage, and that only means something if the underlying runtime curve came from a real battery under real load — not a linear estimate extrapolated from a nameplate rating. So building it honestly meant measuring it directly: three load levels, a real UPS, a real six-node cluster actually running on battery, on purpose.

Three levels, one variable at a time

The fleet's six mini PCs are the only load actually available — there's no separate dummy load to plug in for testing. Getting three genuinely different draw levels meant inducing them directly, with CPU stress across a deliberately chosen subset of nodes for each level, then physically cutting mains power to the UPS so the whole load actually ran on battery, not just theoretically. Level one, at the fleet's natural idle draw, went exactly as planned: a clean multi-minute discharge, a deliberate stop well above the low-battery threshold, a full recharge, done.

Where the plan broke

Level two dropped roughly twice as fast as level one — more load, shorter runtime, which is exactly what should happen. What didn't survive contact with that faster rate was the monitoring approach: watching the discharge through pasted log output and reacting after a round of back-and-forth has real latency built into it, and a fast-dropping battery doesn't leave room for that latency. The stop threshold got crossed several readings before anyone caught it. The UPS declared a real low-battery condition and broadcast a real forced-shutdown signal. All six nodes actually halted.

What an unplanned outage actually proved

Watching six machines go dark on purpose was not the plan for the evening. What came back afterward was more useful than expected, though: every node that was configured to restore power automatically after an outage actually did — a real, if accidental, answer to a question that had been sitting open for a while. It also explained something that hadn't made sense before: a past attempt at testing this exact shutdown chain hadn't triggered when it seemed like it should have. Checking the actual configuration afterward turned up why — a documented shutdown threshold that had never actually been pushed to the UPS itself. The real, live threshold and the one every runbook described were two different numbers, and had been for a while.

Doing it right the second time

Level three carried the heaviest load of the three — meaning it would drop faster than level two, not slower, right after level two had just demonstrated exactly how much that matters. The fix wasn't a different threshold. It was watching the discharge live, in real time, and acting on it directly instead of relaying it through a round trip first. It worked. The plug went back in seconds after the threshold was crossed, well clear of an actual shutdown, and the fleet never lost power a second time.

Three real load levels, three real curves, and one real confirmation that the shutdown chain works — gathered in that order specifically because the second one didn't go as planned. A deliberate, controlled test of that same shutdown chain is still on the list, run properly rather than by accident. The actual runtime estimator gets built from this data next, the same way the Rack Planner's kit dimensions got built from a real measured part instead of a spec sheet first.
