The Query That Counted Four Devices as One

The runtime estimator itself checked out clean the moment it went live — every exact-match case reproduced the real logged numbers precisely, on the first real end-to-end test. Every actual problem that turned up afterward was in the plumbing around it, not the estimator's own logic.

A bug that predates tonight, found by the first real test to exercise it

Testing the power-budget endpoint against a layout with four of the same device placed in it returned the wattage and count for exactly one — as if the other three didn't exist. The query behind it looked for devices matching a list of IDs pulled from the layout, but that list had the same ID repeated four times. SQL's matching clause treats a repeated value in that list as redundant, not as four separate things to find — it returns one row per unique match, regardless of how many times a value shows up asking for it. Four placements of one device type had always collapsed down to one, silently, since before tonight touched any of this code.

Nothing about that bug depended on the wattage estimate being new. It was sitting there the whole time, waiting for a test that actually placed the same device more than once — which apparently nothing had, until tonight's end-to-end check did exactly that by accident of picking a realistic test layout.

The fix separates the two questions the original query conflated: which unique devices exist, versus how many times each one was actually placed. Look up every unique device's wattage once, then sum across every real placement in the layout — not across however many distinct IDs happened to appear. Four identical devices now correctly report four times the wattage, and the device count reflects total placements instead of unique types.

A missing chunk that broke the right thing loudly

Hand-keying the updated route file into the real repo skipped an entire section without anyone noticing at the time — including the line exporting the router itself. The failure that produced was about as clear as a missing-export bug gets: Router.use() requires a middleware function but got undefined, pointing at the exact line trying to mount it. A working router sitting right next to the broken one in the same file made the diagnosis fast — one import resolved fine, the other came back undefined, which narrows the search to "what's different about this one file" immediately, rather than a vague failure with no obvious starting point.

A file that existed on disk and nowhere else

A new source directory for the estimator's real discharge data never showed up in git status at all — not modified, not untracked, nothing, despite genuinely existing on disk with real content in it. The repo's .gitignore had a bare data/ pattern meant to keep the actual SQLite database files out of version control. Without a leading slash to anchor it to the repository root, that pattern matches a folder named data anywhere in the tree — including a same-named source directory nested three levels deeper that had nothing to do with database storage at all. Anchoring the pattern to the specific path it was actually meant to cover fixed it without changing what it was supposed to ignore in the first place.

What actually needed catching, in the end

Three real issues, and the estimator's own interpolation logic wasn't one of them. That's not a coincidence so much as what actually testing a feature for real tends to surface — the core logic gets attention up front, gets checked carefully, and turns out fine. The bugs waiting underneath are almost always in the parts nobody was specifically watching: a query written before this feature existed, a paste that skipped a line, a config pattern written for a different purpose entirely. None of them were exotic. All three were only findable by actually running the real thing end to end and checking what came back, rather than reading the code a second time and trusting it looked right.
