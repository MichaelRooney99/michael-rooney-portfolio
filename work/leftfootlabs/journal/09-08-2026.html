A Comment That Described a Fix That Never Shipped

A type mismatch between the Rack Planner's frontend and backend looked, at first glance, like exactly what it appeared to be: the shared Device type was camelCase (uHeight, isKitItem), and the frontend had quietly declared its own separate snake_case version (u_height, is_kit_item) instead of using it. The actual root cause was smaller and more specific than "the types don't match" — the device API route was shipping raw SQLite rows straight to the client with no mapping step at all. The type mismatch wasn't the bug. It was the visible symptom of a route that skipped a step entirely.

What the fix actually needed

A single rowToDevice mapping, used by both the device route and the layout-validation logic, replaced two separate places that had each been quietly doing (or, in the route's case, not doing) their own version of the same conversion. The route now returns the shared camelCase shape directly; the frontend's separate type declaration stays, but now actually matches the real wire format instead of describing the raw database row shape it was never supposed to see.

The comment that was worth reading twice

The shared types file had a header comment claiming the frontend imported it directly, via a workspace reference, instead of hand-declaring its own copy. That was never actually true. Checking why revealed something more interesting than a stale comment: a real cross-package import here would have required the frontend's Docker build to see backend source at image-build time — and each service's build context is scoped to its own folder. The comment wasn't describing an unfinished feature. It was describing an approach that wouldn't have worked as written, on infrastructure that already existed before the comment was ever added. Fixing the actual bug meant correcting the comment to describe what was real, not chasing what it originally promised.

A test that only proved half of it

The first test written against this fix checked the data-access layer directly — real assertions against a real throwaway database, not mocks. It was a genuine improvement: this codebase had no backend tests at all before it. But on review, it only proved the mapping function returned the right shape. It didn't prove the route actually used that mapping correctly, end to end. Closing that gap meant extracting the Express app itself into its own module — separated from the startup script that also seeds the database and binds a real port — specifically so a real HTTP request could be sent through the actual app in a test, with nothing mocked.

The bug that only showed up on the second machine

Every one of these tests passed cleanly the first time. They also passed cleanly a second time, on a different machine, with one exception: both test files failed their cleanup step with a permission error — on Windows only. SQLite keeps its file handle open until something closes it explicitly; deleting an open file works without complaint on Linux, and is refused outright on Windows. The actual test assertions had been correct the entire time. The fix was one line — db.close(), called before attempting to delete the file — but it only exists because the same code ran on two real operating systems instead of one.

The Rack Planner shares its stack deliberately with the capstone status page — same reasoning discussed in the last entry about why this project runs on its own isolated VM instead of a shared LXC. Repetition across two real projects keeps surfacing real, small lessons like this one instead of one clean success story — which has turned out to be more useful than a clean story would have been.
