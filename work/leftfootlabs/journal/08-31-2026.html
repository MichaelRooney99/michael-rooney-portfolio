A Boolean That Was Secretly a String

A YAML conditional can fail silently in a way that has nothing to do with the logic it's expressing — the value it evaluates to can simply be the wrong type, true-looking text instead of an actual boolean, and Ansible will refuse to guess which one you meant. That was one of two real bugs standing up an LXC for leftfootLabs' Rack Planner tool today. The other was a fresh Debian 13 container template that doesn't ship with sudo installed at all — not misconfigured, just genuinely absent.

Same reasoning, different answer

The capstone status page runs on a VM instead of the fleet's usual privileged LXC for one specific reason: it's internet-facing, and a privileged LXC shares the host kernel with Proxmox — a container escape there is functionally a host compromise, no hypervisor boundary in between. Rack Planner is equally internet-facing, tunneled the same way to planner.leftfootlabs.com. Worth being honest that going LXC here is a real departure from that reasoning, not an oversight of it — the mitigating factor is running it unprivileged with only nesting=1 enabled, which gets Docker without the full host-kernel sharing a privileged container would mean. Not equivalent to a VM's isolation. A documented, accepted tradeoff instead of a silent one — the product surface here is a static Compose stack with no accounts yet, a meaningfully smaller blast radius than the capstone's fleet-adjacent adapters even before the container posture is considered at all.

A condition that was true no matter what

The LXC creation playbook needed the same check-then-gate idempotency pattern used everywhere else in this repo — check current state first, only act if it actually needs changing. One of those gates broke on the very first real run: 

[ERROR]: Task failed: Conditional result (True) was derived from
value of type 'str' at '.../rack_planner_lxc_provision.yml:75:13'.
Conditionals must have a boolean result.

The actual cause was almost invisible on a glance: a folded YAML block scalar (when: >) with a stray literal double-quote character wrapping the whole condition. YAML's > folds newlines into spaces but doesn't interpret quote characters specially — so instead of a Jinja boolean expression, Ansible received one long quoted string. A non-empty string is truthy, so the task ran every time regardless of what the actual check found. The fix was deleting two characters. The harder part was noticing the bug wasn't in the logic at all — it was in what type the logic evaluated to. Caught it by actually parsing the file with PyYAML and printing each when clause's real Python value before trusting the fix, rather than just eyeballing the diff a second time.

The directory that was never there

Past that, the ansible user got created inside the container fine — and then granting it passwordless sudo failed outright: 

bash: line 1: /etc/sudoers.d/ansible: No such file or directory

Not a permissions problem. The directory itself didn't exist, because the minimal Debian 13 LXC template doesn't include the sudo package by default — unlike whatever base image the Ansible control node's own LXC was originally built from months ago, where this was apparently never an issue worth writing down. The fix was two extra tasks: check whether sudo's installed (dpkg -s sudo), and if not, apt-get update && apt-get install -y sudo before ever touching /etc/sudoers.d/. Small, but a real reminder that "matches an existing convention" is a claim worth actually checking against the template in use, not assuming forward from a different container built at a different time.

Proving the tunnel, not just trusting the green output

Getting the Cloudflare tunnel talking took a token from a fresh Zero Trust connector, stored in Ansible Vault as its own key — deliberately not reused from the capstone's tunnel, since each connector needs its own. One real gap caught on the way: the task that installs the token as a systemd service didn't have no_log: true on it. That meant if anything downstream had failed, the token itself could have shown up in plaintext in the exact kind of error output this post is built from. Vault protects a file at rest; it does nothing for terminal output. Added the flag before trusting the task with a real token a second time.

A green systemctl status only proves the service started, not that it's actually talking to anything — the real confirmation was Cloudflare's own precheck log, DNS resolution, QUIC connectivity, and API reachability all reporting pass against the real edge. Past that, a deploy playbook (clone, write the env file, docker compose up -d --build, health check, then a smoke test through nginx rather than straight to the backend — proving the whole request path, not just that one process is alive) brought the actual app up. planner.leftfootlabs.com now serves the real device library, seeded with leftfootLabs' own kit dimensions pulled from verified Blender output, not placeholder numbers.

What's still unverified

The deploy playbook's rollback path — the actual revert-and- rebuild logic for a bad deploy — hasn't fired for real yet. Every run so far has either hit the "nothing to roll back to" branch on a first deploy or found nothing new to deploy at all. Same principle as everywhere else in this project: a mechanism that applies cleanly isn't the same claim as a mechanism that's been proven to actually work when it matters. That's the next real test, not the drag-and-place rack elevation UI still waiting behind it.
