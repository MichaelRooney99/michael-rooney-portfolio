A Drag Event Needs No Package

Placing a device or keystone at a specific point on a shelf's face needed a real interaction the rest of the builder didn't have yet — dragging, not clicking, since a continuous position genuinely suits a drag gesture better than picking a spot off a list. The browser already has a real API for exactly this. No library got added to provide it.

The third time, not the first

This project has now made the same real call three times: a drag-and-drop library was named as a plausible option for the main rack elevation, then deliberately left unbuilt until the simpler click-based interaction proved itself first. A CAD library got evaluated for generating a faceplate and the heavier, more powerful option lost specifically because the real problem was smaller than it could handle. Here, the browser's own drag events already do everything a real implementation needs — reading what's being dragged, computing a real drop position, running a mechanical overlap check before accepting it — without a dependency to install, version, or carry into the production bundle.

What that choice actually costs

Native drag-and-drop has a real, known limitation: no keyboard path. Swapping the picker items from real buttons to draggable elements lost genuine keyboard operability that focus and a tab index alone don't restore. That's a real accessibility gap, not a hypothetical one, and it's now written down as its own scoped, honestly low-priority item — worth fixing once the rest of the tool is functional enough that it's the most logical remaining improvement, and worth admitting might cost more to build well than it delivers, rather than promising it as a confident near-term fix it may not actually be.

Choosing not to add a dependency is still a real decision with real tradeoffs — the honest version of "we didn't need a library" includes saying plainly what going without one gave up.
