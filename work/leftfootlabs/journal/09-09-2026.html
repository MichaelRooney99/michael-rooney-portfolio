The Estimate That Stops Where the Data Does

Three real discharge curves existed after the previous session's testing — logged numbers, not projections. Turning that into an actual runtime estimator the Rack Planner could return from an API meant making a real decision at the edges of the data, not just plotting the three curves and calling it done.

Anchoring at the moment the battery actually starts draining

Each curve's timeline starts at zero the moment its log first showed the UPS genuinely running on battery, not at the last reading while still on line power. That distinction actually mattered: one level's logs showed the reported runtime estimate swinging wildly for several readings while still fully on mains, as the induced load ramped up before the plug ever came out. Anchoring at the real transition point keeps every curve measuring the same thing — time actually spent draining — instead of quietly including a stretch of pre-discharge noise in one curve and not the others.

Labeling what wasn't actually measured

One of the three load levels never had its exact load percentage directly confirmed the way the other two did — it was inferred from how its runtime estimate compared to the baseline level, not read off the UPS directly. Rather than quietly presenting all three curves with equal confidence, that one gets a real flag in the data itself: an explicit field marking it as inferred, not measured, carried through in a comment rather than smoothed over. A future session correcting it only has to change one flag, not rediscover which number was shaky in the first place.

The decision that mattered most: refusing to extrapolate past the floor

The heaviest load level was deliberately stopped early — live-watched, reconnected well before any real risk — which means its curve only actually covers a drop from full charge down to 68%. A naive estimator would happily project that partial slope out to a full depletion estimate. That number would be fiction wearing the shape of data: 150 real seconds of observation stretched into a guess about behavior that was never actually watched.

The estimator's actual rule: report the real, interpolated time to reach the lowest charge percentage genuinely observed at a given load — and say plainly what that floor is — instead of projecting further just because a smooth curve makes that look easy. An honest "I don't know past this point" is worth more than a confident number built on a fraction of the real range.

Interpolating between two real curves instead of one

For a load that falls between two tested levels, the estimator blends both real curves — proportionally by how close the requested load sits to each one — rather than just rounding to the nearest tested level. The one wrinkle: two curves reached different floors (one only measured down to 68%, another all the way to 27%), so a blended estimate can only honestly compare them down to whichever floor is higher. Comparing past that would mean inventing data for the curve that never actually went that low.

Every exact match to a tested level reproduces its real logged number precisely — checked directly, not just trusted because the logic reads correctly. The interpolated cases got the same treatment: traced by hand against the raw log entries for two different in-between loads, and both matched the code's output exactly. Loads outside the tested range get an explicit extrapolated-by-load flag rather than being treated the same as a real interpolation between two measured points — a materially weaker guarantee, and the API says so.

Getting the estimate itself right turned out to be the easy part. Wiring it into the actual running API surfaced two real problems that had nothing to do with any of this — worth its own entry rather than folding in here.
