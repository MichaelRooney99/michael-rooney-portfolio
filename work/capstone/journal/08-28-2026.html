Session 47 — The One Place This App Ever Renders Free Text as HTML

The last session traced a single request end to end and closed on an honest gap: it never touched the admin page. This session closes that gap and, with it, the second of the two planned repetition passes for this project. The admin surface turned out to be worth its own full session — it's not a React route at all, and it's the one place in this entire codebase where a person's free-typed text becomes rendered HTML.

Not a React route, and no login form — both on purpose

client/public/admin/index.html is a standalone static page, served by nginx, completely outside the Vite/React build. The reasoning is stated directly in the file's own header comment: App.tsx has no router, and adding one for exactly one admin screen would be a real new dependency for a single page. There's no login form either, and that's not an oversight — this page assumes Cloudflare Access is already gating /admin/* at the edge. If the page loaded at all, Access already decided the visitor belongs there. The fetch calls underneath carry no credentials of their own. That lines up exactly with the honest caveat already sitting in index.ts's own comment on these routes: zero independent server-side verification today, with validating the real Access JWT named explicitly as a deferred follow-up, not a gap nobody noticed.

One field from last session is doing all the real work here

Every incident this page renders branches on origin — the exact field traced last session as the thing /incidents stamps onto every entry at read time. 'file' gets exactly one button, Promote to editable, and nothing else — a file-backed incident is read-only here by design. Anything database-backed gets the real controls: an update field, Resolve while active, Delete once resolved. It's a small thing to say out loud, but a real one: that field wasn't bookkeeping, it's the single piece of data deciding which buttons a person even sees.

The delete button double-checks a guard it shouldn't need

Delete only ever renders once an incident's status is already resolved, and the handler still checks for a 409 response from the server anyway. The session that built the promote flow established the same pattern for a different route — the server enforces the real lifecycle, the client just tries not to offer a button that would fail, and checks honestly for the case where it's wrong rather than assuming its own guard is airtight.

Why free text becomes HTML in exactly one place, and how that's handled

This is worth explaining in full, because it's the one genuine security-relevant decision on this entire page. Every incident in the list is built as a template-literal string and assigned to innerHTML — not textContent, because the markup includes real structure (buttons, a collapsible update list, conditional action sets), not just plain text. The values dropped into that template — an incident's title, its status tag, its update messages — come from an admin typing into a text field. Nowhere else in this app does that happen. Service names, categories, and metrics all come from infrastructure APIs; nothing about them is free-typed by a person. This page is the one place a human's own words become part of an HTML string another browser will parse and execute.

Without protection, that's a textbook stored-XSS path — see MDN's own security note on innerHTML for why. An incident titled something like <img src=x onerror=alert(1)> would, on the very next page load, execute as real script for whoever's looking at the admin panel — not a hypothetical, exactly the behavior innerHTML is documented to have.

The fix here is two small functions, escapeHtml and escapeAttr, and every dynamic value in the render function passes through one of them before it reaches the template string. escapeHtml doesn't use a regex at all — it creates a detached <div>, assigns the raw string to its textContent, then reads the same element's innerHTML back out. That round trip is the actual escaping mechanism: setting textContent stores the string as a plain text node with no HTML interpretation, and reading innerHTML forces the browser to re-serialize that text node back into safe HTML, encoding &, <, and > as entities in the process. It's the browser's own serializer doing the escaping, not hand-written string replacement that could miss a case.

escapeAttr exists because that round trip alone isn't enough everywhere. The browser only encodes the characters that are actually dangerous inside HTML text content — a bare double quote is harmless there and stays untouched. But two values (data-id and data-title) get written into double-quoted HTML attributes, not text content, and an unescaped " in that position closes the attribute early, handing an attacker the ability to inject a new attribute — an inline event handler, for instance — onto that same element. escapeAttr is escapeHtml plus one explicit .replace(/"/g, '&quot;') on top, specifically for that narrower, attribute-context risk. Two functions, not one, because they're closing two genuinely different holes.

Worth naming the contrast, too: none of this is necessary on the public status page. IncidentList.tsx renders the same title and update-message fields as plain JSX expressions, and React escapes every JSX-interpolated value by default unless something explicitly opts out with dangerouslySetInnerHTML, which nothing in this codebase does. The admin page needed hand-written escaping specifically because it's plain JavaScript building raw HTML strings — the exact tradeoff that comes with skipping a framework for a single screen, made deliberately, and handled correctly rather than just accepted as a risk.

Where this leaves things

Between this session and last, every real corner of the app has now been walked out loud at least once — the live-data read path, the two background loops, the incident write path on both the auto and manual sides, and now the one screen where a person's own text becomes part of the page. Both repetition passes are done.
