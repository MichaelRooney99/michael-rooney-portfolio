Session 13 — A Toggle, and Three Contrast Bugs It Was Right to Catch

Second session of the front-end polish plan, and the one deliberately pulled forward from its own suggested order — the theme toggle needed the same token system the later full visual restyle needs, so building both in one pass meant the actual theming mechanism only gets built once instead of twice.

The token system

This project runs Tailwind v4, which replaced the old tailwind.config.js with a CSS-native @theme directive — and critically, values inside @theme can be var() references pointing at other CSS custom properties, not just static colors. That's the whole mechanism: define --color-capstone-bg: var(--theme-bg), then let two separate selector blocks — :root for dark, [data-theme="light"] for light — decide what --theme-bg actually equals. Flip one HTML attribute, every utility class built on that token updates everywhere, no component-by-component rewrite required for the mechanism itself to work.

The light palette needed deriving from scratch — the portfolio site this is meant to eventually match doesn't have a light mode to copy from. Went with a warm-toned derivation rather than a generic inversion: cream background instead of stark white, warm charcoal text instead of pure black, the same orange accent kept identical across both themes on purpose rather than picked twice.

Proving it without doing Session 5's job early

The plan draws a real line: this session builds the mechanism, Session 5 does the actual component-by-component replacement of every zinc-* class in the codebase. Applied the new tokens to the outer app wrapper and header only — enough to prove the whole thing genuinely works end to end, without quietly doing the full restyle early just because it was tempting to keep going.

Two bugs a real test caught, that nothing automated would have

Toggled to light mode to check the work, and the page title went nearly invisible — text-zinc-100, a near-white color that was never meant to respond to theme at all, sitting on the new cream background it had no way of knowing existed. My first instinct fix used a static mid-gray instead, which technically improved light mode's contrast while quietly making dark mode's worse — a compromise that's mediocre in both places rather than good in either. The actual fix was using the token system for exactly what it's for: text-capstone-text resolves to the right high-contrast color in whichever mode is active, automatically, without picking a middle ground.

Same root bug turned up a second time in the loading skeleton — reload the page with light theme active, and the placeholder blocks would have flashed as dark gray on a cream background before real content ever arrived. Nothing wrong with the skeleton's shape, just the same static-color mistake in a different component. Fixed by converting both skeleton components and the loading wrapper to the same capstone-* tokens — the kind of thing that's easy to miss because a broken loading state only shows up for a second, and only in the one theme mode you weren't looking at when you built it.

Avoiding a flash of the wrong theme entirely

A theme decided in a React useEffect paints too late — the browser renders once with whatever the default CSS says, then visibly snaps to the real answer once JavaScript catches up. Fixed with a plain, blocking <script> in <head>, ahead of any stylesheet, that reads the same stored-choice-then-OS-preference logic synchronously before the browser paints a single frame. No flash, because there's never a wrong frame rendered to begin with — wrote up the full mechanics of this separately, since it turned out to be genuinely interesting on its own.

Testing it properly, not just looking at it

Four real checks, not just "does it look right": basic toggle behavior, confirming <html data-theme="light"> is already present in the raw page source on a hard reload (more reliable than trying to catch a few frames of flash by eye), persistence surviving an actual tab close and reopen — checked directly in DevTools' Application panel, not assumed — and the OS-preference fallback verified through Chrome's built-in prefers-color-scheme emulator rather than touching real system settings. All four passed clean.

Where things stand

Token system and toggle both genuinely working, confirmed through direct testing rather than eyeballing. Two real contrast bugs found and fixed properly instead of patched around. Session 3 is next — response-time tracking and the per-service detail view, built together since one is the natural thing the other displays.
