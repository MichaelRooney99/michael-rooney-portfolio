Session 46 — Load to Render, Explained Out Loud

This is the first of two remaining code-review passes before this project's final documentation phase — deliberately planned as repetition for familiarity, not bug-hunting. The angle this time: trace one real request end to end, from the moment the page loads to the moment something renders, and narrate the why at every hop the same way I'd have to if Perry stopped me mid-sentence and asked "wait, why does it do that." Three earlier passes each used a different technique — a full front-to-back read, working backward from a live outage, reading test names before implementation. This one follows the data instead of the file tree.

The read path starts with a decision, not a fetch

useServiceStatus is the hook the whole app is built around, and the first real decision in it isn't the fetch itself — it's TanStack Query over a hand-rolled useEffect/setInterval. The reason matters specifically for a status page: a plain interval stops firing the moment a browser throttles a backgrounded tab, which is exactly the moment someone would still want to know their homelab went down. refetchIntervalInBackground bypasses that. The 60-second poll and 55-second staleTime aren't arbitrary either — leaving a 5-second gap means a component remounting right at the boundary never double-fetches or serves data that's technically stale.

From there, services/index.ts is the facade — four adapters run through Promise.allSettled, not Promise.all, because one dead source shouldn't blank the whole page. The genuinely sharp detail here: a rejected promise carries no indication of which adapter actually failed, so a parallel array (SERVICE_ADAPTER_CATEGORIES), same order, exists purely to attribute a failure back to a name the unavailable- categories banner can show.

An assumption that didn't survive a second look

Reading prometheus.ts in isolation, it looks like it skips the proxy entirely — it defaults to http://10.10.10.105:9090 directly, with no PROXY_URL anywhere in the file, while proxmox.ts and zabbix.ts both call through the proxy explicitly. That would have been a real inconsistency worth flagging to Perry as a gap. It isn't one. VITE_PROMETHEUS_URL gets baked to a same-origin /prometheus path at build time, and nginx forwards that straight into this same proxy's own allowlisted route — see the session that first built the proxy layer for why that boundary exists at all. Same BFF, same trust boundary, just reached through build-time environment substitution instead of a hardcoded call. Worth having caught that before saying the wrong thing out loud in an interview.

The proxy is the trust boundary, not just a relay

Every route the client actually calls — /prometheus, /proxmox, /zabbix — is path- or method-allowlisted, not just forwarded. That's the real answer to "why does a BFF exist" if Perry asks it directly: it's not only about hiding the Proxmox token and Zabbix bearer token from the browser, it's the only place that can actually restrict what those tokens are allowed to do once they leave this server. Before the allowlists existed, any path or method reached the real upstream API with the real credential attached — a theoretical hole turned into a concrete one the moment this became a public origin.

Two background loops, on purpose, not by accident

poller.ts runs every 15 minutes, records a snapshot, and re-derives an incident-worthy streak straight from the snapshots table rather than tracking it in memory — so a proxy restart never silently loses where a service was mid-streak. nudge.ts runs every 20 seconds and does a cheap signature comparison across all three sources, pushing a live update only when something actually changed. The two intervals are deliberately different clocks: reusing the 15-minute poll for nudges would make Proxmox API and Zabbix updates slower than the 60-second client polling the nudge channel exists to beat.

How an incident actually gets created

Two genuinely separate write paths land in the same drafted_incidents table. Auto-drafted incidents come from the poller's threshold check — two consecutive bad readings, roughly 30 minutes of sustained outage — and carry a hardcoded "Auto-detected" message. Manual incidents come from the /admin/incidents route with a real title and message an admin typed. They're not one function with a source parameter because the auto path's canned message text would be actively misleading attached to something a person actually wrote. The dedup check that stops a service from getting two open incidents filters explicitly to source = 'auto' — without that filter, a manual incident referencing the same service would look like an already-open incident to the threshold checker and quietly suppress a real auto-draft.

Retirement runs the same logic every poller tick: force-resolve anything unresolved past 90 days, with an honest "Auto-closed" note written first, then delete anything resolved past that same window. Both keyed on created_at, one clock, not two — which means a force-resolved incident becomes eligible for deletion in that same pass, not some grace period later. Deletion itself is gated separately: the delete route returns a 409 unless status is already resolved, enforcing a real lifecycle — investigating, resolved, retired — rather than a shortcut straight from active to gone.

What actually reaches the screen

App.tsx groups services against a fixed category order that mirrors how infrastructure actually gets checked in practice — compute, then the API layer in front of it, then power, then network — not alphabetical order. A category that isn't in that list still renders, into a trailing "Other" bucket, specifically so a new category showing up in live data can never silently disappear just because the array wasn't updated for it.

The command palette (⌘K, Ctrl+K, or /, matching GitHub's own jump-to convention) is hand-rolled rather than a library, consistent with every other small UI primitive in this app. Selecting a service opens ServiceDetailModal, which branches by category — Proxmox Nodes and Power query Prometheus range endpoints directly, Proxmox API and Zabbix hit the proxy's own /history/:serviceId/recent route, which is just the same table the poller writes to every 15 minutes, read back out. Two different sources landing in one shape so the chart component never has to know which one it's looking at — the same normalization idea from the facade, one level deeper. One detail worth being able to say plainly: syncing state to a changed prop (the palette's active-index reset, the incident card's forced-open state) happens during render, per React's own guidance on that exact pattern — while the actual scrollIntoView call stays in a useEffect, since that's a real interaction with something outside React, not a state update.

Three comments that didn't sound like the rest of the file

The trace also turned up something that wasn't architectural at all — a few leftover comments in prometheus.ts and one line in the proxy's /incidents route that read like notes to myself rather than documentation, out of step with how disciplined every other comment in this codebase already is. Small fix, but a real one: this code is meant to be read by a hiring audience, and one file sounding noticeably more casual than its neighbors is the kind of thing that stands out for the wrong reason. All three got rewritten to explain their actual reasoning in the same self-contained terms the rest of the project already holds itself to.

Where this leaves things

One full request, traced start to finish, with one wrong assumption caught before it became a wrong answer in an interview and three small honesty fixes along the way. Pass two is next — the admin UI and the incident-authoring surface are the areas this pass didn't touch.
