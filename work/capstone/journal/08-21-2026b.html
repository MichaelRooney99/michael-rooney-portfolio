Session 39 — One Promotion Button, and the Gap It Opened the Same Day

The oldest incidents on this status page — the ones seeded from a hand-edited file rather than created through the admin page — have never been editable through the UI at all. This session gave them a real way in: a promotion action that copies one into the database, fully editable from that point forward, without ever touching the original file directly.

A gap that only showed up while actually building the button

The plan going in was straightforward — add a Promote button next to old incidents, wire it to a new endpoint, done. Building the button surfaced something the plan hadn't accounted for: the admin page had no way to know, before attempting anything, whether a given incident was even eligible. The old behavior found out reactively — try to edit it, get a 404 back, then explain after the fact why it failed. That's a workable pattern for an error case, but a genuinely bad one for something that's supposed to be a real, visible action a person chooses to take.

The fix was small — one extra field on every incident the API already returns, marking whether it came from the file or the database — but it's the kind of small addition that only becomes obvious once you're trying to build the real UI around it, not while just reading the plan on paper.

A dismissable alert wasn't good enough for this one

Promoting an incident can't fully finish itself — the original file entry still needs a small manual edit afterward, on purpose, since nothing in this app is allowed to write back to that file directly. The first instinct was a browser alert() explaining the follow-up step. Worth pushing back on that instinct: an alert is trivial to dismiss without really reading, and this is exactly the kind of one-time instruction that's easy to forget the moment it disappears. It became a real, persistent block on the page instead — sitting in place of the incident's normal buttons until explicitly acknowledged, impossible to accidentally click past.

The double-promotion gap, closed the same day

One real gap got flagged rather than fixed in the moment: nothing stopped the same old incident from being promoted twice if the manual file edit got delayed. Worth actually closing before moving on rather than letting it sit as a known issue — the fix is a single new column tracking which original entry a promotion came from, checked before a second promotion is ever allowed to run. If it fires again on the same entry, the response now points back at the incident that already exists instead of quietly creating a duplicate — useful specifically because the realistic cause of a repeat click isn't someone trying to break anything, it's just forgetting the file-edit step the first time around.

Confirmed the honest way

Full test suite, both packages, run for real rather than assumed clean from reading the new code: 48 proxy tests, 67 client tests, 115 total, all green — including the six new tests covering the promotion function itself, one of which exists specifically to prove a promoted incident keeps its real original date rather than quietly getting a fresh one the moment it's promoted.
