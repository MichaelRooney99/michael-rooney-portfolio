Session 30 — Three Kinds of Testing, and What Broke Along the Way

Everything tested up to this point has been a pure function — feed it an input, check the output, no rendering involved. That's the easiest kind of test to write and the least like what actually breaks in a real UI. This session closed out the last piece of automated coverage with three genuinely different testing problems instead of just more of the same kind, on the theory that three techniques done properly teach more than ten shallow tests of trivial components ever would.

Testing a hook with nothing attached to it

The keyboard-shortcut logic behind the command palette — Cmd/Ctrl+K or a bare "/" opens it, unless whatever's currently focused is a text field — lives in its own hook, completely separate from any component that renders anything. Testing it meant learning renderHook, which mounts a hook inside a real, disposable component behind the scenes so it can be exercised in isolation, without needing to build and render an actual UI just to reach the logic inside it.

The genuinely interesting part was proving the typing-target guard actually works — not just calling a function and checking a return value, but creating a real <input> element, dispatching a real keyboard event at that element, and letting it bubble up to the document-level listener the same way an actual keystroke would. That's the difference between testing what a piece of code is supposed to do and testing what it actually does when a real event reaches it.

Simulating an actual person, not just calling functions

The command palette itself — the searchable list, arrow-key navigation, Enter to select — needed a different kind of test entirely: not "does this function return the right value," but "if someone types into this box and presses Enter, does the right thing actually happen." That's user-event's job, and it's a genuinely different mental model — instead of calling onSelectService(service) directly to check it works, the test clicks and types and presses keys the same way a real visitor would, and only then checks whether the right handler got called.

Mocking the boundary, not the network

The per-service detail modal fetches real data the moment it opens, which meant learning how to test something asynchronous without actually hitting a network. The decision worth explaining: mock the app's own data-fetching function directly, not the browser's fetch underneath it. This app is already built around small adapter modules as the seam between "real data" and "everything else" — mocking at that same seam means this test stays accurate even if the underlying API call it wraps changes shape entirely, since only that adapter's own test would need to know about that.

Two real bugs, both in the tests themselves

Neither of these was a bug in the actual app — both were in code written this same session, caught only by actually running it rather than trusting that it read correctly.

The first: a query meant to find one specific row on screen accidentally matched three, because two unrelated rows happened to share a word with the one row's name. The fix wasn't cleverness, just narrowing the search to something provably unique. The second, more interesting one: clicking on a list item didn't trigger its button's click handler, because the button was a separate element nested inside the item, and a real click event only travels up from wherever it actually lands, never back down into children that weren't the real target. Visually, clicking anywhere on that row looks like it should work — the button fills the whole row. Structurally, the test needed to click the actual button, not the row that merely contains it.

Both were fixed the same way as everything else this project has caught along the way — not by reasoning about what should be true, but by running it, watching it fail, and finding out why.

Where this leaves things

67 tests on the client side now, 34 on the proxy — 101 total, every one of them run for real, not just written and assumed correct. This closes out the last open piece of automated test coverage for this project. What's left on the roadmap now is genuinely different in kind — not more testing, but the deployment pipeline's own next step.
