Session 27 — Proving the Smoke Test Actually Smokes

The post-deploy smoke test built earlier today had one real gap left before it counted as actually done: it had only ever been seen passing. A test that's only ever passed hasn't been proven — it might be correctly checking the right thing, or it might be silently broken in a way that happens to still say 200. This session's whole job was closing that gap, deliberately, against real infrastructure.

The pass, confirmed for real

First, a genuine end-to-end deploy — git pull, rebuild, restart, both checks in sequence. Health check 200, smoke test 200, tunnel active. Clean. That's the easy half, and also the less interesting one — a test passing tells you almost nothing on its own.

The fail, which took more setup than expected

Proving the failure path meant genuinely breaking the deployed site on purpose, which turned out to need a few real steps most of them worth noting. First real snag — docker compose stop proxy over a plain SSH session failed with a permissions error; the ansible user isn't in the host's docker group. Ansible's own privilege escalation handled it cleanly instead — ansible capstone -m command ... --become, the same path every playbook in this project already uses, rather than reaching for raw sudo on an interactive session.

With the proxy actually stopped, curl against the real public domain came back exactly as it should — a genuine 502, nginx correctly reporting it has nothing to forward to. Confirmed the break was real before testing whether anything would catch it.

Running the full playbook at this point would have been self-defeating — capstone_deploy.yml's "Bring up the Docker Compose stack" task runs before the smoke test, and docker compose up -d --build would have silently restarted the stopped proxy as a normal side effect, fixing the outage before the smoke test ever got a chance to see it broken. First real use of --start-at-task — skip straight to the smoke test by name, touch nothing before it. Exactly the tool for this specific problem: testing one task in isolation without editing the file just to comment out the steps around it.

What actually failing looked like

Three real retries, five seconds apart, each one hitting the genuine 502 — then a hard stop. msg: 'Status code was 502 and not [200]: HTTP Error 502: Bad Gateway', failed=1 in the recap, nothing after it ran. No ignore_errors anywhere in the task, so the play halted exactly where it should have. That's the actual proof — not "the code looks like it would fail correctly," a real recorded failure against a real broken deployment.

Restarted the proxy, confirmed the site healthy again — a real 200, matching content-length to what it showed before any of this started. Fully recovered, nothing left in a broken state.

Why this was worth the extra session

The idempotency script earlier today did the exact thing this session was trying to rule out for the smoke test — it reported PASS once for the wrong reason, because forced color codes had silently broken its own parsing logic and it found nothing to flag as a failure. Correct that particular run, but not because it had actually verified anything. A test that's only ever been observed passing carries exactly that risk, invisibly. Confirming both directions — a real pass and a real, deliberately-triggered fail — is the only way to actually rule it out, and it's the same standard this whole project has run on since the first production incident: prove it against the real thing, not against what the code looks like it should do.
