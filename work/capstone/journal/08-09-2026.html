Session 21 — Security Hardening, and the Proxy That Trusted Everyone

22-Security Hardening was scoped as four layers, with the secrets audit expected to be the cheap, boring one — the layer where "nothing's actually wrong" was a completely acceptable outcome. It found the biggest single finding of this entire project instead.

What "audit the secrets" actually turned up

.gitignore and logging were both genuinely clean — no leaked credential, nothing dumped into logs that shouldn't be there. But looking closely at how /proxmox, /zabbix, and /prometheus were actually built revealed something worse than a leak: all three were unrestricted, fully-authenticated passthrough proxies. Any path under /proxmox/* forwarded straight to the real Proxmox API with the real token attached. Any JSON-RPC method sent to /zabbix forwarded to the real Zabbix instance with a real session token. Any path under /prometheus/* hit the real Prometheus install directly. The app's own code only ever called a handful of specific read-only endpoints — nothing enforced that boundary. The public internet had, in practice, whatever access those real credentials actually granted.

Why this mattered more than the original plan

The scope doc's original order put rate limiting first. This finding jumped the queue on purpose — a rate limiter slows down repeated abuse, it doesn't stop one well-aimed request through a door that was never locked in the first place. Fixed with real allowlists: each proxy restricted to the exact paths or methods the app's own client code actually calls, everything else rejected with a 403 before it ever reaches the real upstream.

A real architectural correction along the way

The original plan assumed security headers meant adding helmet.js to the Express proxy — a reasonable default assumption that turned out to be wrong for this project's actual architecture. The proxy never serves the HTML page; nginx does, in this single-origin setup. A CSP only means something on the response that delivers the page — setting it on the proxy's JSON API responses would have protected nothing. Headers moved to nginx instead, which turned out to be strictly better: one place to configure, coverage for both the static page and every proxied API response, and zero new npm dependency.

Confirmed against real production, same standard as always

The allowlists were tested with real requests the app never makes — a Proxmox config path, an unused Zabbix method, an unused Prometheus endpoint — each correctly returning this project's own 403 instead of the real backend's response. Rate limiting was tested with a real 150-request loop against /incidents: exactly 60 clean responses (matching the configured burst), then a genuine leaky-bucket refill pattern afterward — textbook behavior, not noise. The git-history check for a committed .env came back clean too, though only after catching a real mistake mid-session — the first check ran against the wrong repo entirely (the Ansible playbooks repo, not homelab-status), caught before it got trusted as the real answer.

Where this leaves things

22- is done — three of four original layers plus a finding the original scope doc never anticipated. Only Dependabot remains, still deliberately deferred to 23-, where it costs almost nothing once any GitHub Actions presence exists.
