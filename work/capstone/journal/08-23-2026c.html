Session 45 — A Real Outage Test, and Two Wrong Guesses Along the Way

The last real code for today's feature was small — a genuine correctness bug found along the way (a single failed query used to silently take down history for two categories that never depended on it at all), and a deliberate refusal to build something that turned out not to be buildable honestly. What actually filled the rest of the session was proving the whole thing works against real infrastructure, and getting corrected twice by real evidence before it did.

A real limit, hit honestly instead of worked around

Two categories on this page get their history from Prometheus, and most of a 90-day window showing "no data" for them is completely expected — Prometheus only retains 30 days. The real, harder question was whether a "no sample" day within that 30-day window could be told apart from a genuine outage inside it, rather than just retention running out. That distinction needs Prometheus's own historical uptime to check against — and checking directly against the real, running instance confirmed it doesn't self-monitor at all. No self-scrape job, nothing to compare against. Not a harder engineering problem to push through — a genuinely missing precondition. Closed out honestly rather than half-built: documented plainly as not currently possible, instead of quietly shipping something that looked like it worked but couldn't actually prove what it claimed.

First wrong guess: the direction of the block

Testing this for real meant making a monitoring source genuinely unreachable on purpose — the safe way, a scoped firewall rule rather than actually taking a real service down. The first version got stuck on the wrong question entirely: should the capstone's own outbound calls be blocked, or should the services be blocked from reaching the capstone? The real answer was simpler than the question made it sound — every failure path this feature actually covers starts with the capstone initiating a request out, never the reverse, so only one direction was ever worth testing. Confirmed, not assumed, before touching anything further.

Second wrong guess: what "no data recorded" actually meant

The real puzzle came after unblocking — a source had genuinely been down for over half an hour, and nothing showed up as unreachable in the history afterward. The honest first move was checking the real proxy logs rather than guessing further, and they told a clean, complete story: the poll genuinely had failed, exactly once, right in the middle of the blocked window. The write had happened. What hadn't happened was a bug — the very next successful poll, right after unblocking, wrote a real reading for the same calendar day, and real data winning over an unreachable one on the same day is the exact rule built into this earlier today. The system did precisely what it was supposed to do; the test just needed a moment after the fact where nothing else overwrote the evidence before checking it.

Proving that directly, rather than trusting the reasoning alone, meant writing one real "unreachable" row straight into the database and watching it show up — a genuine reading sitting in a service's actual recent-readings list, between two real operational ones, rendered correctly and immediately deprioritized in the day's own rollup exactly as designed. Recorded, displayed, and correctly outranked by real data, all confirmed in one place.

Where this actually landed

A monitoring source going fully unreachable and a source with nothing to report no longer look the same anywhere on this page — not in the history bars, not on the live view, not in a service's own detail log. The one piece that genuinely isn't buildable right now is written down plainly as exactly that, not quietly dropped. And two real, different wrong guesses along the way both got corrected the same way everything else in this project has been — by checking the actual source instead of trusting the more comfortable explanation.
