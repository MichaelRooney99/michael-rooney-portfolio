Session 14 — Click Into a Node, See What It's Actually Doing

The idea that started this whole roadmap branch, several sessions back: click into a service, see a real 24-hour picture instead of just the current badge. Built it this session, paired with response-time tracking per the scope doc's own recommendation — one is the natural thing the other displays.

What actually needed building, and what didn't

The genuinely good news going in: neither Prometheus nor the snapshot poller needed a single new piece of data collection. Prometheus already retains 30 days of real granular scrape data, and appends a scrape_duration_seconds metric to every scrape automatically — response time for the two Prometheus-backed categories was sitting there, already collected, never queried. The poller-backed categories needed one real addition: timing its own fetch calls and storing the result, a small change to a database table that already existed.

The actual new work was almost entirely about exposing data that already existed rather than collecting anything new — a genuinely good sign for scope, and a nice contrast to sessions like the category-history one, which had to build an entire independent poller from nothing.

An honest limit worth stating plainly, not hiding

The proxy fetches an entire node list or host list in one request — so every node in a given poll gets the exact same recorded response time. That's not per-node latency, it's "how long the whole list endpoint took to respond," uniformly applied. A more precise version would mean querying each node individually, which is slower and more load for a number that's mostly useful as a rough trend line anyway. Documented directly in the code rather than implying a precision the endpoint shape can't actually give.

A chart, hand-rolled again

Same decision as the uptime bars: no charting library. MiniLineChart is a plain SVG polyline with two normalized axes — nothing a 24-hour trend line actually needs that a real charting library would add. Consistent with how this codebase has handled every other visualization so far, and small enough that reaching for a dependency would have been the wrong tradeoff.

A real bug, caught by asking the actual source instead of guessing

Wrote the Prometheus query for the UPS's response time using job="nut_exporter" — a reasonable guess, matching the naming convention every other exporter in this fleet follows. Wrong. Queried Prometheus directly for every scrape_duration_seconds series it actually has, and the real job label was just nut, no suffix.

Would have shipped as a silently empty chart for exactly one category — no error, no crash, just a permanently blank graph that looked like "not enough data yet" instead of "wrong query." The fix was one word, but finding it required actually asking Prometheus what it has, not assuming a naming pattern held everywhere. Same debugging instinct this project has leaned on from the very first session: query the real source directly before trusting a guess, even a reasonable one.

Confirming both paths, not just one

This feature has two genuinely different code paths under it — Prometheus range queries for Nodes and Power, the proxy's own new /history/:serviceId/recent route for Proxmox API and Zabbix. A screenshot of one working proves nothing about the other; they share almost no code. Tested both independently — a Proxmox Node's chart populated with real millisecond data pulled straight from Prometheus, then a Zabbix host and a Proxmox API node confirmed the proxy route and the new database column separately. Both genuinely worked, but only checking because two different things could each fail independently was the right instinct, not an assumption that one success implied the other.

One more honest gap the response-time chart made visible immediately: the response-time column only exists from the moment this session's migration ran, so a freshly-tested service showed just two data points on the chart while its status log went back much further. Not a bug — the same no-retroactive-backfill principle every other piece of history in this project has followed, just visible sooner here since a two-point line chart looks obviously sparse in a way a mostly-grey 90-day bar doesn't.

Where things stand

Both new features confirmed live, both real data paths checked independently, one real bug caught before it ever reached a screenshot. Three of the four items from this round of functionality scoping are done now — only auto-drafted incidents left, deliberately saved for last since it's the one with genuine architectural weight, not just more of the same pattern.
