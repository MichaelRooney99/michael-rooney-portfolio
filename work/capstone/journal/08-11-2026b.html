Session 29 — The Comment Describing a Route That Was Never Built

A follow-on to earlier today, and not one that was planned. The task was a full pass through this project's source comments — replacing references to private planning notes with explanations that stand on their own, no outside context required. Mechanical work, in theory. Reading every comment in every file to do it properly is what actually surfaced something real.

A comment describing behavior that didn't exist

The nginx config for the live-update channel had a detailed comment explaining exactly what that route needed — response buffering off, a long read timeout, the works. What it didn't have was the route itself. No location block for it anywhere in the file. The comment described the fix; the fix was never actually applied.

Confirmed it directly rather than trusting the read — a plain curl against the live production URL for that route came back 200, text/html, with a last-modified header attached. That's not what a live server-sent-events connection looks like — that's nginx quietly serving the app's own static homepage instead, the same fallback it uses for any URL it doesn't otherwise recognize.

Why nobody noticed

This is the part worth sitting with. The feature this route powers was built specifically to degrade gracefully — if the live-update connection never establishes, the page just falls back to checking for updates every 60 seconds instead of near-instantly, and the client-side error handling for a failed connection is deliberately silent, since a dropped connection reconnecting on its own is completely normal and shouldn't clutter a console with noise. Both of those were good decisions on their own. Together, they meant a completely dead feature looked, from the outside, exactly like a healthy one running on its slower fallback path. It had been that way since the day it shipped.

The fix, and proving it twice

Added the missing route with the directives the orphaned comment had already correctly described — buffering off, the connection header cleared so the upstream connection doesn't get torn down after the first byte, a read timeout long enough for a connection meant to stay open indefinitely. Deployed for real, then ran the exact same curl command from before against production again. This time: text/event-stream, an open connection instead of an immediate response, and the server's own keep-alive signal arriving right on schedule — proof the fix reached all the way through, not just that the config file looked different.

A comment can describe the right behavior in perfect detail and still not be the behavior. The only way to know which one you actually have is to go check.
