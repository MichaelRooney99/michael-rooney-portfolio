Session 40 — Giving the Admin Page a Log It Already Had the Data For

The admin page has always been the only place an incident's update history actually gets written — every "Add an update" or "Resolve" action happens there and nowhere else. Until this session, it was also the one place that history couldn't be read back. Checking whether a just-written update actually landed with the right wording meant leaving the admin page entirely and going to check the public site instead.

A rendering gap, not a data gap

The fix turned out to be smaller than the problem sounded. The admin page already fetches every incident's full update timeline on every load — it just never rendered it. No new endpoint, no new fetch, nothing on the backend changed at all. Each incident now gets a small, collapsed-by-default toggle showing how many updates it has; opening it reveals the same timestamp-and-message history the public page has always shown, styled to match this page's own plain CSS rather than pulled in from the client app's design system.

Collapsed by default here on purpose, which is the opposite default from the public page. The public page opens active incidents automatically because a visitor is scanning for what's currently wrong. The admin page's real use case is different — confirming one specific incident's history on demand, right after touching it — so keeping every entry compact until asked for reads better for that actual workflow.

Confirmed the honest way

Full test suite still green, and the feature itself confirmed live — opened, read, collapsed again, against real incidents already sitting on the production page, not just clicked through once locally and assumed correct.
