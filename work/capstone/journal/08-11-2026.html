Session 28 — Gating Deploys on Tests, and a Fixture File Docker Couldn't See

The last piece of a deploy-safety effort built over the past couple of sessions — static linting, idempotency checks, a post-deploy smoke test, and now the final layer: gate the live deploy on the app's own test suite actually passing. Small in scope on paper, but it needed a real decision before any code, and it surfaced a genuine structural gap that had nothing to do with the tests themselves.

Where should the tests actually run

The capstone VM's provisioned role has stayed narrowly Docker and cloudflared since it was first set up — no Node toolchain on the host itself. Three real options: install Node on the host directly, run the tests from the Ansible control node against a separate checkout, or run them inside each service's own Docker build stage — the same stage the real deploy image is built from, dev dependencies and all. Went with the Docker build stage. Installing Node on the host works against a design choice that's held since the deployment pipeline was first built. Testing a separate checkout on the control node means testing a sibling of the deployed commit, not the commit itself — exactly the kind of gap this project has spent this whole stretch trying to close, not one worth reopening for convenience.

A bare npm test is not a safe gate

Both the client and proxy define their test script as plain vitest, which defaults to watch mode and only skips it via TTY or CI-environment detection. Running that inside docker run --rm — no TTY, no guaranteed CI variable — wasn't something worth trusting for a task meant to gate a real deploy. Swapped in npx vitest run explicitly. No ambiguity, no dependency on detection logic behaving the way it's assumed to.

The fixture that didn't know its own address

First real run against the built images failed on the proxy side — ENOENT, looking for a JSON fixture file that clearly existed in the repo. A set of shared test fixtures live at the repo root, read independently by both the client and the proxy's own copies of a small status- deriving function, specifically so the two implementations can never silently drift apart. But each service's Docker build context had been scoped to its own folder a few sessions back, for unrelated reasons — which meant that shared, sibling directory was never in scope to get copied into either image in the first place. Not a bug in the test itself — a real structural consequence of two separate decisions from earlier in the project that had simply never been run against each other until now.

Fix was a bind mount, not a copy — mounting the real fixtures directory into each container at test-run time rather than baking it into either image. Keeps the single shared source of truth intact; neither Dockerfile needed to change at all.

Both directions, confirmed for real

Pass path first — both images built and run by hand against real infrastructure, the full suite green on both sides, fixture mount working correctly. Then the fail path, same discipline used to verify the smoke test earlier this week: a scratch branch, one deliberately wrong expected value in a real fixture-driven test, pushed for real, deployed for real with the target branch overridden on the command line rather than touching anything committed.

The deploy's own recap told the whole story — five tasks completed, one failed, and every task after the failing test simply absent from the run, not skipped. The environment file never written, the running stack never touched, the live site never at risk. Eight of the fixture cases failed with the deliberately wrong value; everything else in the same run stayed fully green, confirming the break was scoped exactly where it was supposed to be. Deleted the scratch branch, ran the deploy clean afterward — full pass, health check good, smoke test good, tunnel active.

The deploy-safety work is now fully closed — four layers, built and confirmed, most of them against a real deliberately-broken state as well as a real passing one. What's left on the roadmap is a final architecture write-up, saved deliberately for last, and whatever gets picked up next with no particular schedule behind it.
