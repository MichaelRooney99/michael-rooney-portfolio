Session 38 — Built, Broken by a Cache, and Two Gaps It Was Worth Finding

Incidents on this status page have always been able to pile up forever — nothing ever removed one, whether it genuinely needed to stay visible or not. This session closed that gap: a real delete action for the admin page, plus automatic cleanup that ages old resolved incidents out on its own after 90 days, matching the same 90-day window the uptime history already uses.

What actually got built

deleteIncident and pruneOldIncidents joined db.ts, called from the same poller tick pruneOldSnapshots already runs on. The real interesting piece was the interaction between the two retirement mechanisms the scope doc settled on: an incident still unresolved at the 90-day mark gets force-resolved with an honest system note before deletion, rather than either sitting open forever or vanishing with no trace. A real wrinkle only became visible while actually writing that function — force-resolve and delete both key off the same created_at cutoff, which means a force-resolved incident becomes eligible for deletion in the very same pass that closes it, not after some second grace window. The doc had said "around the 180-day mark" before this was built; that line didn't survive contact with the real implementation and got corrected in place.

The admin UI's new Delete button only renders for already- resolved incidents, and the server enforces that same rule independently with a real 409 — not just a UI nicety, the actual guard. That split matters: the confirm() dialog on the button is a courtesy for the person clicking it, but the workflow discipline itself — investigating → resolved → retired, never a shortcut straight from active to gone — is enforced server-side, where it can't be bypassed by a stale page or a direct request.

A production test that turned out to be nothing

The Delete button didn't show up in the browser right after deploying. Before assuming a logic bug, the real question was simpler: had the deploy actually happened, and was this genuinely the new code being served? A private-browsing load answered it in one step — the button, and its confirm() dialog, both worked exactly as built. Pure browser caching on the regular window, nothing wrong server-side at all. Worth remembering as a first move next time something "isn't working" right after a deploy: rule out cache before debugging code that might not actually be broken.

A real bug the private-window test surfaced anyway

That same screenshot caught something genuinely wrong, separate from the caching question: the confirmation dialog read Delete "delete? resolved manual"? instead of just the incident's real title. The message was pulling from .incident-title's textContent — but that element also contains the status and source badge <span>s as children, and textContent grabs every descendant's text, not just the direct one. Fixed by storing the real title as its own data-title attribute at render time, straight from the fetched incident object — sidesteps the scraping problem entirely instead of writing a more careful selector around it.

Real test coverage, and a bigger gap it made visible

The three new functions got ten real tests in db.test.ts, matching the file's existing conventions — real in-memory SQLite, no mocking. Writing them surfaced something worth being honest about directly in the test file itself rather than glossing over: because force-resolve and delete share one cutoff, there's no way for a test to observe the "auto-closed but not yet deleted" state from outside — by the time anything could check, it's already gone. The tests confirm the real, external outcome instead of pretending to verify an internal step that doesn't actually persist long enough to check.

Writing those tests also made a bigger, pre-existing gap obvious by contrast: db.test.ts has never tested a single one of its incident-related functions — not the auto-threshold write path, not the manual-incident write path, nothing. That's not a small oversight; it's the entire incident subsystem's write logic running on trust alone. Scoped as its own follow-up rather than patched in here, since fixing it properly is real, separate work, not an afterthought to bolt onto this session.

A second gap, found by trying to use my own feature

Testing the new Delete button meant actually looking at the admin page's incident list closely for the first time in a while — and noticing it shows a title, a status, a source tag, and nothing else. No way to see the actual update history an incident has accumulated, even though the admin page is the only place that history ever gets written. The public page already solves this well with an expand/collapse pattern; the admin page just never got the equivalent. Scoped as its own follow-up too, rather than folded into an already-shipped session.
