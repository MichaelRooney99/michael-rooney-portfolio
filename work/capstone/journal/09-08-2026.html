Session 49 — A Fifth Adapter, Slotted Into the Middle

The two review passes and the architecture write-up closed out everything this project actually required — the internship hours cleared, the documentation done, a real case study written. This session isn't part of any of that. New hardware showed up in the rack, and it happened to expose exactly the kind of thing this status page already knows how to show. Worth doing, and worth writing up, capstone requirement or not.

A real ESP32, wired to a temperature and pressure sensor, has been sitting in the rack reporting to Prometheus for a little while now — a homelab addition, built for its own reasons. Folding it into the status page turned out to be less about building something new and more about following a shape that already existed twice.

The same shape, a third time

The UPS integration already established the pattern: one fixed service, a liveness check driving operational or outage, everything else riding along as display metadata rather than feeding the status itself. The rack sensor is structurally identical — a reachability check, temperature and pressure shown alongside it, neither one able to degrade the status on its own. That last part was a real, deliberate choice rather than an assumption: visibility into the reading was the actual goal here, not building a second threshold system for what counts as "too hot," which would have been a meaningfully bigger decision than the one this session actually needed to make.

The real risk wasn't the new code — it was where it landed

The trickier part of this session had nothing to do with the sensor itself. The live page already merges four adapters and tracks which one failed by its position in the list, since a rejected fetch carries no label of its own. Adding a fifth adapter in the middle of that list — not appended at the end, genuinely spliced between two existing ones — is exactly the situation an off-by-one error hides in. A test that only ever rejected the first or last item in the list would never have caught a shift happening somewhere in the middle.

The fix was writing a test aimed specifically at that insertion point — rejecting the new adapter on its own and confirming both that it gets blamed correctly, and that its two neighbors on either side still report clean. Passing the existing tests wasn't enough proof on its own; the existing tests were written before this adapter existed; a genuinely new scenario needed a genuinely new check.

Naming a gap instead of quietly living with it

The file this new function lives in has never had any test coverage at all for its two existing functions — a real, pre-existing gap that an earlier full audit of every test file in this project never actually caught, since it was scoped to a fixed list of files rather than a fresh enumeration of everything that exists. Worth being honest about rather than quietly working around: the new function got real tests today, matching the standard everything else in this project holds to. The two older functions sitting right next to it didn't, and that's a genuine, separate gap still sitting there, not something this session pretended to close.
