Session 44 — A Banner That Refuses to Overclaim

The history-side fix from earlier today only covers half the real problem. A source can also fail at the exact moment someone's looking at the live page — and until now, that failure just made the affected services quietly disappear from view, with nothing anywhere explaining why.

Knowing which promise actually broke

The live page fetches four categories at once and merges whatever comes back. If one of those four rejects, the merge logic already knew to just skip it — what it never knew was which one. A rejected promise on its own carries no label. The only place that information exists at all is the promise's own position in the list it was fired from, so the fix is really just paying attention to that position instead of throwing it away — mapping each index back to the real category name it belongs to, in the exact order the four requests were actually sent.

The real risk with a fix like this is a quiet off-by-one — blaming the wrong neighbor for a failure that wasn't actually theirs. The test that actually catches that isn't the obvious one (reject something in the middle of the list); it's rejecting the very first item specifically, since a shifted index would point at whatever sits next to it instead and still look like it passed.

Saying only what's actually true

The tempting version of this banner said something like "showing the last known state" for the affected category. That's not actually what happens here. Every fetch either fully succeeds or the response just resolves with fewer services in it — nothing ever throws all the way up — which means a failed category's services don't linger as stale data, they're just gone from this refresh entirely. Claiming otherwise would be a small, comfortable lie dressed up as reassurance. The final copy says the plainer, less flattering true thing instead: services in that category aren't shown this cycle, not confirmed down.

One banner, not two

Two Prometheus-backed categories can fail on their live status and their 90-day history independently, and often will fail together, since both ultimately depend on the same upstream. Rather than stacking two near-identical warnings on top of each other, both signals get merged into one deduplicated list before the banner ever renders — a visitor sees one honest sentence about what's actually wrong, not two slightly different ones saying almost the same thing.
