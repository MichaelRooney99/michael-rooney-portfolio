Session 23 — The Badge, the Fixture, and the Gap We Finally Closed

20-Embeddable Status Badge's design had been fully settled since 08-07 — extend nudge.ts's existing 20-second loop to also cache an overall status, add a route that reads that cache, add the nginx forward rule. Small enough to be one session, per the doc's own recommendation, and it stayed that size — no surprises, for once.

A cache, not a query

The whole point of the badge is that it never talks to Prometheus, Proxmox, or Zabbix directly. Every 20 seconds, nudge.ts was already fetching from all three to check whether anything changed — the badge just needed that same tick to also derive an overall status and hold onto it. getCachedOverallStatus() reads that value synchronously, no network call, no matter how many times the badge gets requested. A badge embedded somewhere gets hit on every pageview of whatever's embedding it — computing status fresh per request would mean this project's own data sources take traffic that has nothing to do with anyone actually visiting the status page.

The SVG itself is hand-rolled, same precedent UptimeBars and MiniLineChart already set — a colored dot, a label, no image library. Colors match StatusBadge.tsx's existing mapping exactly, so the badge never disagrees with the page it represents.

The checklist that's caught three bugs before this one

/incidents in July, /history/ in late July, both times the same shape of bug: works against the proxy directly, silently broken against the real public domain, because nginx never got a forward rule. Checked this one against both — curl against 10.10.20.55:3001/badge.svg directly, then https://status.michaelrooney.dev/badge.svg through the actual public path. Both came back clean. Cheap insurance against a bug this project has now made three times.

The gap that had been sitting open since August 7th

deriveOverallStatus needed a second copy on the proxy side — the badge can't call into client code — joining the Zabbix status logic already duplicated three times across this codebase. That duplication was flagged back when 04-Services Index first named the real threshold for when it's worth fixing with actual shared code versus just watching for drift: two Dockerfiles, two separate build contexts, a decision that size isn't justified by two small functions. The stated fix was a fixture-based parity check — one shared JSON file of input/output pairs, read independently by both suites. Real, written down, never built. 18-'s Phase 2 sat scoped and open for exactly this reason.

Built it this session instead of letting it sit open a second time. A fixtures/parity/ folder at the repo root — genuinely a sibling of both client/ and proxy/, not inside either — holding two JSON files: expected outputs for every real combination of statuses deriveOverallStatus should handle, and the same for the Zabbix availability derivation. Both the client's Vitest suite and a new one in proxy/ read the identical file and assert their own local copy still produces the fixture's answer. If either copy ever drifts from the other, a test fails immediately — the direct, addressable fix for how the real nut_exporter vs. nut job-name bug went unnoticed back in July: not the duplication itself, but duplication with no mechanism to notice drift.

Two real environment differences, caught by the editor before the terminal

The client-side test file hit two errors the proxy-side one never did — fs/path unresolved, and __dirname undefined. Not a mistake in the test logic, a real difference in how the two packages build: proxy/ is CommonJS, where __dirname and Node's types are just there. client/ builds as ESM through Vite, which has no __dirname global at all, and its tsconfig has an explicit types array that doesn't include node by default. Fixed with @types/node added to that array and import.meta.url swapped in for __dirname — the actual ESM equivalent, not a workaround.

32 client tests, 14 proxy tests, all green locally, then confirmed the way this project confirms things — a real push, a real CI run, both jobs passing on the actual GitHub Actions infrastructure built two sessions ago. The fixture-parity gap is closed for real now, not just documented as closed.

One more thing, since it was already open

20-'s own doc left the portfolio switch-over as a reasonable follow-up, not required scope. Turned out there'd never been a static status representation on capstone-index.html to begin with — nothing to swap, just a plain <img> pointing at the new badge route, wrapped in its own link rather than folded into the existing "View Live Site" button's text. Left the image without fixed width/height attributes on purpose — the badge's own width isn't constant, since Operational and Outage aren't the same length, and forcing a fixed box would stretch whichever one doesn't match. Turns out that's a feature, not just a tolerance: a wider badge reading something other than Operational visibly shifts the layout next to it, a second signal on top of the color change, free.
