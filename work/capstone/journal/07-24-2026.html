Session 10 — Incident History, and Five Bugs on the Way There

Session 9 scoped incident history and deliberately stopped short of building it, on the theory that build time should go to building rather than re-deciding the shape of it mid-session. That paid off — the scope doc from last time turned into a straight build this time, minus one genuine improvement over the original plan and five real bugs along the way, several of which had nothing to do with incidents at all.

What actually got built

Incident history landed roughly as scoped: a hand-edited incidents.json, a new proxy route, a client adapter, and two components. The one deliberate change from the original plan — bind-mounting incidents.json into the proxy container instead of baking it into the image. Docker Compose doesn't need a restart to see a changed bind-mounted file, and the proxy already reads the file fresh on every request rather than caching it, so an edit takes effect on the very next request — whether that edit happened through a direct SSH edit on Dega or through the normal git-pull-then-redeploy path. Nice property to get for free from a decision made mostly for a different reason.

The tooling bug that had nothing to do with incidents

First real snag wasn't in the new code at all — npm run dev in the proxy started crashing with an error pointing at an internal ts-node placeholder path, the kind of thing that looks like a mystery until you've seen the pattern before: ts-node patches Node's internal module resolution directly, and breaks every time Node's internals shift under it. Running Node 24 with TypeScript 6 and a `ts-node` version that predates both was exactly the setup where that was going to happen. Swapped it for tsx — same job, doesn't touch Node internals, and picked up file-watching as a bonus that plain ts-node never had.

A timezone bug hiding in a tooltip

The 90-day history code from Session 9 computed its Prometheus query window as "90 days back from right now" — which sounds fine until you notice that "right now" moves. The specific instant Prometheus samples for "the bucket labeled July 16th" drifted depending on what time of day the page happened to load, so the same nominal day could genuinely show a different status on different visits. Caught it because a tooltip read Jul 16 — Operational for a day the entire fleet was physically powered off for a rack rebuild. Fix was anchoring both the query window and the day labels to real UTC midnight instead of a moving "now" — stable regardless of load time. Worth being honest about the remaining limit, not hidden by the fix: Prometheus still only takes one sample a day, so a partial-day outage can still land on an "up" moment if that's what the midnight sample happens to catch.

A filename, twice

The updated proxy server code got saved as proxy-index.ts instead of replacing index.ts — an artifact of dodging a filename collision on my end that turned into a real bug on the other end. Locally, tsx couldn't find its entry file. On Dega, tsc had nothing new to compile, the proxy container failed to start, and the deploy playbook's health check failed with a clean connection refused. Same root cause, two different-looking symptoms in two different environments — the kind of thing that's obvious once you check the actual file on disk and easy to chase in circles before that.

Somewhere in the same stretch, a second file — incidentbadge.tsx — turned up sitting right next to the correctly-cased IncidentBadge.tsx. Classic Windows/git trap: NTFS doesn't care about case, git does, so it's possible to end up with two tracked paths that look identical in Explorer. TypeScript's strict casing check caught it as a real error rather than silently picking one. Confirmed it never made it into the actual pushed repo — worth deleting locally regardless, since it kept confusing the language server every time it reopened.

The one that actually mattered

Everything above got fixed, redeployed, and confirmed working — and the incident section still didn't show up on the live site. Worked perfectly in npm run dev the entire time, which was the tell in hindsight: dev mode talks straight to the proxy, production talks through nginx on the same origin. Every other API route — Proxmox, Zabbix, Prometheus, health — had an explicit nginx forward rule. /incidents never got one, because I built the proxy route and the client fetch without touching nginx at all. The request fell through to nginx's SPA fallback, got HTML back instead of JSON, failed to parse, and got silently swallowed by the same Promise.allSettled-style failure isolation that's protected this app from cascading failures three times before — this time hiding my own bug instead of catching someone else's.

One missing location block, styled to match the existing ones, and a client rebuild later — confirmed through the actual public domain this time, not the direct proxy port, since that had been working the whole time and never proved anything about whether the public path was wired up.

Where things stand

Incident history is live — two real incidents on the page right now, one of them a warts-and-all writeup of the timezone bug this exact session found and fixed. Five bugs deep to get here, none of them in the feature's own logic — a dev tool aging out from under a new Node version, a math mistake in day-boundary handling, a misnamed file, a filesystem quirk, and a missing routing rule. Noted for later, not built tonight: making the incident section collapsible once there's enough history in it to be worth collapsing.
