Session 15 — A Command Palette, and the Same Bug Caught Twice

Fourth item off the front-end polish list: a command palette, Cmd/Ctrl+K or /, matching the convention GitHub itself uses. Sequenced right after the per-service detail view on purpose — the plan going in was that "jump to a service" would have somewhere real to land instead of just scrolling the page.

Reusing more than I built

The palette searches three things — services, categories, incidents — in one flat, filterable list. Selecting a service doesn't scroll to its row, it opens the exact same detail modal a click already opens. That decision made itself once the detail view existed: building a second, palette-specific way to inspect a service would have been duplicate UI for no real benefit. Category selection was the one genuinely new piece of app state — nothing before this filtered the visible list to a single category, so that's a small addition to App.tsx, not a reuse of anything.

The part that turned out harder than the palette itself

"Jump to and expand a specific incident" sounded like the smallest of the three targets. It wasn't. IncidentList's open/closed state has always lived entirely inside each card, uncontrolled from outside — exactly right for a visitor clicking to expand one, and exactly wrong for a palette somewhere else in the tree needing to force one open. Fixing it meant giving IncidentCard a forceOpen prop and a ref for scrolling it into view — the first real case in this codebase of lifting a component's local state into something a parent can reach into.

One ESLint rule, two components, same mistake

The obvious way to write "when forceOpen becomes true, open the card and scroll to it" is a useEffect watching forceOpen, calling setIsOpen(true) inside it. ESLint's react-hooks/set-state-in-effect rule flagged it immediately — and then flagged the exact same pattern a second time in the palette itself, where a new search query needs to reset the highlighted row back to the top. Two components, two unrelated pieces of the feature, one identical mistake.

The rule's complaint is specific: calling setState synchronously inside an effect body causes a cascading extra render — React commits once, the effect fires, the effect sets state, React commits again. The fix isn't useSyncExternalStore this time (that's for reading a value that lives outside React entirely, like the system clock — the fix a few sessions back for the days-since-incident counter). This is a different shape of problem: a prop or a piece of state changed, and some other state needs to sync to it. React's own docs have a name for the correct version — adjusting state during render — comparing the current value against a tracked previous one, and calling setState directly in the render body (not inside an effect) the moment they diverge: 

const [prevForceOpen, setPrevForceOpen] = useState(forceOpen)

if (forceOpen !== prevForceOpen) {
  setPrevForceOpen(forceOpen)
  if (forceOpen) setIsOpen(true)
}

The scroll-into-view call stayed in a real useEffect — it's an actual external-system interaction (an imperative DOM call), not a setState, so it was never what the rule was objecting to. Splitting "sync some state" from "touch the DOM" turned out to be the whole fix, applied identically in both places once the pattern was recognized the second time.

Confirming it, not just shipping it

Full manual pass before calling this done: arrow keys move the highlight correctly and stop at both ends instead of wrapping; a service selection opens the detail modal; a category selection filters the list and shows a working Clear control; an incident selection scrolls to and expands that specific card without disturbing any other card's state; / opens the palette from nowhere and doesn't fire while typing inside it; opening it while the detail modal is already open does nothing, by design, rather than stacking two overlays. All of it passed on the first real test run — the two lint catches happened before that point, not during it.

Where this leaves the roadmap

Five of six items from the front-end polish list are built now — SSE is the one deliberately-last item remaining, sized differently than everything else on that list and scoped to wait until the app is otherwise stable. Per the planned session order, the full visual restyle is next — the token system this session's zinc-* classes still lean on already exists from a few sessions back, so that one gets to be color work, not plumbing work.
