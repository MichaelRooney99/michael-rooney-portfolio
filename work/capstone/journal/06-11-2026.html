Session 4 — Proxmox Adapter and Debugging

Last session ended with the Express proxy confirmed working and the Proxmox adapter written but not yet wired in. This session was supposed to be straightforward — connect the adapter, see the data, move on. It wasn't. Three separate issues surfaced before the Proxmox API category rendered with real numbers, and each one taught something worth writing down.

Issue 1 — NaN metrics

First render showed the Proxmox API category appearing under Other with three nodes listed — but every metric showing NaN%. The nodes were connecting and returning as operational, but the CPU, memory, and uptime values were all not-a-number.

The cause: any math operation on undefined produces NaN in JavaScript. The adapter was assuming fields like node.cpu and node.maxmem would always be present, but the /nodes endpoint was returning them as undefined. Adding nullish coalescing fallbacks — node.cpu ?? 0 — stopped the NaN, but everything showed as 0.0% instead. Better, but still wrong.

Issue 2 — the /nodes endpoint doesn't return metrics

Querying the proxy directly revealed the real problem. The Proxmox /nodes endpoint in a clustered setup returns only a summary list — node name, online status, and SSL fingerprint. No CPU, no memory, no uptime. Those fields simply aren't in the response. The initial adapter design assumed flat metrics on the node list, which was wrong.

The fix was a two-stage fetch. First call /nodes to get the list of online nodes. Then call /nodes/{nodename}/status for each one concurrently using Promise.allSettled. The per-node status endpoint returns the full picture — CPU, nested memory object, uptime in seconds. Two calls instead of one, but the data is actually there this time.

One shape difference worth noting: the memory object in the per-node response is nested — { used, total, free, available } — rather than the flat mem/maxmem fields the summary endpoint implies. The interface had to be updated to match.

Issue 3 — Sys.Audit permission

After switching to per-node calls the category disappeared entirely. No error in the UI — just six services instead of nine, no Proxmox API section at all. This is Promise.allSettled doing exactly what it's designed to do: catching all three rejections silently and returning an empty array. The silence that makes the app resilient also makes this class of failure invisible.

Querying the per-node endpoint directly from PowerShell showed the cause immediately: 

{"message":"Permission check failed (/nodes/ankhh, Sys.Audit)\n","data":null}

The prometheus@pve!monitor token's custom role didn't include Sys.Audit. The /nodes summary endpoint doesn't need it. The /nodes/{name}/status endpoint does. Adding Sys.Audit to the role in Proxmox resolved it immediately.

When a category disappears from the status page with no error shown, the first debugging step is to query the relevant proxy endpoint directly. The UI swallows errors by design — the raw response tells the truth. In this case a 403 with a specific permission name pointed directly at the fix.

What the page shows now

Nine services, all operational. Five Proxmox nodes from Prometheus. Three nodes from the Proxmox API directly — Murloc, Ankhh, and Shasta — each showing CPU percentage, memory percentage, and uptime. Ankhh and Shasta showing 42 days 16 hours of uptime confirms the data is real. UPS operational, 48 minutes runtime, 14% load. Overall banner green.

A note on silent failure

The Promise.allSettled pattern in the services facade was a deliberate design choice — partial visibility over blank pages. This session showed both sides of that tradeoff clearly. When the proxy was down or permissions were wrong, the page kept rendering the data it could get. But the failure was invisible without going looking for it. That's the right behavior for a status page facing users — less so for a developer trying to debug why a category isn't showing up. The debugging move is always to test the endpoint directly rather than reading the UI.

What's next

The three primary data sources are all working. Next session moves to the Zabbix adapter — JSON-RPC over HTTP, a different protocol from everything else so far — and then the Cloudflare tunnel for public deployment. After that, incident history and a polish pass before Perry reviews the finished site.
