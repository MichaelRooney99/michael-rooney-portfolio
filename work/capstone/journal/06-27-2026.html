Session 6 — Zabbix Adapter and Four Live Data Sources

Session 5 ended with a deliberate deferral: the Zabbix proxy route was built and authenticating, but Zabbix itself had no hosts configured beyond the Zabbix server, so building a client adapter against empty data wasn't worth doing yet. That gap closed in separate homelab sessions — Zabbix Agent 2 deployed across all five Proxmox nodes, host objects and templates created in the frontend, 606 items collecting. Today's session picked up where Session 5 left off: build the adapter, wire it in, confirm it renders.

What Zabbix uniquely provides

The status page already shows CPU and memory from Prometheus, and CPU, memory, and uptime from the Proxmox API directly. Adding a third source of the same metrics would just add noise. The question was what Zabbix provides that the other two don't.

The answer is agent availability state — a discrete signal, not a time-series metric. Prometheus knows that a node's CPU was at 2.3% five minutes ago. Zabbix knows whether it can reach the node's agent right now, and whether it's been reachable consistently. Those are different things. The adapter is scoped to exactly that: one service per node, status derived from Zabbix agent availability, category Zabbix so it renders as a distinct section.

A permissions gap first

Before writing any adapter code, the proxy sanity check confirmed whether host.get actually returned the five Proxmox nodes: 

{"jsonrpc":"2.0","result":[{"hostid":"10084","name":"Zabbix server","status":"0"}],"id":1}

Only the Zabbix server. The api-readonly user was in the API Read Group but that group didn't have read permission on the "Proxmox Nodes" host group. Added Read permission in Administration → User groups → API Read Group → Permissions, re-ran the check, and all six hosts appeared. Worth checking permissions before writing code that will silently return empty data if they're wrong.

The adapter

src/services/zabbix.ts follows the same pattern as the other adapters — one exported function, one internal helper, interfaces for the API response shapes. The queryZabbix helper POSTs to /zabbix on the proxy and handles error checking. The exported fetchZabbixStatus calls host.get, filters out the Zabbix server entry, and maps each host to a ServiceStatus object.

The Zabbix server itself — hostid 10084, name "Zabbix server" — appears in every host.get response because it's a monitored host in its own right. It's not a Proxmox node and doesn't belong on the status page. A simple .filter(host => host.name !== 'Zabbix server') before the map handles it cleanly.

The availability field that wasn't there

First render showed all five Zabbix nodes appearing — but every one showing Unknown rather than Operational. The adapter was reading host.available to determine status, but the API response didn't include that field at all despite it being in the output array.

Running the raw host.get query confirmed it: available simply wasn't coming back on the host object. In Zabbix 7.x, agent availability moved out of the host-level available field and into the interfaces object. The old field is deprecated. The correct approach is to add selectInterfaces: ['type', 'available'] to the query params, then find the agent interface (type === '1') and read its available value.

Running the raw API query directly is always faster than reading source code. The response either contains the field or it doesn't. In this case it didn't, which pointed immediately at a version difference in how the API works rather than a bug in the adapter code.

After switching to selectInterfaces, the sanity check returned: 

{"hostid":"10780","name":"network","status":"0","interfaces":[{"type":"1","available":"1"}]}

All five nodes returning "available": "1". Updated the adapter, reloaded, all five showing Operational.

Wiring into the facade and UI

The facade change is two lines — one import and one entry in the Promise.allSettled array. Nothing else in the data layer needed to change. That's the facade pattern working as intended: adding a new data source means touching exactly one file outside the adapter itself.

The UI needed one additional change. App.tsx uses a fixed CATEGORY_ORDER array to group and sequence services, with anything not in the list falling into "Other." 'Zabbix' wasn't in that list, so the five nodes were landing in Other rather than their own section. Adding it to the end of the array put them in the right place.

What the page shows now

Fourteen services across four data sources, all operational. Five Proxmox nodes from Prometheus with live CPU and memory. Three nodes from the Proxmox API with CPU, memory, and uptime. CyberPower UPS from NUT with flags, runtime, and load. Five nodes from Zabbix showing agent availability state. Overall banner green.

The four data sources are meaningfully distinct. Prometheus tracks what happened over time. The Proxmox API shows hypervisor-level state. NUT monitors power. Zabbix confirms agent reachability. Each one is answering a different question about the same infrastructure.

What's next

The data layer is complete. Every planned source is wired in and rendering live data. Next session moves to deployment: Docker Compose to bundle the React client build and the Express proxy into a single deployable unit, and the Cloudflare Zero Trust tunnel to make the status page publicly accessible at status.michaelrooney.dev without opening any inbound ports.
