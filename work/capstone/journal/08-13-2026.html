Session 32 — One Push, Three Networks, Zero Commands

The webhook and rollback logic were both already proven working a session ago — but only by bypassing Cloudflare entirely, triggering the receiver and the playbook directly. What was still missing was the actual front door: the part that lets a real GitHub Actions job, sitting on infrastructure with no path into this network at all, reach in and trigger any of it. That's what this session closed.

The individual pieces — a Cloudflare tunnel, a service token, an Access policy — each made sense on their own. What didn't click until sitting down and tracing it start to finish is that a single deploy actually crosses three completely separate networks, each with its own authentication, each unaware the other two exist. That separation is the actual reason this took real, careful work to wire up — and it's also the thing that makes the whole system trustworthy once it's done. Worth walking through properly, in order, rather than just listing what got built.

Leg one: the public internet, gated by Cloudflare Access

This leg starts the instant git push finishes and ends the moment a request either gets rejected or reaches this homelab's front door. Nothing in it happens on this network — it's GitHub's servers and Cloudflare's edge talking to each other, entirely outside anything this project controls directly.

A push to main fires the two existing CI jobs first — client and proxy, unchanged from before. Only once both genuinely pass does a third job wake up: trigger-deploy. Its entire job is one HTTP request — a POST to a URL (deploy.michaelrooney.dev/deploy) that resolves, via DNS, to two Cloudflare IP addresses, not anything on this network. Attached to that request are two headers carrying a service token — not a password typed by a human, a credential meant specifically for one machine to hand another.

That request never gets anywhere near this homelab yet. Cloudflare's edge intercepts it first, checks the token against the Access policy configured for that exact hostname, and makes a binary decision right there. Sent with no token at all, the real response was a clean 403, an actual Cloudflare-branded error page, proof the policy is genuinely enforcing something rather than just existing unused. Sent with the real token, the request is allowed through — and Cloudflare attaches a second credential of its own, a signed JWT, as proof to whatever's on the other end that this specific request already passed a real check.

Only past that gate does the request enter the second leg at all — through a tunnel connection that the receiving side already opened outward, before any of this ever happened, and keeps open continuously. No port was ever opened inward on this network for any of this to work. The direction of connection never reverses.

Leg two: the private LAN, no Cloudflare involved at all

Past the tunnel, everything is different. There's no more Access policy, no more public internet, no more Cloudflare in the loop at all — just a small Flask process listening on a single internal port, and everything from here happens entirely inside this network's own boundaries.

That process does almost nothing on purpose. It doesn't re-check the token — Cloudflare already did, and checking twice would just be duplicating a decision that's already been made correctly. It writes a lock file so a second near-simultaneous trigger gets rejected instead of starting a competing deploy, hands the real work to a background thread, and responds immediately. That immediate response is the entire reason the GitHub Actions job finishes in about two seconds even though the actual deploy takes far longer — the job only ever waited to hear "started," never "finished."

What happens in that background thread has nothing to do with Cloudflare, tunnels, or tokens at all — it's the exact same ansible-playbook command that's been run by hand dozens of times this project, connecting over plain SSH, on the internal LAN, to the actual capstone host. Every layer already built and proven — the test gate, the health check, the smoke test, the rollback — runs here, completely unaware that anything upstream involved Cloudflare at all. From this playbook's own point of view, a webhook trigger and a person typing the command by hand are indistinguishable.

Leg three: reporting out, a second and entirely separate trip to the internet

The last leg starts only once the deploy itself either succeeds or fails, and it goes back out to the internet a second time — but through a completely different door than the first leg used. The Ansible play, running on internal infrastructure, sends a plain internal request to an existing alert relay already sitting on this network — no tunnel, no Access policy, nothing shared with leg one at all. That relay is the one that actually reaches out to Discord, using its own separate webhook, entirely unrelated to anything Cloudflare was involved in.

That's genuinely why the message can show up in Discord a little while after the GitHub Actions job itself already shows green — they're not the same event. The job succeeding only ever meant "the trigger was accepted." The Discord message means the actual deploy, minutes later, finished — and it's reporting through a path that never touched Cloudflare, GitHub, or the tunnel at any point.

What actually went wrong along the way, and why each was worth catching slowly

None of this worked on the first attempt, and every failure pointed at a real, specific boundary between these three legs.

The service type on the tunnel's public hostname route got set to HTTPS by default — but the receiver only speaks plain HTTP internally. Cloudflare terminates real TLS at its own edge regardless; asking it to also speak TLS to an origin that never offered any just breaks leg two before it starts. A quick fix once spotted, but a real reminder that "public HTTPS" and "internal HTTP" are two independent choices, not one setting.

After the route was fixed, the exact same request that had just failed to resolve at all started resolving to a real answer within Cloudflare's own DNS, but kept failing to resolve through the internal resolver specifically — a genuine negative-cache issue, the internal DNS server having asked once, correctly gotten "doesn't exist yet" at that exact moment, and cached that answer. Confirmed by comparing the exact same query against Cloudflare's own resolver directly rather than guessing — one worked, one didn't, and that difference was the actual diagnosis.

The Access policy itself came with its own built-in warning, caught before it ever got saved wrong: an Allow action paired with only a service-token selector is a real, common misconfiguration, since Allow assumes a human logging in through an identity provider — exactly what a machine credential can't do. The fix was switching to Service Auth specifically, a genuinely different policy type built for exactly this case, not just a stricter version of the same one.

And the very last gap, the one that actually could have shipped silently wrong: the Access Application itself never got its own final save, buried a step behind the policy editor that was being worked in. Found the only real way it could be — testing the unauthenticated request and getting a clean 200 back instead of the expected rejection, immediately proving something was configured but not yet enforcing anything.

What actually proved it, at the end

Not the Actions job turning green — that only confirms leg one. The actual proof needed three separate pieces of evidence, one from each leg: the GitHub Actions run itself showing a real 202 instead of an instant failure, the receiver's own log file on the internal network showing a real trigger and a real success tied to the exact commit SHA that was pushed, and a genuine message landing in Discord through the completely separate reporting leg, timestamped a little after the Actions job finished, exactly as the mechanism predicts.

All three lined up. A commit landed on main and, entirely on its own, ended up live — no command typed anywhere in the loop, three independent networks each doing their own small piece, none of them aware the others existed.
