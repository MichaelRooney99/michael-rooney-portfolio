Session 34 — Starting From a Real Outage and Working Backward

The first full read-through of this codebase went forward — types first, then the layers that build on top of them, one at a time, ending at deployment. This session deliberately went the other direction: pick something real and visible, and trace it backward to find out where it actually came from. Different exercise entirely, and it turned up things the forward read never would have.

A prediction, confirmed on real data

A few sessions back, a real question came up about what happens to a service that goes down for less than the 30-minute incident threshold — the honest answer at the time was reasoned through the code, not observed. This session, that exact scenario happened for real: a live host, deliberately powered off briefly, produced a genuine red day on its uptime history and, correctly, no drafted incident. Pulling the raw data confirmed it precisely — one bad poll reading, sandwiched between two good ones roughly fifteen minutes apart on either side, never crossing the two-consecutive-reading threshold that would have triggered a real incident record. Reasoning about code and watching it happen for real are two different kinds of confidence, and this was the second kind.

The same physical host, tracked twice, briefly disagreeing

Tracing that outage backward surfaced something genuinely unplanned: the exact same physical machine shows up on this page as two separate services, tracked through two completely independent pipelines with two different IDs — one from a generic node-exporter query that doesn't filter by cluster membership, one from a real Zabbix host entry. For a real moment, live, those two disagreed with each other — one showed operational, the other's history showed an outage for that same day. Not a bug. Two different sources answering two different questions ("what's true right now" versus "did anything happen today") at slightly different moments, both honestly. Worth remembering that one machine and one service aren't always the same thing in this system.

A real misconception, caught and corrected

The most useful moment of the session wasn't a discovery — it was being wrong about something specific enough that the correction actually stuck. The assumption: the per-service detail view must be getting pushed live updates the same way the main status list does, through the existing nudge mechanism. It isn't. The nudge system only ever invalidates one specific piece of cached data — the main list — and the detail modal's own cached data lives under a completely different key that nothing in this app's own live-update logic ever touches. If the detail view refreshes on its own at all, it's because of the query library's own generic, built-in behavior — refetch when the tab regains focus — nothing this project specifically built. Two systems that look connected because they're built with the same tool aren't automatically wired together at all.

What a click actually sets in motion

Tracing the detail modal's own trigger chain turned out to be longer than it looked from a single line of code — a click doesn't fetch anything by itself. It updates one piece of state in the parent component; that state change is what causes the modal to even exist in the render tree for the first time; only once it actually mounts does its own internal data-fetching hook run for the first time. Four real, distinct steps between "clicked" and "a request left the browser," not one.

.map() and what it actually buys

The realization that stuck hardest today: the whole reason adding or removing a monitored service touches zero lines in the rendering code isn't really about any one clever trick — it's that a loop over an array, paired with every adapter honoring one shared shape agreed on all the way back at the very start of this walkthrough, means the rendering layer never has to know how many services exist or what kind any particular one is. The moment something conforms to the agreed shape, it's just one more item the loop happens to run over.

That same array, memoized, was the other half of today's lesson — and specifically, working through two separate memoized computations sitting right next to each other, only one of which actually saves anything during normal use, was worth more than either one alone would have been. The one that looks like it should help during typing doesn't — its own dependency list includes the very thing that changes on every keystroke. The one that actually pays off protects something else entirely: keeping a stable list while navigating it with arrow keys, not while filtering it with text.

Presentational versus container, and a real counter-example

Comparing the detail modal against the command palette directly — both full-screen overlays, both managing real internal state — was the cleanest way to see that the actual dividing line has nothing to do with looking like a modal. One fetches its own data on mount; the other receives everything it needs as props from its parent, same as the plainest presentational row component in this whole app. Two components that look like the same UI pattern can sit on opposite sides of that line, depending entirely on whether they're viewing data someone else already has, or actively going and getting their own.

What TypeScript actually knows, versus what's actually true

The smallest, and maybe most durable, thing from today came from three characters: as. A single line reads a child element out of a list by index, then explicitly asserts a more specific type than what the DOM's own generic typing could ever prove on its own. Checking the real inferred type directly, rather than assuming it, confirmed exactly why the assertion exists — TypeScript's own indexing types can't know that this specific list only ever contains one kind of element, because the browser's generic collection types have to stay honest about every possibility, including ones that don't apply here. The assertion isn't papering over a gap in the type system. It's the developer supplying something true about this one specific piece of code that the compiler has no way to know on its own. Worth writing down exactly as it came up: the point of a type isn't just to make something compile, it's to have the type reflect what's really true, not just what's minimally required to pass.

Where this leaves things

A second read-through, genuinely different in shape from the first, and enough real ground covered to call the overall understanding solid in places, still forming in others — an honest place to be, not a finish line. A third pass is planned, later, once the two open scope decisions from a couple sessions back are actually settled — by then there should be real code changes worth walking through again, not just more reading of what's already there.
