Session 48 — The One-Page Version of Everything

With both code-review passes done, this session had one real job: write the document that answers "why is this built this way" without making anyone go dig through the actual commit history to find out. The result is a real ARCHITECTURE.md now living in the repo itself, built around one diagram, a request-lifecycle walkthrough, and a decisions index that explains itself without pointing anywhere else.

Two flows, drawn separately, on purpose

The diagram splits cleanly into two halves that share almost nothing at the edge: the live application, and the deploy pipeline that ships changes to it. That's not a layout choice, it's the actual shape of the infrastructure — two independent Cloudflare tunnels, two different Access policy types. The public tunnel is read-only from the internet's perspective; the deploy tunnel is the only write-capable edge surface in the whole system, and it's gated by a service-token policy built for a machine, not an identity-based policy built for a person logging in. Drawing them as one undifferentiated "Cloudflare" box would have hidden the one distinction that actually matters here. For anyone curious about the general approach behind a diagram like this — one page, every real component, nothing abstracted away — the C4 model is a well-known reference point for that kind of system-level view.

Verifying the deploy pipeline against the real scripts, not memory

The deploy pipeline hadn't come up directly in either review pass, so writing about it accurately meant going back to the actual source instead of reconstructing it from what a past session's journal entry said about it. Pulling the real webhook receiver script and the real Ansible playbook confirmed a few specific details worth having exactly right: the receiver runs a deploy in a background thread and returns a 202 immediately, specifically because the triggering HTTP client — GitHub Actions — would likely time out holding a connection open for a full deploy's duration. The playbook captures the current commit as its own first step, before touching anything else, so the rollback target always exists before there's anything to roll back from. And the rollback path still fails the overall run even after a successful rollback — a real, deliberate distinction: the service recovering is not the same thing as the requested deploy having succeeded.

A decisions index, not a decisions repeat

The temptation with a document like this is to re-explain every decision from scratch. Instead, the index is a short table — decision, one real sentence of reasoning — pulled from judgment calls tracked throughout the project as they actually got made, not reconstructed from memory at the end. A few of them are worth naming here because they show the same pattern repeating in different subsystems: duplicating a small piece of status-derivation logic across three files instead of building shared-package tooling for something that small, a hybrid live-update signal that tells the client to refetch early instead of pushing real state over the wire, and staying on manual deploys for most of this project's life before CD was ever justified. Same underlying instinct each time — the cheaper option, and a real reason it isn't a compromise.

Where this leaves things

The diagram now also exists as a PDF for anyone who'd rather open it directly than browse to GitHub. That closes out the architecture documentation. One real deliverable left on this project now — a portfolio case study, external-facing and narrative rather than technical, which is a genuinely different kind of writing than anything in this entry.
