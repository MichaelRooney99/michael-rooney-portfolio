August 25, 2026 Reflection

The Status Page Was Never the Point

The actual problem this project set out to solve is small. Scrape a few APIs, roll the results up into a status, show it on a page. That's genuinely it — the whole brief, honestly described. Nothing about that brief requires a CD pipeline with automated rollback. Nothing about it requires an auto-drafted incident system with its own threshold logic. Nothing about it requires a full test-coverage audit across ten files, or a real production test where a monitoring source got deliberately blocked from reaching the site, timed against a 15-minute poll interval, just to prove a single status value renders correctly. A minimal, entirely reasonable version of this project would have taught me React components and how to call fetch.

That's not what happened, and sitting with why felt worth writing down before starting the last real stretch of this — two more code-review passes, then the two scope docs that were always meant to come last.

What the overbuilt version actually taught

None of the real complexity in this project came from the brief. It came from a question that kept showing up after each piece already worked: what happens when this breaks. That question is where the CD pipeline came from — not because deploying manually was hard, but because a bad deploy should recover itself. It's where the auto-incident threshold logic came from — not because manually noting an outage was hard, but because a real outage shouldn't depend on someone happening to be watching. It's where an entire session spent deliberately breaking a monitoring source on purpose, then chasing down two wrong guesses about why the result looked wrong, came from — not because the feature needed proving on paper, but because the only way to actually trust it was watching it survive something real.

A tutorial-sized version of this project would have taught me how to build a status page. The version that kept asking "what happens when this breaks" taught me how production systems actually behave under stress, and — more honestly — taught me to stop trusting my own first explanation for anything and go check the real source instead. That habit showed up everywhere by the end: real proxy logs over guessing, a real database query over assuming, a real firewall rule over a comfortable theory.

The actual list

Design structure and component boundaries. Real scope and documentation discipline — writing a decision down before building it, and correcting the doc when the real implementation didn't match the plan. Backend work that went well past a simple proxy — caching, persistent storage, a real database schema that had to evolve without breaking existing data. Ansible, treated as the actual right way to manage infrastructure rather than a set of manual steps typed once and forgotten. A real CI/CD pipeline, built and tested in both directions — not just the deploy that succeeds, but the one that's supposed to fail safely too.

None of that was required by "scrape some APIs, show a status." All of it came from choosing the harder, more realistic version of each piece instead of stopping at demo-quality. That's the actual honest answer to why a status page ended up with this many logged sessions behind it — not a scope-management failure, a deliberate one, made over and over, to keep building the version of each feature that would actually hold up.
