Session 43 — Teaching the Poller to Remember What It Just Saw

A real gap flagged a couple weeks back, finally closed: this status page has never been able to tell "the monitored thing is down" apart from "the monitoring itself couldn't check." Both looked identical — a quiet grey day, or nothing at all. The one blind spot a status page probably shouldn't have is its own visibility.

The real wrinkle: no data to work with when it matters most

The obvious plan was: when a poll fails outright, write an explicit "we couldn't check" reading instead of writing nothing. The obvious plan broke immediately on inspection — the poller only ever learns which specific services exist from the very API response it's trying to poll. If that call throws before it's ever parsed, there's no list of service ids left to attach anything to. You can't record "X was unreachable" if the failure itself is what stops you from knowing X existed in the first place.

The fix: a small, in-memory cache of whichever ids were last seen on a genuinely successful poll, updated only when a check actually works. A failed poll now falls back on that memory instead of a blank slate. A source that's never once succeeded — a fresh deploy, or one down from the very start — correctly still records nothing, since there's genuinely no known list to work from yet. That's not a gap in the fix; it's the honest limit of what "remembering the last known state" can promise.

A fallback that has to lose to real data, every time

The harder design question lived in the history rollup itself. A day that's genuinely unreachable and a day that's genuinely quiet both need to end up looking different from each other — but a day can have both an unreachable reading and a real one, if the source came back partway through. Real data has to win in that case, unconditionally. The fix keeps two separate trackers while scanning a day's readings instead of one — the existing "worst real severity" logic, completely unchanged, plus a second, independent flag for "was anything unreachable today at all." Only once both are known does the day's final status get decided: real severity first if it exists, the unreachable fallback second, and only genuine silence falls all the way through to the same "no data" result this page has always shown for that.

The clearest way to prove that ordering held was to test it directly against its closest existing neighbor — a day with an unreachable reading sitting right next to a real one, same shape as the test already proving an "unknown" reading can't hide a real outage. Same principle, a genuinely different reason it has to hold.

Where this leaves it

The mechanism itself is done and tested — real in-memory database tests, no mocking, same standard as everything else in this file. What's left is making this actually visible to a visitor: a real color and label in the uptime bars, and the live page's own version of the same honesty, for the moment a source fails mid-request rather than during history collection.
