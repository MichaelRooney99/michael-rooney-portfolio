Session 17 — Auto-Drafted Incidents, and the Build Assumption That Wasted Twenty Minutes

The last item off 16-Next-Round Functionality, and the one that doc itself called out as the biggest architectural lift of the four — worth taking that framing seriously rather than treating it as just another feature ticket.

The conflict this was always going to run into

incidents.json is bind-mounted read-only into the proxy container on purpose — it's meant to be a hand-edited, git-tracked file, and the running proxy genuinely cannot write to it no matter what the code tries. Auto-drafting an incident from the poller can't target that file without either removing the read-only guarantee (real data-loss risk the next time someone edits it by hand and redeploys) or finding it a different home. It got a different home: a new drafted_incidents table in snapshots.db — the same SQLite file the history poller already writes to, on the same named Docker volume that already survives every redeploy. No new infrastructure, one more table in infrastructure that already existed.

Deriving the threshold instead of tracking it

The obvious way to detect "two consecutive outage readings" is an in-memory counter in poller.ts — increment on outage, reset on recovery. Didn't do that. A counter like that resets silently on every proxy restart or redeploy, quietly losing track of exactly where a service was mid-streak. Instead, the check re-reads the last two rows from the snapshots table directly, every time. Slightly more database work per tick, for a handful of services on a 15-minute cadence — a genuinely free trade for not having a second, more fragile source of truth about the same question the table can already answer.

Testing this took real production, not a click-through

Everything before this session could be verified by loading the page and looking at it. This one couldn't — there's no UI action that fakes "a service has been down for 30 minutes." Testing it meant SSH'ing into the actual capstone VM and calling the real database functions directly against production data, then cleaning up afterward so a fake test incident didn't sit on the live site telling Perry something untrue.

First attempt at that test was wrong in an instructive way: manually inserting two outage rows into the snapshots table doesn't actually test the drafting logic, because the threshold check only ever runs as a side effect inside the poller's own tick, immediately after it records a real reading. A raw insert writes data nothing then reads. The fix was testing the drafting function directly — calling createDraftedIncident itself, independent of both the fake rows and the real poll cycle — which is actually the more honest test anyway: it isolates exactly the piece of logic in question instead of hoping a chain of side effects happens to line up.

The twenty minutes that shouldn't have been necessary

Locating the deployed code to test against took longer than it should have, because of a wrong assumption carried in from earlier project notes: that the proxy runs tsx directly against live .ts source in production, no build step. It doesn't. Checking the actual container directly — find / -name "db.ts" — turned up nothing at all outside node_modules, and tsx itself wasn't even installed, needing a fresh npx download. The real answer was sitting one file over the whole time: 08-Express Proxy.md already documented "build": "tsc" and "start": "node dist/index.js" correctly. The doc was right. The assumption carried in from somewhere else wasn't, and didn't get checked against the doc that already had the answer before costing real time chasing a file that was never going to exist.

Confirmed against the real thing

Full round trip on the actual production container: created a drafted incident directly, confirmed it through /incidents with the correct shape and source: 'auto', resolved it and confirmed the status flip and the appended update, then cleaned up both the test incident and the two fake snapshot rows so nothing false was left in real history. The live site showed the actual investigating badge correctly during the test — the first real end-to-end confirmation of the whole pipeline, not just the database layer in isolation.

Where this leaves things

16-Next-Round Functionality is fully closed now — 4 of 4. One item left project-wide: the SSE/real-time nudge channel, deliberately saved for last since it benefits most from everything else already being stable, which it now is.
