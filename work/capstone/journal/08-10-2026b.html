Session 26 — Three Bugs, a Disk, and an Idempotency Check That Actually Worked

Idempotency verification — running a playbook twice and confirming the second run reports no changes — was scoped weeks ago for the three playbooks with the worst real history, and never built. Built it today, and it earned its keep on the very first real run.

A script, and where it actually has to run

verify_idempotency.sh is simple in concept: run a playbook, run it again immediately, and fail loudly if the second run's recap shows anything other than changed=0 across every host. First real snag — it can't run from a Windows machine at all. ansible-playbook needs a real Linux environment, which is exactly why this project's actual Ansible control node lives on a dedicated LXC in the first place, not on whatever machine happens to be open at the time.

Bug 1 — the script itself, hiding its own failures

First real run against zabbix_agent.yml hit a genuine host failure (network — more on that below) partway through the first pass, and the script just... stopped. No explanation, nothing pointing at what happened — set -e killed the whole thing silently the moment any command inside it returned non-zero. Fixed by checking the first run's own recap explicitly before ever attempting a second run, and printing exactly which host and which failure caused the abort. Small fix, but it's the difference between a tool that tells you what went wrong and one that just goes quiet.

The detour: a corrupted UUID and a silently full disk

That first real host failure was network (Node 0) failing an apt cache update with No space left on device. df -h confirmed root at 100% full — 65G used on a 68G disk. Working backward through du (and hitting a real GNU-coreutils gotcha along the way — -s and --max-depth=1 are mutually exclusive flags, silently producing nothing instead of erroring) led to /mnt/usb-backup: 50G, sitting directly on the root filesystem, not on any actual mounted drive. The real USB drive's UUID in /etc/fstab had one group of characters transposed — 5779 instead of the drive's real f579 — and because the mount used nofail, the boot process just silently skipped it instead of complaining. A nightly vzdump backup job had been dutifully writing into the empty fallback directory instead, for who knows how long, with zero indication anything was wrong until the disk actually filled.

PBS already had complete, confirmed coverage of this host, and OPNsense's config is separately repo-tracked — so this wasn't a real backup gap, just redundant. Retired it properly rather than just deleting files: removed the scheduled vzdump job through the Proxmox UI, removed the storage definition with pvesm remove, cleaned up the stale fstab line, and only then cleared the actual files. Root filesystem went from 100% to 24% used. The real value here isn't the disk space recovered — it's that a months-old, completely silent problem got found specifically because a testing tool was run for real against real infrastructure, not because anything was monitoring for it.

Bug 2 — the version check reading the wrong output stream

Back to the actual idempotency work. node_exporter.yml's "is this already installed" check compared the target version against ne_installed.stderr — but node_exporter --version writes exclusively to stdout, confirmed directly rather than assumed (2>/dev/null vs 1>/dev/null, the text only survived the first one). Checking the wrong stream meant the comparison was always true, no matter what was actually installed — which made six otherwise-correct tasks (download, extract, copy, cleanup) look non-idempotent, when the install itself had been fine the whole time. One word, stderr → stdout, and the first run against a system that already had node_exporter 1.8.1 installed went from changed=8 to changed=0, immediately.

Bug 3 — a raw command with no idempotency logic at all

new_node_setup.yml's Prometheus-user ACL assignment was a bare ansible.builtin.command running pveum aclmod, with no changed_when and no when at all — Ansible's default for the command module is to report changed: true unconditionally, every single run, regardless of whether anything actually changed. Fixed by adding a real check first — pveum acl list --output-format json, parsed for the specific ugid/roleid pair — matching the exact pattern the task right above it already used correctly for user creation.

First attempt at pasting that fix in didn't actually take — the check task was there, but the when: condition gating the assignment itself never made it into the file. Caught by cross-checking two independent, real pveum acl list outputs (one from network, one from dega) against what the playbook was actually reporting, rather than trusting that a paste landed correctly. Once genuinely in place, both hosts went straight to skipping on the assignment task, on the very first run — the real ACL state had been correct the whole time, only the check was missing.

Bug 4 — the idempotency script losing its own eyesight

Small, but worth naming since it's a real class of bug on its own: forcing colored Ansible output (ANSIBLE_FORCE_COLOR=true, so the script's terminal output would match a normal interactive run) embedded real ANSI escape codes into the log file the script parses for its pass/fail decision. The recap-matching regex expected a clean line starting with a hostname — with invisible color codes sitting in front of it, the pattern matched nothing at all. The script fell through to PASS not because it verified changed=0, but because it found nothing to check and had nothing to flag as a failure. Correct answer that particular run, for the wrong reason — a silently blind check is exactly the failure mode this whole script exists to prevent, just relocated into the tooling itself. Fixed by stripping ANSI codes before parsing, while leaving the real terminal output and log file fully colored for a human to read.

Where this actually lands

All three targeted playbooks — zabbix_agent.yml, node_exporter.yml, new_node_setup.yml — confirmed genuinely idempotent now, not just believed to be. Four real bugs found doing it, only one of which was actually in the playbooks' own application logic (node_exporter.yml's stream mismatch) — the other three were split between a missing safety check, a paste that silently didn't take, and the verification tooling itself briefly losing the ability to see what it was checking. That's the actual argument for building this layer at all: not one bug, a whole class of them, none of which were visible from reading the code, only from running it for real and watching closely enough to notice when the tool itself might be lying.
