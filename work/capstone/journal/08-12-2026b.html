Session 31 — A Deploy Broke Itself on Purpose, and Fixed Itself Too

The last real piece of the deployment pipeline — a webhook that triggers a deploy automatically on every push to main, and automated rollback riding alongside it, since the decision made a session earlier was explicit: build these two together, not one after the other, because the moment the webhook ships is the exact moment deploys stop being watched in real time.

Four decisions before any code

Same discipline as everything else this project has built — talk through the shape before touching a file. Four real questions, not one: where does the thing that receives the trigger actually run, how does an automated system authenticate through an access layer built for humans, what does "rollback" concretely mean given how the deploy is already gated, and how does anyone find out it happened.

The receiver landing on the Ansible control node rather than the capstone host itself wasn't a coin flip — the capstone host is the thing being redeployed, so triggering from inside it is circular. The authentication question turned out to be the one place "reuse the existing pattern" wasn't quite literal: the admin panel's access control is identity-based, a human logging in. A GitHub Actions job has no browser. The real answer was a service token — same underlying product, a genuinely different policy type.

Testing the receiver before it ever touched real infrastructure

Before any of this went near the actual control node, the webhook receiver got built and run against a fake stand-in for the deploy command — same server, same lock-file logic, same background-thread handoff, just pointed at something harmless. That caught the concurrency behavior working correctly (a second request while one's already running gets a real rejection, not a silent double-deploy) before it ever had the chance to matter against something real.

A real access gap, found by actually trying it

The plan assumed the control node could manage itself the same way it manages every other host in the fleet. It couldn't — the account existed, but had no key and no sudo access configured on itself, since nothing had ever needed to treat it as a target before, only as the place commands run from. Not a bug in anything built this session, just a real gap that only showed up by actually trying the connection instead of assuming it would work because everything else always had.

Three bugs in an alert relay, caught one at a time

Wiring deploy notifications into the existing alert relay surfaced three real, separate problems in that file — an entire dictionary of message templates that had gone missing, a duplicate function definition, and a character- encoding issue that kept corrupting the same two symbols through several rounds of copy-paste before the actual fix was to stop fighting the terminal's encoding and just not use those characters at all. None of these were subtle bugs requiring deep debugging — they were the kind that only show up by actually running the code and watching what happens, not by reading it and deciding it looks right.

Proving the happy path, then breaking it on purpose

A real trigger, a real deploy, a real success message landing in a dedicated Discord channel — separated from the existing alert noise specifically so a deploy notification never gets lost in routine backup messages. That confirmed the whole chain works when everything goes right. It proves nothing about what happens when something doesn't.

So: a scratch branch, one route deliberately rewritten to return a real 500, triggered as a real deploy. The test suite passed cleanly — nothing in it exercises the live HTTP route, so a broken route sails right through. Compose came up. The health check passed, since it never touches the broken route either. Then the smoke test hit the real failure, retried three times, and failed for real — and that's the exact moment this session's entire second half was actually about proving: the deploy checked out the exact commit that was live before this run started, rebuilt, re-verified health, and a rollback notification landed in Discord with the real reverted commit and a real passing health check. The site was broken and then it wasn't, inside about a minute, and nobody had to notice on their own to fix it.

The detail that would have made this fail silently

Worth writing down specifically, since it's non-obvious and genuinely mattered: Ansible's own documented behavior is that once a rescue block completes successfully, the original failure gets reverted for the purposes of the run's overall status — the play continues as though the failing task had actually succeeded. Left at that, a successful rollback would have made ansible- playbook exit with a plain success code, with nothing anywhere signaling that the requested deploy had actually failed. The rescue block ends with an explicit failure instead, on purpose — service gets restored, and the run still reports itself as failed, because the code that was supposed to go live didn't. Two different, both true things, and the second one is arguably the more important of the two.

This closes out the CD pair — both directions now proven against real infrastructure, not just read and trusted. Cloudflare's own configuration is the one piece still left entirely manual, dashboard work with no way to script it from here.
