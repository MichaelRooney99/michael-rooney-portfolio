# michaelrooney.dev

Personal portfolio and build journal. Static site, no framework, no build step — plain HTML, CSS, and vanilla JS, deployed as-is.

**Live:** [michaelrooney.dev](https://michaelrooney.dev)
**Author:** Michael Rooney

---

## What this is

A portfolio site with a public build journal attached to it. The journal is the actual point — session-by-session notes on homelab infrastructure, front-end work, and Network+ study, written to be readable by someone who isn't already inside my head. Two dedicated sub-journals live under `work/`, each tracking a separate project with its own landing page and update history:

- **Capstone** (`work/capstone/`) — the Madison College internship capstone, `status.michaelrooney.dev`. Has its own hours log against a 216-hour floor.
- **leftfootLabs** (`work/leftfootlabs/`) — a side venture selling 3D-printed homelab rack kits. No hours tracked; not an internship deliverable.

No React, no bundler, no npm install. Every page is a hand-written `.html` file sharing one stylesheet and one script file.


**Nav is identical across every page**: `MR` logo → home, then `Work` / `About` / `Journal` / `Contact`, plus a `Capstone` link that only appears active on pages inside `/work/capstone/`. Relative paths shift by directory depth — one level up inside `/journal/`, but **three** levels up inside `/work/capstone/journal/` and `/work/leftfootlabs/journal/` (`../../../css/styles.css`, `../../../index.html`, etc.), since those entries now sit two directories deeper than a general `/journal/` entry. This is the most common copy-paste mistake when starting a new entry from an old one — doubly so since the capstone move, since older entries copied as templates may still carry the old two-level-up paths. Landing-page back-links are a related, separate trap: a file has been found pointing two directories up when its landing page actually only sits one up — always verify the real link resolves, don't assume from a sibling file's pattern.

**`journal/` vs `work/capstone/` vs `work/leftfootlabs/` — how to tell which one a new entry belongs in:** determined by content, not date.

- Capstone-app work (the status page itself — features, bugs, deploys) → `work/capstone/journal/`, needs an hours table row.
- leftfootLabs work (rack design, print tests, storefront) → `work/leftfootlabs/journal/`, no hours row.
- General homelab/Ansible/networking/cert work → `journal/`, no hours row.

## Journal entry anatomy

Every dated entry — general, capstone, or leftfootLabs — follows the same internal structure:

```
<head>         ← full meta block: title, description, robots, OG, Twitter card,
                  canonical, JSON-LD BlogPosting schema — see Metadata & SEO below
entry-header   ← title, date, tags
entry-meta     ← reading time / category chips
prose          ← the actual write-up, semantic headings, internal + external links
entry-nav      ← prev/next links to adjacent entries
```

Capstone entries additionally carry a **Session N** heading (sequential, continuous — never restarts) and contribute a row to the hours table in both `work/capstone/capstone-index.html` and the capstone Obsidian doc (`00-Overview.md`). leftfootLabs entries are dated but not session-numbered, and don't touch any hours table.

## Metadata & SEO/AEO

Every dated entry's `<head>` carries a full metadata block — this isn't optional boilerplate, it's load-bearing for three separate things: search engines, social link previews, and the feed/sitemap generator, which parses these exact fields rather than the prose body.

**Required fields, every entry:**

```html
<title>Entry Title — Michael Rooney</title>
<meta name="description" content="..." />
<meta name="robots" content="index, follow" />
<meta name="author" content="Michael Rooney" />
<meta property="og:type" content="article" />
<meta property="og:title" content="Entry Title — Michael Rooney" />
<meta property="og:description" content="..." />
<meta property="og:url" content="https://michaelrooney.dev/.../entry.html" />
<meta property="og:site_name" content="Michael Rooney" />
<meta property="og:image" content="https://michaelrooney.dev/img/og-image.png" />
<meta property="og:image:alt" content="Michael Rooney — homelab and software development portfolio" />
<meta name="twitter:card" content="summary_large_image" />
<meta name="twitter:title" content="Entry Title — Michael Rooney" />
<meta name="twitter:description" content="..." />
<meta name="twitter:image" content="https://michaelrooney.dev/img/og-image.png" />
<meta name="twitter:image:alt" content="Michael Rooney — homelab and software development portfolio" />
<link rel="canonical" href="https://michaelrooney.dev/.../entry.html" />
<script type="application/ld+json">
{ "@context": "https://schema.org", "@type": "BlogPosting", "headline": "...", "description": "...", "datePublished": "YYYY-MM-DD", "url": "...", "author": { "@type": "Person", "name": "Michael Rooney", "url": "https://michaelrooney.dev" } }
</script>
```

**Why the duplication (title / og:title / twitter:title all carry near-identical text) is intentional, not sloppy:** each one is read by a different consumer — the browser tab, a Slack/Discord/Twitter unfurl, and a search result snippet respectively — and they don't always render identically, so keeping them as separate fields (even when the content matches) means each surface can diverge later without touching the others.

**What `generate_rss_feed.py` actually depends on:** exactly four fields — `og:title`, `og:description`, `og:url`, and `<time datetime="...">` in `entry-meta`. Both `feed.xml` and `sitemap.xml` are generated from this same set in one pass; an entry missing any of the four is silently skipped from both outputs (the script prints a `SKIPPED` warning rather than failing the whole run). This is why `sitemap.xml` and `feed.xml` are both marked **do not hand-edit** in the site structure above — regenerate via the script after adding entries, don't append manually. `sitemap.xml`'s `<lastmod>` comes from each file's last git commit date (falls back to filesystem mtime if git isn't available), not from anything in the `<head>`.

**SEO vs. AEO, and why both get real weight here:** traditional SEO optimizes for a person typing a query and clicking a results-page link — title tags, meta descriptions, and the sitemap all exist to influence that click. AEO (answer-engine optimization) is a genuinely different target: an AI system synthesizing an answer without the person ever visiting the page at all, where structured data (the `Person` schema on the homepage, `BlogPosting` on every entry) matters more than click-through copy, since it tells a crawler unambiguously what a page *is* rather than requiring it to infer structure from prose. Full reasoning behind this split is in the [`08-09-2026` journal entry](https://michaelrooney.dev/journal/08-09-2026b.html).

**Internal + external linking inside prose:** journal entries (general, capstone, or leftfootLabs) should naturally link to genuinely related entries and relevant external resources where it adds real value — not forced in to hit a link count, and not limited to the `entry-nav` prev/next pair. This is real SEO/AEO value, not decoration.

**Inline link styling:** use the `.prose-link` class on inline `<a>` tags inside prose, not the browser default (blue/underline) and not a repurposed `.tag-*` class. `.prose-link` uses `var(--accent)`, matching the site's real accent color:

```css
.prose a.prose-link {
  color: var(--accent);
  text-decoration: underline;
  text-decoration-color: var(--accent-dim, currentColor);
  text-underline-offset: 2px;
  transition: color 0.2s, text-decoration-color 0.2s;
}
.prose a.prose-link:hover,
.prose a.prose-link:focus-visible {
  color: var(--text);
  text-decoration-color: var(--text);
}
```

## Adding a new journal entry — bundled checklist

A new entry is never just the entry file. Each one is one deliverable made of several coordinated edits:

1. New entry `.html` in `journal/`, `work/capstone/journal/`, or `work/leftfootlabs/journal/`, matching the `entry-header`/`entry-meta`/`prose`/`entry-nav` structure and the full metadata block above — with paths correct for that directory's depth (see Site structure above)
2. Previous most-recent entry's `entry-nav` updated to link forward to the new one
3. The relevant landing page's entry list — new `<li>` prepended (lists are `reversed`, newest first): `journal.html` for general entries, `work/capstone/capstone-index.html` for capstone, `work/leftfootlabs/leftfootlabs-index.html` for leftfootLabs
4. Run `python generate_rss_feed.py` to regenerate **both** `feed.xml` and `sitemap.xml` in one pass — never hand-edit either
5. If capstone: hours table row added to `work/capstone/capstone-index.html` **and** `00-Overview.md` (same numbers, both places — this project has had a real hours-log math error from these drifting, so ask before guessing on the actual figure)
6. Obsidian changelog entry (Summary/Added/Fixed/Investigated/Verified/Pending)

Favicon (`img/favicon/favicon.svg`, or the correct relative path from subdirectories) must be present in the `<head>` of any new page — it's been missed before.

## Accessibility

- Skip-to-content link (`.skip-link`) as the first focusable element on every page
- `role="navigation"` / `aria-label="Primary"` on the nav, `aria-expanded`/`aria-controls` on the hamburger toggle
- Full-card links on project/entry cards rather than a link buried in the text
- Mobile tap targets sized for touch, hamburger nav on all pages (not just some)
- Skills table uses `data-label` attributes so it degrades to a readable stacked layout on narrow viewports instead of a squeezed table
