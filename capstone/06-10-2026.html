Session 3 — The Proxy Layer

Every piece of this project up to this point has run entirely in the browser. React, TanStack Query, the Prometheus fetch calls — all of it is JavaScript the browser downloads and executes. That works for Prometheus because Prometheus has no secrets. This session introduced the first piece of the project that can't live in the browser: a small Express server whose only job is to hold a credential the browser should never see.

Why the browser can't hold credentials

The browser is a public environment. Any code or data that lives in the browser is accessible to anyone who visits the page. I had no idea how to build a proxy server before this session. I had never used Express, never heard of CORS, and didn't know how environment variables work in Node. But I did know that the Proxmox API token was a secret that couldn't go in the browser, so I knew I needed some kind of server layer to keep it safe. The rest was just research and experimentation until it worked.

The Proxmox API requires an API token to authorize requests. The token is a long credential string — something like prometheus@pve!monitor=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx. If that token lives in the React app, it lives in the browser. And anything in the browser is public. Anyone who visits the status page, opens DevTools, and watches the Network tab will see that token in plain text in the request headers. With it they could query the Proxmox API directly.

The solution is a server that sits between the browser and Proxmox. The browser never talks to Proxmox directly — it talks to the proxy. The proxy holds the token in an environment variable on the server, attaches it to every request it forwards to Proxmox, and sends the response back to the browser. The token never travels to the browser at all.

This pattern has a name: Backend for Frontend, or BFF. A thin server layer purpose-built to serve one specific frontend, handling credential management and API translation on its behalf. It's a well-documented architecture pattern worth searching for if you want to read further.

What Express is

Express is a minimal web framework for Node.js — the most widely used one. Node.js is JavaScript that runs on a server instead of in a browser. Express makes it straightforward to define routes and middleware in a small amount of code.

The proxy lives in a proxy/ folder at the monorepo root — a completely separate Node.js project from the React app. Its own package.json, its own dependencies, its own TypeScript config. It's a small independent server that happens to live in the same repository.

How the forwarding works

Rather than writing the forwarding logic manually, the proxy uses http-proxy-middleware — a library built specifically for this pattern. Every request to /proxmox/* gets forwarded to the Proxmox host with two modifications: the path gets rewritten, and the authorization header gets attached.

Path rewriting: when the browser asks for /proxmox/nodes, the proxy rewrites that to /api2/json/nodes before forwarding it to Proxmox. The browser doesn't need to know the internal Proxmox API path structure.

Header injection: the proxyReq handler runs on every forwarded request before it leaves the proxy. The browser sent a request with no credentials. The proxy adds the Authorization header with the token before Proxmox ever sees the request.

One Proxmox-specific detail: Proxmox uses a self-signed SSL certificate by default. The proxy sets secure: false to tell the forwarding library not to reject the connection over the unverified cert. Without this, every forwarded request would fail at the TLS handshake.

What CORS is and why it matters

CORS stands for Cross-Origin Resource Sharing. Browsers enforce a security rule: JavaScript on one origin — say localhost:5173, the Vite dev server — cannot make requests to a different origin — say localhost:3001, the proxy — unless the server at that second origin explicitly permits it.

Without CORS headers the browser would block every request from the React app to the proxy before it even left the browser. The middleware in the proxy sets two headers on every response: which origin is allowed, and which methods are permitted. The allowed origin is read from an environment variable so it can differ between development and production.

There's also an OPTIONS preflight check. Before making a cross-origin request, the browser sends an OPTIONS request first to ask whether the real request is permitted. The proxy responds with 204 (no content) and the browser proceeds. This happens automatically and invisibly — it only becomes visible if the CORS config is wrong and the preflight gets rejected.

How dotenv keeps secrets out of source code

dotenv reads a .env file from disk and loads its contents into process.env — Node's environment variable object. The proxy reads PROXMOX_HOST and PROXMOX_TOKEN from there at runtime.

The .env file is in .gitignore. It exists on the development machine and on whatever server the proxy runs on, but it is never committed to GitHub. The source code can be completely public — the credentials stay private because they only ever exist in the environment, not in the code.

The pattern is: code is public, configuration is private. Source code describes what the program does. Environment variables describe where it runs and what credentials it uses. Keeping those two things separate means the same code can run in development, staging, and production with different credentials and different targets — none of which appear anywhere in the repository.

The startup guard and health check

The proxy checks for required environment variables immediately on startup. If either PROXMOX_HOST or PROXMOX_TOKEN is missing it logs an error and exits rather than running in a broken state that might fail silently later. This is a fail-fast pattern — surface the problem immediately and loudly rather than letting it manifest as a confusing error elsewhere.

There's also a /health endpoint that returns {"status":"ok"}. This exists so the React app, Docker, and monitoring tools can verify the proxy is reachable before trying to use it. A health check is standard practice for any networked service — it's the first thing you hit when something seems wrong.

How the whole flow looks

The request path from browser to Proxmox and back:

  • Browser sends GET /proxmox/nodes to the proxy — no credentials attached
  • Proxy rewrites the path to /api2/json/nodes
  • Proxy attaches Authorization: PVEAPIToken=... to the request
  • Proxy forwards the request to Proxmox
  • Proxmox returns node data to the proxy
  • Proxy forwards the response to the browser
  • Browser receives node data — the token never appeared in any response
