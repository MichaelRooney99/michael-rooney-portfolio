Session 2 — Hook, Components, and First Live Render

Last session ended with a complete data layer and nothing in the browser. This session closes that gap. By the end of it the status page is rendering live data — five Proxmox nodes and a UPS, all pulling from real Prometheus metrics, updating on a 60-second poll. There was one debugging detour along the way that turned out to be instructive.

The TanStack Query hook

The hook — src/hooks/useServiceStatus.ts — is a thin wrapper around TanStack Query's useQuery. It calls fetchAllServices from the services facade and exposes three things to the UI: statusPage, isLoading, and isError. The UI never touches query keys, retry logic, or polling configuration directly.

The polling configuration is worth spelling out because each option is a deliberate choice:

  • refetchInterval: 60_000 — poll every 60 seconds. The underscores are a JavaScript numeric separator for readability only, no effect on the value.
  • refetchIntervalInBackground: true — keep polling even when the tab loses focus. Default behavior pauses polling when you switch tabs. For a status page that's the wrong call — you want fresh data when you come back to it.
  • retry: 2 — retry twice on failure before surfacing an error state. Uses exponential backoff between attempts.
  • staleTime: 55_000 — treat data as fresh for 55 seconds. Set 5 seconds under the refetch interval so cache hits don't fight with the polling timer.

Components — smallest first

The build order matters: smallest and most self-contained first, composing upward. StatusBadge has no dependencies on other components. ServiceRow uses StatusBadge. OverallHealth uses StatusBadge. App uses all three.

StatusBadge introduced a pattern worth understanding: Record<Status, config>. Rather than a switch statement or a chain of conditionals, all display configuration for each status value lives in a lookup table keyed by the Status union type. TypeScript enforces that every possible value has an entry — if a fifth status is ever added to the union, the object immediately errors until you add a matching entry. It also keeps the component itself clean: one lookup, done.

ServiceRow contains an internal sub-component — MetadataDisplay — defined in the same file but not exported. It only serves ServiceRow and has no reason to exist elsewhere. Keeping it colocated avoids creating a file whose entire purpose is to support one other component. The metadata display auto-formats camelCase keys into readable labels using a regex replace, and guards against rendering when the metadata object is empty.

OverallHealth uses the same Record<Status, ...> pattern for both the colored top bar and the headline text. A thin colored bar across the top of the card gives an immediate visual signal before any text is read — green for operational, yellow for degraded, red for outage. The timestamp converts the ISO string from the data layer into a readable local time using toLocaleTimeString, which respects the browser's locale automatically.

App.tsx — grouping and layout

App.tsx calls the hook and handles three states before attempting to render anything: loading, error, and the case where data is undefined. Guard clauses handle the first two and return early. Only after both checks pass is statusPage guaranteed to be defined.

Services come back from the data layer as a flat array. The UI groups them by category using a fixed display order — Proxmox Nodes, Power, Network, Services — with anything outside that list collected into Other. The grouping function returns a Map rather than a plain object because Maps preserve insertion order reliably. The categories render in the sequence they were inserted, which is the sequence we defined.

The UPS debug

First render showed all five nodes operational but the UPS returning Unknown, which pulled the overall banner to Unknown as well. The flags field was empty — flags: with nothing after it — which meant activeFlags was coming back as an empty array and none of the status checks were matching.

Querying nut_ups_status directly in Prometheus showed the cause immediately. The label key on those metrics is status, not flag. The adapter was reading result.metric.flag which doesn't exist on these metrics — it was always returning undefined, which never matched anything. One character change: result.metric.status. Overall banner flipped green on the next poll.

The right debugging move was going directly to Prometheus and running the raw query rather than guessing at the adapter code from google search results. The data was there and correct — the adapter just had the wrong label key. Seeing the actual metric structure makes the fix obvious in a way that staring at the TypeScript doesn't.

What the page shows now

Six services, all operational. Five Proxmox nodes each showing live CPU and memory percentages. CyberPower UPS showing OL flag, 51 minutes of runtime, 13% load. Overall banner green with a service count and last-updated timestamp. Polling every 60 seconds in the background.

What's next

The foundation is solid. Next session starts on the uptime bars component — 90-day colored blocks per service, the piece Perry specifically asked about and the most distinctly front-end challenge left in the project. After that: the Express proxy for the Proxmox API token boundary, the Proxmox adapter, and eventually the Cloudflare tunnel for public deployment.
