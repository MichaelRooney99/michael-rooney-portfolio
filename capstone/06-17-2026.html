Session 5 — Zabbix, Debugging, and a Deliberate Deferral

The goal for this session was the Zabbix adapter — a fourth data source using JSON-RPC over HTTP, a different protocol from everything else in the project. The proxy route got built, TypeScript errors got fixed, the right IP got found, and the API started responding. Then it became clear that Zabbix itself hadn't been configured with any hosts beyond the Zabbix server. The adapter works. The data isn't there yet. This session ended with a deliberate decision rather than a failure.

What Zabbix JSON-RPC looks like

Prometheus and Proxmox both use REST — different URLs for different resources. Zabbix uses JSON-RPC — every request goes to the same endpoint (/api_jsonrpc.php), and the body of the request describes what you want. A typical call looks like this: 

{
  "jsonrpc": "2.0",
  "method": "host.get",
  "params": { "output": ["hostid", "name", "status"] },
  "id": 1
}

The method field tells Zabbix what operation to perform. params is the arguments. id is a request identifier you choose — useful for matching responses when batching multiple calls, which we don't need here.

Zabbix also requires authentication before any data call. You call user.login first, get a token back, and include that token in every subsequent request. The proxy handles this automatically — login on first call, cache the token, refresh before it expires. Zabbix sessions expire after 15 minutes of inactivity by default, so the proxy refreshes 1 minute early to give headroom.

The proxy route

The Zabbix route in the proxy is a thin pass-through — it takes whatever method and params the client sends, gets or reuses the cached auth token, attaches it, forwards the request to Zabbix, and returns the raw response. The client decides what Zabbix data it wants. The proxy's only job is handling credentials.

One addition the Proxmox route didn't need: express.json() middleware on the route. The Zabbix route accepts a POST body from the client specifying the method and params. Without express.json() the body parser doesn't run and req.body is undefined. The Proxmox route uses http-proxy-middleware which handles body parsing internally — the Zabbix route is a manual handler so it needs explicit middleware.

The CORS middleware also needed updating — it originally only allowed GET requests. The Zabbix route requires POST, so Access-Control-Allow-Methods was updated to include POST. Without this the browser's preflight OPTIONS check would reject the request before it left the browser.

TypeScript strict mode errors

The proxy's TypeScript config has strict mode enabled. response.json() returns unknown in strict mode — not any — which means you can't access properties on it without narrowing the type first. Three errors surfaced:

  • json.error — can't access property on unknown
  • json.result — same issue
  • Return type mismatch — zabbixToken typed as string | null but function return type is string

The fix was a ZabbixLoginResponse interface and a cast on the parsed JSON. Adding a if (!json.result) guard after the error check narrows the type so TypeScript knows json.result is a string at the assignment point. The return type mismatch resolves automatically once that narrowing is in place.

Wrong IP — the expected mistake

The initial proxy/.env had ZABBIX_HOST=http://10.10.10.56:8090 — Murloc's host IP. Zabbix runs inside an LXC on Murloc at its own IP: 10.10.10.108. The proxy was trying to reach the Zabbix LXC at the wrong address entirely. Updating the env variable and restarting the proxy fixed it immediately.

This is the same class of mistake as the NUT LXC situation — confusing the Proxmox host IP with the LXC IP. In a multi-LXC environment these are always different. The host is the hypervisor. The LXC has its own IP on the same subnet. Worth having a reference of LXC IPs somewhere accessible.

The API works — the data isn't there

Once the correct IP was in place the sanity check returned: 

{"jsonrpc":"2.0","result":[{"hostid":"10084","name":"Zabbix server","status":"0"}],"id":1}

Login successful, token cached, request proxied correctly, response returned. One host visible: the Zabbix server itself. The Proxmox nodes and the GS308EP switch were never added to Zabbix after initial setup. The monitoring configuration — adding hosts, assigning templates, configuring SNMP for the switch — was always a "figure it out later" item that never got done.

The decision

Two options were on the table. Set up Zabbix monitoring properly now — adding all hosts, SNMP config for the switch, user group permissions — then build the adapter against real data. Or defer Zabbix configuration to a dedicated session, build a placeholder adapter that connects and returns whatever is visible, and move on to deployment.

The second option is the right call for where the project is. The status page has three working data sources, nine services rendering live data, and a public URL waiting to be wired up. Zabbix configuration is its own project — doing it properly deserves its own session and its own journal entry. Trying to do it inline here would slow deployment down for work that doesn't block anything else.

Knowing when to defer something is as important as knowing how to build it. The Zabbix adapter infrastructure is in place — proxy route, auth token caching, correct IP. When the monitoring config gets done, wiring it into the status page is a short session.

What's next

Deployment. The next session covers Docker Compose — bundling the React client build and the Express proxy into a single deployable unit — and the Cloudflare Zero Trust tunnel that makes the status page publicly accessible at status.michaelrooney.dev without opening any inbound ports.
