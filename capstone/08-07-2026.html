Session 19 — The First Real Tests, and a Folder Nobody Planned For

With all three planned scope docs closed out, the only remaining roadmap item was the one that had been sitting unscoped the whole time: automated tests. Zero coverage anywhere in this project, client or proxy — every real bug documented in this journal was found by hand, after the fact. This session is the first step toward that not being true anymore.

A scope doc for something that's never had one

Unlike 15-/16-/17-, which all had scope docs written before any code, testing had no doc at all — so this session opened with one: 18-Automated Test Coverage. The actual argument it makes isn't "100% coverage" as an abstract goal. It's narrower and more honest than that: every real bug this project has ever had is now a candidate for a specific, named regression test. That reframing did the actual prioritization work — instead of picking test targets by "what's easiest," the list became "what's already broken once."

The tension the doc had to name explicitly

This project's own convention — internal adapter helpers stay unexported, only the facade functions the app actually needs get exported — is good API design and directly at odds with testability. The functions most worth testing here are exactly the small, pure, internal ones: status derivation, day-bucketing, uptime-percent math. Resolution: a narrow, explained exception. Pure functions with no I/O get exported specifically for testing, each with a comment saying why — not a silent violation of the convention, a documented one.

Three targets, all with real bug history

utcMidnightSeconds and buildUptimeDays in history.ts are the exact logic that caused the real day-boundary timezone bug on 07-24-2026 — a direct regression test now runs two different times of day through the same function and asserts an identical anchor. deriveAvailability in zabbix.ts is the canonical copy of logic duplicated three times across this codebase, the same failure class as the nut_exporter/nut job-name bug from that same 07-24 session. calculateUptimePercent hasn't caused a bug yet, but it's the same shape of easy-to-get-subtly-wrong math the other two are — worth covering before it does, not after.

The lint rule that reshaped the plan mid-session

The original plan exported calculateUptimePercent straight from App.tsx, same file it already lived in. ESLint's react-refresh/only-export-components rule caught it immediately — a file that exports anything besides React components can't be safely hot-reloaded by Vite's Fast Refresh, so mixing a plain function export into a component file breaks that entirely. Fix wasn't suppressing the rule; it was moving the function to its own file. That turned out to be the better outcome regardless of the lint rule — a new client/src/lib/ directory, home for pure helpers that aren't a service adapter and aren't a component, which is honestly what this function always was.

Confirmed the way this session's own subject demands

Unlike command palette, auto-drafted incidents, or the SSE nudge channel — all of which needed the real deployed site to test meaningfully — this one runs entirely against local source, no deployment involved at all. npm test: 23 passed, 3 test files, 0 failures. Genuinely the fastest confirmation of any session so far, which is the actual point of this kind of testing existing.

What doesn't happen automatically yet

Worth being honest about the actual current state: a passing or failing test doesn't stop anything from running or deploying right now. npm test only executes when someone types it. That gap is exactly what led into the second document this session produced — 19-Deployment Testing and Playbook Safety, scoped but deliberately not built yet. It covers capstone_deploy.yml and the broader fleet playbooks with the same class of gap this project's Ansible work has already hit once (zabbix_agent.yml's three-layer idempotency bug): four separate layers — static linting, idempotency verification, a post-deploy smoke test, and gating a deploy on this session's own test suite passing — kept deliberately separate rather than one big "add CI" task, since they solve genuinely different problems at very different costs.

Where this leaves things

Phase 1 of 18- is built and confirmed. Phase 2 (proxy-side tests — db.ts's day-bucketing, the auto-drafted-incident threshold logic, nudge.ts's signature comparison) and Phase 3 (component/integration tests, deliberately deprioritized) remain open, alongside the newly-scoped 19- — the next real candidate for a session once it's sized.
