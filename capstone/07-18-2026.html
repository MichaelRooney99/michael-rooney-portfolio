Session 9 — Real History, and Two Loose Ends Tied Off

Session 8 ended with the site actually live and three items explicitly deferred rather than fixed: a stale reference doc, a stray function redefining itself on every render, and a 90-day uptime history that was still 100% placeholder. This session closed all three, plus a fourth that had been open since Session 7 and never came back around.

The reference doc that didn't exist

Ansible Reference.md had been cited throughout Ansible.md and Ansible-Refresher.md as "the full troubleshooting reference" for months, but it was never actually part of the uploaded file set — it existed in name only. Once it was finally uploaded, it turned out to document a five-node fleet with none of the last several sessions' playbooks or fixes in it: no Dega, no zabbix_agent.yml, no capstone provisioning, and none of the troubleshooting entries that had already been written up individually in changelogs but never consolidated.

Full rewrite, not a patch — six-node inventory, every current playbook, and every open troubleshooting pattern folded in: the missing Dockerfiles, the env-var crash-loop that looked like a networking problem, the --check --diff secret leak, VLAN double-tagging on Dega, the OPNsense rule-direction bug, and a quieter one that's cost real time more than once — group_vars has to live under inventory/, not the repo root, or variables silently fail to resolve with no error pointing at why.

A function that forgot where it lived

Small one: generatePlaceholderDays was declared inside the App() component body instead of at module scope, which meant it got redefined on every single render instead of once. Not causing a visible bug — just wasted work on every render cycle. Moved it up next to groupByCategory, where it should have lived from the start.

Wiring in real history

The uptime bars had been 89 grey blocks and one colored block since the component was first built — by design, deferred as future work back when the site was internal-only. Now that it's genuinely public, that stopped being an acceptable long-term state.

New adapter, services/history.ts, separate from the live-status adapters on purpose — it answers "what happened over the last 90 days," not "what's the state right now," so it runs on its own hook with an hourly poll instead of riding along with the 60-second live status query. Proxmox Nodes pull from up{job="node_exporter"} via query_range; the UPS pulls all three NUT status flags rather than just OL, so a day spent on battery shows as degraded instead of getting flattened into a plain outage — matching the priority logic the live adapter already used.

Proxmox API and Zabbix services stay on the placeholder, deliberately. Neither adapter has a queryable history source — they only ever see current state through a REST call or a JSON-RPC call, not a stored time series. There's no honest data to fetch for them, so the fallback isn't a gap to close later, it's the correct answer for what those sources can actually tell you.

One thing the bars make visible now that they didn't before: Prometheus keeps 30 days of retention, so every service's history — including the ones with a real Prometheus backing — trails off into grey past the one-month mark. That's not a bug in the new code, it's the actual shape of the data. Worth a decision at some point on whether to extend retention now that the gap is publicly visible, but that's an infrastructure call, not something to quietly change while wiring up a chart.

One grey day, explained

The first time the real bars rendered, every single service — all five nodes, the UPS, everything — showed an identical one-day gap on July 16th, sandwiched in the middle of otherwise continuous data. Fleet-wide, same day, every metric at once. That shape usually means Prometheus itself went down or lost scrape targets across the board.

It didn't. Every node had been physically powered off that day for a rack refit — moving the whole fleet into a 10-inch 10U rack I'd 3D-printed. Prometheus had nothing to scrape because the hosts genuinely weren't running. The history code reported that correctly; there was nothing to fix. Good reminder that a clean, fleet-wide gap in monitoring data is exactly as informative as it looks — it just doesn't tell you why on its own.

The idempotency gap that finally got closed

Flagged back in Session 7 and carried as an open item ever since: the cloudflared install task in capstone_provision.yml used creates: /etc/cloudflared/config.yml to decide whether it needed to run again — except a token-based cloudflared service install never writes a file there. It writes /etc/systemd/system/cloudflared.service instead. Every full re-run of the playbook re-attempted the install and failed with cloudflared service is already installed, which is a real error, not a false alarm — the service genuinely was already there, the check just never noticed.

One-line fix: point creates: at the file that actually gets written. Confirmed on Dega with --check --diff — the install task now reports ok instead of changed, same as any other properly idempotent task in the fleet.

Where things stand

All three items from the Session 8 handoff are closed, plus the cloudflared gap from Session 7. The uptime bars on status.michaelrooney.dev now show real data for Proxmox Nodes and Power going back 30 days, an honest placeholder for the two sources that don't have history to give, and one correctly-explained grey day in the middle of it that has nothing to do with the code at all.
