Session 22 — GitHub Actions, and a Folder That Never Existed

Second session of the day, picking up right where the first one left off — 23-GitHub Actions CI/CD, the item that had been the most exciting one on the list since it was first scoped. Building it turned out to surface something none of the excitement was about.

The client folder that was never real

Every scope doc written this entire session — every "Monorepo structure" diagram, without exception — described client/ and proxy/ as sibling folders. The actual repo doesn't match. proxy/ genuinely is nested; the client app lives directly at the repo root and always has. Nothing had ever broken because of this, since nothing before this session had actually executed against those paths — a CI workflow was the first thing to try, and it failed with a plain "No such file or directory" the instant it tried to cd into a folder that isn't there.

Fixed in the workflow itself by dropping the assumption — but the more interesting question was which direction to fix the real mismatch in: correct every doc to describe the flatter actual layout, or move the real files to match documentation that had been describing the cleaner shape all along. Chose the second, scoped separately as 26-Client Folder Restructure rather than rushed into the same session — this touches the live deploy pipeline directly (docker-compose.yml's build context, at minimum), and that's exactly the kind of change this project has always tested carefully before trusting, not something to squeeze in as an afterthought.

A deliberate line held on secrets

Ten playbooks need the Ansible vault password to fully resolve during ansible-lint's syntax-check — without it, all ten fail every single run. Adding the vault password to GitHub Actions would fix that, and would also be the first exception to something this project has held consistently since 22-: CI stays genuinely secret-free everywhere. The actual coverage lost by not adding it is narrow — deep variable-resolution checking specifically for vault-dependent values, not the bulk of what ansible-lint actually checks. Kept secret-free.

A permanently red check is worse than none

Left at default severity, those same ten vault-related findings would fail the build forever — a check that's always red teaches you to stop looking at it, which defeats the entire reason to have one. Fixed with a real .ansible-lint config moving them to warn_list: still visible in every run's output, correctly no longer blocking. The 30 real style findings underneath them — inconsistent colon spacing, missing trailing newlines across six inventory files — got fixed for real, and one deliberately didn't get the "obvious" fix: a long secret token over the line-length limit got an explicit noqa rather than YAML folding syntax, since folding rejoins line breaks as spaces — correct for wrapped prose, and something that would have silently corrupted the actual token value if applied to an opaque credential string instead.

Confirmed the way this project confirms things

Both workflows ended the session genuinely green — not red-with-an-accepted-asterisk, actual passing checks for real reasons. Real debugging along the way too: a caching step that failed for one reason (a path assumption) that turned out to be hiding a bigger one (the folder that never existed), traced properly instead of patched around.

Where this leaves things

23-'s CI half is done; CD stays deliberately unbuilt, per the doc's own reasoning about what GitHub's hosted runners can and can't reach. A real side effect worth naming: the same ansible-lint workflow satisfies 19-'s Layer 1 too — static linting, now live, not a separate task waiting for its own session.
