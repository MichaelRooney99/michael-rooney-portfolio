Session 7 — A VM, a VLAN, and a Backwards Firewall Rule

Session 6 ended with the data layer complete and a clear next step: deployment. Docker Compose to bundle the client and proxy, a Cloudflare Zero Trust tunnel to make the status page public, and Dega — the isolated VLAN 20 node built specifically for this — as the actual home for it. Today was supposed to be "spin up the VM, run the two playbooks, done." It took four separate detours to get there, each one worth writing down.

Skipping Portainer

Before touching the VM, one open question from the 07-10 session needed an answer: Portainer or not. The documented plan never actually called for it — capstone_deploy.yml brings the stack up directly via docker compose up -d --build through Ansible, no GUI layer involved. Given the entire reason Dega is a VM instead of the fleet's usual privileged LXC is reduced exposure for something internet-facing, adding a second web UI with its own auth surface on that same node would have worked against the reasoning that justified the VM in the first place. Skipped it — Ansible-driven Compose only, matching what was already planned.

Netinst is gone, cloud-init is better anyway

First real snag: the Debian 12 netinst ISO referenced in the original plan no longer exists on Debian's mirrors — 404. A directory listing against cdimage.debian.org confirmed current stable had moved to Debian 13 (Trixie), which — usefully — already matches what's documented for Dega's own host OS. Not a departure, just catching up to what's already true one layer down.

Rather than fight through the interactive installer a second time, this was the right moment to switch to a cloud image + cloud-init build instead — qm importdisk against a pre-built genericcloud-amd64.qcow2, network and SSH key trust configured via --ipconfig0 and --sshkeys rather than clicking through installer menus. Meaningfully faster, and repeatable in under a minute if Dega ever needs a second VM later.

Two small gotchas in that flow worth remembering next time: qm importdisk attaches the new disk as unused0, not scsi0 directly — has to be checked with qm config 200 | grep unused and attached explicitly. And --sshkeys pointed at ~/.ssh/ansible_ed25519.pub failed outright, because that keypair lives on the Ansible control node, not on Dega — had to scp the public key over first.

The VM that couldn't reach its own gateway

Once the VM was up, SSH from the control node timed out. Console access via qm terminal confirmed the VM had the right IP and a correct route table — but ping 10.10.20.1 from inside the VM came back Destination Host Unreachable, on the very first hop.

A host that can't reach one hop away, despite a correct IP and route table, is a Layer 2 problem — not a firewall problem. Firewall rules produce clean timeouts on already-established L3 connectivity. An ARP-level failure one hop out points at the bridge or VLAN config instead. Worth knowing the difference before spending time in OPNsense chasing a symptom that lives below it.

The cause: the original qm create included tag=20 on the virtual NIC. But Dega's physical uplink lands on switch ports 5–8, which are VLAN 20 untagged access ports — the switch already strips any tag before frames reach Dega at all. Adding tag=20 on top of a bridge that's already implicitly untagged VLAN 20 produced double-tagged frames the switch couldn't make sense of. Dropping the tag entirely — qm set 200 --net0 virtio,bridge=vmbr0, no tag — fixed it immediately.

Three wrong tokens

capstone_provision.yml failed twice on the cloudflared install step before the token was actually right. First attempt used the Tunnel ID from the dashboard's summary view — a UUID, not the connector token — which produced illegal base64 data at input byte 8. Worth noting: byte 8 lines up exactly with the first hyphen in that UUID string, which is a genuinely useful signature for "you copied the wrong field" rather than "the token is corrupted."

Second attempt copied the full Windows PowerShell install command wholesale — cloudflared.exe service install <token> — instead of extracting just the token itself. Same error class, different byte offset. The actual fix was realizing the token value is identical across every OS tab in the dashboard; only the surrounding install command syntax changes. Pasting just the raw base64 blob, with nothing before or after it, finally worked.

The rule that was pointed the wrong way

With cloudflared running, the playbook's three wait_for checks — confirming outbound reach to Ankhh, Prometheus, and Zabbix — all hung for the full timeout. Not a fast reject. A hang.

First ruled out the obvious suspect: pve-firewall status on Ankhh came back disabled/running, so the Proxmox host firewall wasn't the cause. The real answer was sitting in the OPNsense rule list the whole time — all three pinhole rules on the edge_Lab interface had source and destination reversed. They were written as "Ankhh / Prometheus / Zabbix → capstone VM," when the actual traffic that needs to flow is the reverse: the capstone proxy is the one initiating these connections on every poll cycle, not the other way around.

A firewall rule written backwards doesn't fail loudly — it just never matches. The packet falls through to whatever the next rule is, which in this case was the VLAN20 block rule. That's exactly why this looked identical to a missing rule rather than a wrong one, right up until actually reading the source and destination columns side by side.

There was also a second, compensating rule sitting on the LAN interface page — source Ankhh, destination the capstone VM, port 8006 — that looked like an earlier attempt to work around this same bug from the return-traffic side. Not needed once the real rule is fixed the right way; OPNsense's stateful firewall already permits return traffic for anything it allowed outbound. Flagged for cleanup rather than fixed in the moment, since Dega was mid-debugging and this wasn't blocking anything.

One more wrinkle before the fix actually took: the first attempt at correcting the rule direction still failed identically, because the edited rules had never actually been applied — a banner at the top of the OPNsense rules page warns about exactly this, staged changes that don't take effect until "Apply changes" is explicitly clicked, and it's an easy thing to miss mid-troubleshooting when the instinct is to immediately retest.

What's still a known gap

capstone_provision.yml's cloudflared install task checks creates: /etc/cloudflared/config.yml to decide whether to skip re-installing — but token-based installs never write to that path at all, writing the config into the systemd unit file instead. Every full re-run after the first successful one will try to reinstall a service that's already there and fail loudly. Same category of issue as the Zabbix repo idempotency gap from a few weeks back — documented, not fixed today, not blocking anything since provisioning itself is confirmed working via --tags verify.

Where things stand

The capstone Docker VM is live on Dega at 10.10.20.55, running Debian 13 via cloud-init, with correct untagged VLAN 20 networking. Docker and cloudflared are both installed and running. All three firewall pinholes — Ankhh, Prometheus, Zabbix — are corrected and confirmed reachable. capstone_provision.yml passes clean.

What's next

capstone_deploy.yml — clone the repo, write the proxy's .env from Vault, bring the Compose stack up. Then the public hostname route in the Cloudflare Zero Trust dashboard, and confirming status.michaelrooney.dev actually resolves end to end through everything fixed today.
