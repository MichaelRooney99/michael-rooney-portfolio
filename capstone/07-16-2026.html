Session 8 — Deployment Day: Dockerfiles, a Single Origin, and a Password That Got Away

Session 7 ended with provisioning confirmed clean — Docker and cloudflared running on the VM, all three firewall pinholes reachable — and one command left: capstone_deploy.yml. It felt like the last step. It was actually four separate problems wearing a trenchcoat.

The Dockerfiles that were never written

First run failed immediately: no configuration file provided: not found. The clone succeeded, the .env write succeeded, and then docker compose up had nothing to build from. Checking the actual repo confirmed it — docker-compose.yml referenced a root Dockerfile and a proxy/Dockerfile, and neither one existed. The compose file had been written ahead of the containers it was supposed to build, and the gap never got closed on the way to VM provisioning and firewall work.

Wrote both as two-stage builds — a Node stage to install and build, then a slim final stage. For the client, that's nginx:alpine serving the Vite output. For the proxy, it stays Node in both stages, but the run stage reinstalls with --omit=dev so ts-node and the TypeScript toolchain don't ship in the final image — just the compiled dist/index.js.

Two containers, one public port

First real deploy attempt built cleanly but exposed a design gap that had been sitting unaddressed since the tunnel route was first discussed: the client and proxy were built as two independent containers on two separate ports, but the Cloudflare tunnel only routes one public hostname to one origin. A browser hitting localhost:3001 from outside the LAN resolves to the visitor's own machine, not Dega — that request was never going to work no matter how correctly everything else was configured.

The fix wasn't more infrastructure, it was less exposure: nginx serves the static build and reverse-proxies /proxmox, /zabbix, and (later) /prometheus internally to the proxy container over the Compose network. The browser only ever talks to one origin. The proxy stops being something the public needs to know exists at all.

The other half of that fix lives in the client build itself. Vite bakes VITE_PROXY_URL into the compiled JS at build time, not runtime — the adapters' dev-mode fallback of http://localhost:3001 would have shipped straight into production otherwise. Writing an empty value into .env.production before npm run build makes the nullish-coalescing fallback in the adapter code treat it as "set, just empty" rather than "unset" — so the fetch calls become same-origin relative paths instead of pointing at a port that doesn't exist for anyone outside this laptop.

The proxy that wouldn't start

With the compose file and nginx config both fixed, the stack built and nginx came up — but every proxied path returned a clean 502 Bad Gateway. Nothing was listening on 3001 at all.

The cause was sitting in the proxy's own startup guard: process.exit(1) if ZABBIX_HOST, ZABBIX_USER, or ZABBIX_PASSWORD are missing. capstone_deploy.yml's .env write task had never been updated to include them — it only ever wrote the Proxmox variables from when the Zabbix adapter didn't exist yet. The container started, hit that guard immediately, and exited. nginx's 502 was accurate: there genuinely was nothing behind it.

Added the three missing variables, plus new Vault entries pulling the existing api-readonly Zabbix credentials that were already documented from the adapter work back in Session 5 and 6. Caught one more small thing in the same pass — the task wrote CORS_ORIGIN, but the proxy code actually reads CLIENT_ORIGIN. Wrong variable name, silently falling back to a dev default. Harmless now that everything's same-origin through nginx, but worth fixing for accuracy regardless.

The password that got away

Re-running with --check --diff to preview the env file change before applying it for real — standard practice all session — printed the new Zabbix password in plaintext to the terminal. Vault encrypts the file at rest, but --diff shows the decrypted content being written, and that content ended up in a shared, logged session.

Vault protects a file on disk. It does nothing to protect output printed to a terminal that's being watched, copied, or logged elsewhere. --check --diff is genuinely useful for previewing config changes, but any task that writes a secret needs no_log: true regardless of whether you're using diff mode that particular run — the moment secrets show up in playbook output is the moment they stop being secret, and that moment doesn't announce itself in advance.

Rotated the credential and added no_log: true to the task before moving on — flagged explicitly as open until both were actually confirmed done, rather than assumed fixed just because they'd been discussed. That distinction matters: a conversation about a fix isn't the fix.

Live, but quietly incomplete

With the env fix in place, deployment finally succeeded clean — health check 200, real Proxmox node data flowing through the proxy. Configured the Cloudflare Zero Trust public hostname route (one small snag: the Service URL field needs an explicit http:// scheme, a bare host:port wasn't enough), and curl -I https://status.michaelrooney.dev came back HTTP/2 200.

Looked done. Wasn't. Opening the actual site showed 9 services instead of 14 — every Proxmox API and Zabbix entry present, but all 5 Proxmox Nodes and the UPS entirely missing, with no error anywhere on the page.

Third time this exact failure shape has shown up across the project — Session 4's missing Sys.Audit permission, Session 6's Zabbix availability field move, and now this. Promise.allSettled is doing exactly what it's designed to do: a failed adapter disappears cleanly rather than breaking the page. That's the right behavior for a visitor. It also means a real bug and "working as intended" look identical from the outside, every time, and the only way to tell them apart is to go check the adapter directly rather than trust that a rendered page means a working page.

The cause: prometheus.ts was the one adapter that never got moved behind the proxy. It fetches 10.10.10.105:9090 directly — fine on the LAN during development, unreachable from anywhere on the public internet, tunnel or not, since the tunnel only exposes what nginx serves. Every public page load, both Prometheus-backed categories failed instantly and silently. This is the first time the site was ever actually tested from outside the LAN, so it's also the first time this could have been caught.

Added a /prometheus route to the proxy — same shape as the existing /proxmox forward, no auth needed since this is purely a reachability problem, not a credentials one. One more nginx location block, one more baked-in build-time env var, redeploy. All 14 services showed up on the next load.

Where things stand

status.michaelrooney.dev is live, publicly reachable, serving real data from all four sources — Prometheus, the Proxmox API, Zabbix, and NUT. Single-origin architecture throughout: the browser only ever talks to nginx, which is the only thing the tunnel exposes and the only thing that needs to be trusted from outside.

Both loose ends from the credential leak are closed now too — the Zabbix password rotated, no_log: true confirmed in the playbook. Deployment day is actually done, not just looking done.
