Session 1 — Scaffold, Dependencies, and Data Layer

The internship capstone project is a public-facing infrastructure status page — something like Atlassian Statuspage but built from scratch and self-hosted. The goal is a React SPA that polls live data from Prometheus and the homelab infrastructure, shows the current health of every node and service, and deploys publicly at status.michaelrooney.dev via Cloudflare Zero Trust tunnel. Today was session one: scaffold, dependencies, data layer, and nothing in the browser worth looking at yet.

Starting from scratch

I had a working version of this project from a previous session but made a deliberate choice to rebuild it from the beginning rather than pick up from existing files. The reasoning was straightforward — hand-keying the code produces a better journal, a more accurate hour log, and a project I can speak to completely in a conversation with Perry or anyone else who asks about it.

The scaffold is Vite with React and TypeScript. Vite replaced Create React App as the standard way to scaffold React projects — it starts faster, builds faster, and doesn't carry CRA's legacy weight. TypeScript over plain JavaScript because the data layer in this project is complex enough that catching type errors at compile time is worth the overhead.

The dependency choices

Three production dependencies beyond React itself: TanStack Query, Recharts, and Tailwind CSS.

TanStack Query deserves the most explanation because it replaces something you'd normally reach for instinctively. The standard React pattern for fetching data is a useEffect with a fetch call inside it, combined with useState for loading and error states. That works but it has real gaps — no automatic retries, no background refetching, no caching, and every component that needs data has to wire all of it up independently. For a status page that needs to poll Prometheus every 60 seconds and update automatically, building that reliably with useEffect and setInterval is genuinely fiddly. TanStack Query handles all of it in a single hook call with a refetchInterval option. Notably, TanStack Query is not part of the official React documentation — it lives at tanstack.com/query as a third-party library.

Tailwind v4 uses a Vite plugin instead of a config file. The entire CSS setup is one import line in index.css. That's a meaningful simplification over v3.

Wiring up TanStack Query

Before writing any fetching code, TanStack Query needs to be wired into the app at the top level. This means creating a QueryClient — a single object that holds the cache, configuration, and state of every query in the app — and wrapping the entire component tree in a QueryClientProvider that makes it available everywhere. This goes in main.tsx, one level above App. Any component below it can then use the useQuery hook without passing anything down through props.

Types before code

The first real file written was src/services/types.ts — the data contract for the entire project. Before any fetching logic exists, the shape of the data is defined. The key pieces:

  • Status — a union type: 'operational' | 'degraded' | 'outage' | 'unknown'. A union type restricts a value to one of a specific set of strings. Assigning anything else causes a TypeScript error at compile time.
  • ServiceStatus — the normalized shape every adapter must output. Every data source — Prometheus, NUT, Proxmox, Zabbix — speaks a different protocol and returns different structures. The adapter for each is responsible for translating its raw response into this single agreed shape. The UI only ever works with ServiceStatus objects.
  • StatusPage — the top-level shape: overall status, array of services, array of incidents, and a timestamp.

Writing types first forces decisions about the data model before you're in the middle of writing logic. Once ServiceStatus is defined, every adapter knows exactly what it needs to produce. TypeScript will flag anything that doesn't match.

The Prometheus adapter

src/services/prometheus.ts contains two exported functions and one internal helper. The helper — queryPrometheus — centralizes the fetch, error handling, and JSON parsing so neither adapter has to repeat it. It is not exported because nothing outside this file needs it directly.

Both adapters fire multiple Prometheus queries concurrently using Promise.all rather than awaiting them sequentially. Three queries running simultaneously instead of one at a time — a meaningful difference on a polling interval.

The NUT adapter required understanding something non-obvious about how the nut_exporter formats UPS status. Rather than a single numeric value, it emits one row per possible flag — OL, OB, LB, and others — with a value of 1 if that flag is currently active. Reading the UPS status means collecting all active flags and deriving state from their combination. Two other quirks worth noting: nut_battery_charge returns a boolean in this exporter version, not a percentage — use the warning and low flags instead. And nut_load returns a ratio between 0 and 1, not a percentage — 0.15 means 15% load, multiply by 100 for display.

The services facade

src/services/index.ts ties the adapters together. Its main function — fetchAllServices — calls every adapter concurrently using Promise.allSettled rather than Promise.all. The distinction matters: Promise.all fails fast — one failing adapter takes down everything. Promise.allSettled waits for every promise regardless of outcome, then processes only the ones that succeeded. If the Proxmox adapter is down, the page still renders Prometheus and NUT data. Partial visibility is better than a blank page.

Overall status uses worst-status-wins logic — outage beats degraded beats operational. One node down means the overall banner shows outage even if everything else is healthy.

What's next

The data layer is complete for the two working sources. Session 2 picks up with src/hooks/useServiceStatus.ts — the TanStack Query hook that wraps fetchAllServices and handles polling, caching, and error states — then moves into the UI components. Nothing renders yet. That changes next session.
