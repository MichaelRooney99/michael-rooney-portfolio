Session 11 — Giving Every Category Real History

Two roadmap items had been sitting scoped-but-not-built for a while: real uptime history for the two categories that never got it, and scripting the manual Zabbix host-registration step. Small wins first — a collapsible incident list, two genuinely stale Ansible docs finally deleted — then both mediums got properly scoped before either got touched, and the bigger one got built the same session.

Small first

The incident history section only ever had two entries, but per-card collapse was worth doing now rather than later — active incidents default open, resolved ones default collapsed, same pattern real status pages use. And Ansible_Reference.md and Ansible-Refresher.md — both fully superseded weeks ago by the consolidated capstone/fleet split — were still sitting in the active project files, which is exactly the kind of drift that caused the original documentation mess in the first place. Deleted for real this time.

Scoping before building, again

Full-category history turned out to need more thought than "add a route." Proxmox Nodes and Power get their 90-day bars from Prometheus, which already scrapes independently of whether anyone's looking at the page. Proxmox API and Zabbix have no equivalent — building this meant the proxy itself becoming that missing scraper, which is genuinely new territory for this codebase, not a component tweak.

Three real decisions got worked through before any code: where the status-derivation logic should live (duplicated proxy-side, kept small on purpose, rather than standing up shared-package tooling across two separate npm projects for one small function), how often to poll (frequent, with a worst-of-day rollup — deliberately not the same "keep it simple" call made on the first decision, since these two categories have zero other source of truth to fall back on if a single sample misses something), and what to store it in.

That last one didn't stay theoretical. Rather than guess whether node:sqlite would work without the old --experimental-sqlite flag, I exec'd straight into the actual deployed proxy container and ran require('node:sqlite') directly. v22.23.1, confirmed working, zero new dependencies, zero Dockerfile changes. Nice to settle an architecture decision with a real terminal result instead of a version-number guess.

A bug found while scoping, not while building

Working out what the poller's status logic should mirror meant actually reading the existing client adapter closely — and it had a real bug. Nodes got filtered down to "online" before the code that was supposed to decide operational-vs-outage ever ran, which meant the outage branch of that ternary could never execute. A genuinely offline Proxmox node didn't show as down. It just silently disappeared from the page.

Worth a real decision, not a silent pick: mirror that behavior in the new poller, or fix it properly. Went with fixing both — the poller and the live client adapter — since building new history-tracking code that deliberately reproduces a known gap felt worse than the small risk of the live page and the history bars occasionally disagreeing about a node that's actually down.

Building it

The poller reuses the proxy's own existing /proxmox and /zabbix routes over localhost rather than duplicating upstream auth and TLS-bypass logic a second time — one source of truth for "how to reach Proxmox," used by the browser and the poller alike. SQLite handles the day-bucketed worst-of-day rollup, anchored to the same UTC-midnight boundary the client's history code already got fixed to use last session — not repeating that exact mistake twice.

tsx doesn't type-check anything, just strips types and runs — which is exactly why four real ts(18046) errors sat quietly in the terminal while local dev looked completely fine. proxy/Dockerfile's build stage runs actual tsc, which would have failed the Docker build outright on deploy. Caught by checking the Problems panel instead of trusting a clean npm run dev — a good reminder that "runs locally" and "type-checks" aren't the same claim when the dev tool and the build tool don't agree on how strict to be.

Applying last session's lesson instead of relearning it

Incident history shipped working in dev and silently empty in production, because nginx never got a forward rule for the new route. That turned into an actual written checklist: proxy route, client adapter, nginx forward rule, verify through the public domain. This session, the nginx block for /history went in before the first deploy, not after discovering the same gap a second time. Small thing, but exactly the kind of small thing that's easy to skip under momentum — worth noticing that writing the lesson down last time is what made it automatic this time.

Where things stand

Confirmed live through the actual public domain, not just the direct proxy port — today shows real data, every day before it honestly says no-data, since there's nothing to backfill from before the poller existed. Both scoped mediums from a few sessions back are done now. The one surviving open item — scripting Zabbix host registration — is fleet-wide infrastructure work, not capstone-app work, so it stays tracked with the rest of the Ansible roadmap instead of here.
